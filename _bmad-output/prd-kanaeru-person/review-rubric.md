# PRD Quality Review — 人物メモ（prd-kanaeru-people）

点検日：2026-11-27。もとにした決まり：`.claude/skills/bmad-prd/assets/prd-validation-checklist.md`。前提：最初は持ち主1人で使い（`operator_only`）、あとで営業・フリーランス向けに一般に出す。書き方は試合表アプリの PRD（`prd-kanaeru-match`）の流儀に合わせている。読む先は `specs/people/` の spec-kit の仕様。

## Overall verdict

ねらい（「前に話した○○、どうなりました？」と自分から言える）が1つにはっきりしていて、UJ-1 の場面A・B から FR とプライバシーの決めごと（AI に渡さない・顔写真なし・電話とメールの欄なし）まで筋が通っている。「持ち主が決めた」と【仮決め】の区別、作らないものの一覧（7.2）、公開前の条件（7.3）も、個人で使う段階としては十分に正直である。危ういのはデータの形で、**「会った場」が人をまたいで共有される1つの記録なのか、人ごとの付け札なのか**が決まっておらず、**FR-P4（電波が切れても失わない）と 7.2（電波がないときに書いて後で送ることは作らない）がぶつかっている**。作る順（7.1）で表を作る PR が先に来るため、仕様に入る前にこの2つを決めておくべきである。

## Decision-readiness — strong

決めたことは決めたこととして書かれている。FR のほとんどに「（持ち主が決めた）」か【仮決め】が付き、何を人が決め何を AI が置いたかが一目でわかる。調べもの（`research-competitors.md` 4章）が勧めたもののうち、「次に話したいことをチェックで消す」「会った回ごとの記録」を 7.2 で「持ち主が決めた」として明示的に断っている点は、反論する人が自分の論点を見つけられる書き方で良い。10章の「決めきれていないこと」3件は、どれも答えが次の文に書いてある飾りの問いではなく、本当に開いている（LINE のリンク・event の関数・規約の時期）。

弱いのは、調べもの b7 と食い違う決定を、食い違いとして書いていない点である。

### Findings

- **[medium]** b7 の「専門家確認が済むまで作らない」と、今作る決定の関係が書かれていない（§0・§7.3） — b7（5章・8章）は「**専門家確認が済むまで作らない**」「それまでは受付アプリの参加したイベント一覧に自分用のメモ欄を付ける程度の小さな実験」と結論している。PRD は 7.3 で専門家確認を「一般に公開する前」に回し、今は `operator_only` で作る。これは筋の通った決定だが、b7 の結論を覆していることがどこにも書かれていないため、b7 を読んだ人には見落としに見える。*Fix:* 7.3 の頭か 1章に「b7 は専門家確認まで作らないとしたが、持ち主1人の自分用（運営者＝書く本人）に限って先に作る。他人の情報を他人の利用者から預かるのは 7.3 を満たしてから（持ち主が決めた）」と1文足す。
- **[low]** 断った案で何を手放したかが書かれていない（§4.1 FR-P3・§7.2） — 「会った回ごとに分けた記録」を作らないことで、「いつの会で何を話したか」の時系列が失われる（調べもの 4章の2「会った記録を人の項目と分ける」は何年も出ている要望）。手放したものが書かれていないので、のちに一般に出すときに戻すべきかを判断しにくい。*Fix:* 7.2 の該当行に「代わりに失うもの：会ごとに何を話したか。一般に出す前に見直す」と添える。

## Substance over theater — strong

飾りはほとんどない。人物は持ち主1人だけで、2.2 の「相手にしない人」3つはそれぞれ機能の線引き（名刺の読み取り・共有・顔写真）に直結している。守ること（5章）は「安全・確実」の決まり文句ではなく、「MCP のツールも作らない」「電話番号・メールの欄を作らない」「メモの本文と人の名前はログに書かない」のように、この製品にしか当てはまらない中身になっている。ねらい（1章）もほかの PRD に差し替えられない具体さがある。

唯一の形容詞は 5章「気軽さ」の「スマホの片手で、1人を足すのが短く済む形にする」で、数の上限は 8章の逆の目印（2分）にだけある。これは Done-ness の側で扱う。

## Strategic coherence — adequate

賭けははっきりしている：名刺ではなく「どこで会い何を話したか」の文脈を残し、「交流会（会った場）」を単位にする（調べもの 4章の3・8）。FR-P6〜P8・P13 がその賭けをそのまま形にしている。成功の基準（8章）も、使った回数や登録人数ではなく「『前に話した○○』と自分から言えた回数」というねらいそのものを測っており、逆の目印（書くのが重すぎる）も置いてある。MVP の種類は「自分の困りごとを片づける」で、範囲の切り方と合っている。

ずれているのは、作る順と、基準を測ったあとの使い道である。

### Findings

- **[medium]** 作る順の1番目が、ねらいの中心でない領域をまたぐ PR になっている（§7.1・§2.1） — 2.1 で持ち主自身が「会う人の多くはそれ以外の会（connpass の勉強会・紹介の会など）で会う」「受付アプリを使う会はこれから月に一度」と書いている。それなのに 7.1 の1番目は受付（reception）の小さな PR（自分がチェックインした交流会の一覧）で、しかも持ち主は主催者として自分の会にチェックインしないことが多い（主催した会は event 側で読む）。ねらいの中心（4.1・4.3：足す・書く・探す）はこの PR に頼らない。共通の PR を先に入れる手間と調整（parallel-development の 4）を、いちばん価値の小さい部分のために最初に払う順になっている。*Fix:* 7.1 を「表 → 足す・書く・探す（会った場は手で書くだけ）→ kanaeru の交流会から選ぶ（ここで受付・event の PR）→ 続けて何人も足す → 書き出しと退会」に並べ替えるか、今の順の理由を書く。
- **[medium]** 成功の基準を測る方法が弱く、結果で何を決めるかがない（§8） — 「月に一度、持ち主が振り返って数える」は、1か月前に何回言えたかを記憶で数える形で、まさにこのアプリが解こうとしている「思い出せない」に頼っている。また「月3回以上」を満たした・満たさなかったときに何を決めるのか（7.3 に進むのか、機能を足すのか、やめるのか）が書かれていない。*Fix:* 言えたらその場か帰り道に、その人のメモへ一言書く（「話せた」など）か、手元のメモに印を付けると決めて数えやすくする。基準の後ろに「満たせば 7.3 に進む／満たさなければ逆の目印を見て、入力の重さを直す」のように、結果ごとの次の一手を1行足す。

## Done-ness clarity — thin

FR-P1・P5・P8・P10・P12・P17 は、そのまま受け入れの条件に書き直せる程度に具体的である（例：FR-P10 の検索が当たる欄の列挙と、ひらがな・カタカナ・全角半角の揺れ）。しかし、データの形を決める FR に解釈が2通りに割れるものがあり、7.1 では表を作る PR（DB の変更だけ）が早い段に来るため、そこで取り違えると作り直しが重い。

### Findings

- **[high]** 「会った場」が共有の記録か、人ごとの付け札かが決まっていない（§3「会った場」・FR-P6・FR-P7・FR-P13・FR-P9） — ことばの表では「その人に会った交流会。…1人に何回でも付く」と人の属性のように書かれている。一方、FR-P7「会った場を1回選んだら、そこで会った人を続けて何人も足せる」と FR-P13「会った場ごとに、そこで会った人を並べて見られる」は、**手で書いた会った場も、名前と日付を持つ1つの記録として何人もが指す**形を前提にしている。手で書いた「Go 勉強会 11/20」を2人に別々に付けたとき、同じ会として FR-P13 で1つにまとまるのか、名前を直したら全員に効くのか、会った場そのものを消せるのか、が決まらない。FR-P9（交流会が消えたら名前と日付を残す）の写しをどこに持つかもこれで変わる。*Fix:* ことばの表に「会った場は、名前・日付・（任意で）kanaeru の交流会を持つ1つの記録で、何人にも付けられる。持ち主ごとに持つ」と決めて書き、FR に「会った場の名前・日付を直せる（付いた人すべてに効く）」「会った場を消すと、人からその付け札が外れ、人は残る」を足す。同じ kanaeru の交流会を2回選んだときは同じ会った場になる、も書く。
- **[high]** FR-P4 と 7.2 がぶつかっている（§4.1 FR-P4・§7.2） — FR-P4【仮決め】は「書きかけで画面を離れても、書いたものを失わない（帰り道に電車を降りる・**電波が切れる場面**）」。7.2 は「電波がないときに書いて後で送ること」を作らない（持ち主が決めた）。電波が切れたまま保存を押したとき、書いたものを端末に残してあとで送るなら 7.2 に反し、残さないなら FR-P4 に反する。5章の夜の停止（0時〜8時に DB が止まる）でも同じことが起きる。*Fix:* FR-P4 を「書きかけは端末（ブラウザ）に下書きとして残り、画面を開き直すと戻る。送れなかったときは『送れませんでした』と出し、下書きは消さない。自動で後から送ることはしない」のように、何が残り何をしないかで書く。7.2 の行にも「下書きを端末に残すのは別（FR-P4）」と添える。
- **[medium]** FR-P3「続けて書き足せる」が、FR-P2 のふつうの書き直しと何が違うのかがない（§4.1 FR-P3・UJ-1 の5） — 会った回ごとの記録を作らないなら、「書き足す」は「話したこと」の文を書き直すのと同じに見える。日付の見出しを自動で入れるのか、どの会った場で話したかを残すのか、が決まらないと、仕様で受け入れの条件が書けない。ねらいの「前に話した○○」は「前回」がどれかわかることに頼っている。*Fix:* 「書き足すときは、話したことの終わりに日付（と選んだ会った場の名前）を自動で入れてから続ける」のように1つ決めるか、「ふつうの書き直しと同じで、区切りは持ち主が自分で書く」と明記する。
- **[medium]** FR-P11 の並び順のキーが2つあり、どちらが勝つかがない（§4.3 FR-P11） — 「最近書いた・会った順」は、メモを書き直した時刻と、いちばん新しい会った場の日付の2つがある。手で書いた会った場に過去の日付を入れたとき、どちらで並ぶかが割れる。*Fix:* 「最後に書き直した時刻と、いちばん新しい会った場の日付の、遅い方で並べる」のように1つの式で書く。
- **[medium]** FR-P7「続けて何人も足せる」の流れの終わりが測れない（§4.2 FR-P7・§5 気軽さ・§8） — 「1回に10〜20人」とあるが、1人あたり何を入れれば次に進めるのか（名前だけで次の人へ進めるのか）、前に足した人を選ぶときの探し方、途中で抜けたらどうなるかがない。5章の「1人を足すのが短く済む形」は形容詞で、上限は 8章の逆の目印「2分」にしかない。*Fix:* FR-P7 に「会った場を選んだ画面のまま、名前を打って足すと次の人の入力に戻る（ほかの欄はあとで書ける）。前に足した人は名前の検索で選ぶ」を足し、5章に「名前と見た目の特徴だけなら、1人を足すのは〇秒以内・〇回の操作」のような上限を置く（8章の2分と同じ数でよい）。
- **[low]** CSV の中身が決まっていない（§4.5 FR-P16） — 1人に何回も付く会った場・いくつものタグ・アカウントを1行にどう入れるか、文字コード（Excel で開くなら BOM 付き UTF-8）が書かれていない。機種変更とバックアップの不安を消す（調べもの 4章の6）という目的なら、後で読み戻せる形かも決めておきたい。*Fix:* 「1人1行。会った場とタグは『；』でつなぐ。BOM 付き UTF-8。読み戻しはこの版では作らない」程度を書く。
- **[low]** タグの手入れが書かれていない（§4.1 FR-P2・FR-P12） — タグの名前を直す・まとめて消すができるかがない。人数が増えると揺れ（「Go」「golang」）が出る。*Fix:* 作るか作らないかを1行で決め、作らないなら 7.2 に足す。

## Scope honesty — adequate

7.2 の「この版で作らないもの」は、黙って抜けていそうなもの（名簿を候補に出す・AI・顔写真・電話とメール・知らせ・夜の利用）をきちんと拾っている。【仮決め】14件はすべて 9章に集まり、本文と一覧が往復する。個人で使う段階の割に未決の数は多めだが、低い賭け金で中身のある仮決めなので問題ない。

抜けているのは、構成の決めごとの「既定の形」から外れる部分と、似たアプリなら当然ある欄である。

### Findings

- **[medium]** 組織に入れないことが書かれていない（§5 権限・§6） — 構成の決めごと AD-19・AD-22 は「新しいアプリの最上位の記録は組織に入れられ、持ち主の退会では組織の管理者に引き継ぐ」形を既定にしており、試合表（AD-25）もそうしている。人物メモは「本人だけのもの」なので組織に入れない・チームにも入れない・退会では引き継がずにすべて消すはずだが、PRD は組織に一言も触れていない。仕様を書く AI が AD-19 の型どおりに `people_*_organization` を作るおそれがある。*Fix:* 6章に「AD-19・AD-22：人物メモは組織にもチームにも入れない。退会の手順 (2) で引き継ぐものはなく、すべて消す（持ち主が決めた）」を足し、7.2 にも「組織・チームに入れること」を足す。
- **[medium]** 似たアプリが持つ欄（ふりがな・所属／会社・職種）を持たないことが、作らないものに書かれていない（§4.1 FR-P2・§7.2） — 調べもの 1章のほぼすべてのアプリが「ふりがな」「所属・職業」を持ち、★1 には「カナで検索しても当たらない」がある。PRD の欄にはどちらもなく、7.2 にも出てこない。IT 交流会では会社や職種は思い出す手がかりとして強い。持ち主が「話したこと・見た目の特徴に書けば足りる」と決めたのなら、それを書いておかないと仕様で足されるか、足すべきか迷う。*Fix:* 欄に足すか、7.2 に「ふりがな・所属・職種の欄（話したことや見た目の特徴に書く）」と理由付きで書く。
- **[low]** 公開前に暗号を足すとき、すでにある平文のメモをどうするかがない（§5 個人の情報・§7.3） — 「最初の版は暗号にしない」「一般に公開する前に暗号の形を決める」とあるが、それまでに書いたメモを暗号に移すのか、端末だけの鍵を選んだ場合にどう移すのかが書かれていない。*Fix:* 7.3 の暗号の行に「それまでのメモも移す（移し方は暗号の形と一緒に決める）」と添える。

## Downstream usability — adequate

ことばの表（3章）があり、FR-P1〜P17 は抜けも重なりもない。UJ-1 は主人公（持ち主）を持ち、FR-P14 などから「UJ-1 の3・4」と引かれている。各節は単独で抜き出しても AD 番号と章番号で辿れる。spec-kit の仕様に分けるときの切れ目（7.1 の段）も見えている。

足を引っぱるのは、同じ人を指す呼び名の揺れと、構成の決めごとに足すべきものの列挙漏れである。

### Findings

- **[medium]** 「持ち主」「主催者」「運営者」が同じ人を指したり、違う役を指したりする（§0・§5・§6 AD-16） — 0章は「持ち主（主催者）」、5章は「運営者の画面にメモの中身を出さない」「運営者は読まない」、6章 AD-16 は「運営者だけに見える（`operator_only`）」。最初の版では3つとも同じ1人だが、仕様では「メモを書く本人（どの account でもよい役）」と「運営者（AD-16 の台帳の役）」を分けて作る必要がある。今の書き方では、5章の「運営者の画面に出さない」が持ち主自身にも効くように読める。*Fix:* ことばの表に「持ち主：メモを書く本人の account。最初の版では運営者と同じ人だが、役としては別」と「運営者：AD-16 の運営者」を足し、本文の「主催者」は交流会の主催者の意味だけに使う。
- **[medium]** 構成の決めごとに足すべきものが一部しか挙がっていない（§6） — 6章は「ログに書かないもの」の追記は挙げているが、AD-3 の「表を作る PR の順（account → … → match）」と「持ち主の表の一覧」に `people` を足すことと、試合表の AD-25 にあたる人物メモの AD（領域・表・`uses`・権限・消し方）を足すかどうかに触れていない。仕様を書く AI が共通の文書の変更を見落とすと、parallel-development の「共通は先に小さな PR で」が守れない。*Fix:* 6章に「AD-3 の順と表の一覧に people を足す」「人物メモの AD を足す（または足さない理由）」を、共通の小さな PR として挙げる。
- **[low]** 1章の「連絡先」と、ことばの表の「アカウント」が揃っていない（§1・§3） — 1章は残すものに「連絡先」を挙げ、3章・FR-P2 は「アカウント」（電話番号とメールは欄を作らない）。「連絡先」は電話・メールを連想させる。*Fix:* 1章を「アカウント（X・LINE ID など）」に揃える。

## Shape fit — strong

持ち主1人が使う道具として、UJ は1本だけ、FR は機能の一覧の形で、成功の基準も持ち主が数える運用の目印になっている。重すぎも軽すぎもしない。チェーンの先頭（`specs/people/` の仕様に分ける）なので ID とことばの表を持つのも釣り合っている。のちに一般に出すときの相手（営業・フリーランス）の UJ を今書いていないのも、7.3 で公開を区切っている以上は正しい判断である。書き方も試合表の PRD の流儀（番号の章・FR-P の ID・【仮決め】・やさしい日本語）にそろっている。

## Mechanical notes

- **ID の連続**：FR-P1〜FR-P17 は抜けも重なりもない。UJ は UJ-1 のみ。成功の基準に ID はない（1つだけなので不要）。
- **仮決めの往復**：本文の【仮決め】（2.2 の3件・FR-P4・P5・P10・P11・P14・5章の7件・6章のログ・7.1・7.2 の2行・8章）は、9章の 1〜14 とすべて対応している。9章にあって本文にないものもない。FR-P15 の「要確認」は【仮決め】ではなく 10章に入っており、扱いとして正しい。
- **解決しない参照**：FR-P8「範囲と規約の下書きに合わせる」が指す文書へのリンクがない。`_bmad-output/legal/`（`terms-draft.md`・`privacy-policy-draft.md`）には人物メモの記述がまだないので、どの文書のどの決めに合わせるのかを書くか、「b7 の法律の節（第三者提供）に合わせる」に直す。
- **AD の引き方**：FR-P17 と 6章の「AD-22（退会）」は、AD-22 の見出しが「組織は suite が持ち…」なので、見出しだけ見ると外れて見える（中身の「退会の手順」は AD-22 にある）。「AD-19・AD-22 の退会の手順」と書くと迷わない。`withdrawal` の名前は、event・booking・match の `index.ts` が出しているものと揃っている。
- **6章の AD-3・AD-23**：主催した会・受付係をした会について、event の `index.ts` には今 `currentEventRole`・`getEventRole`・`listOrganizationEvents`・`listPersonalEventIds`（withdrawal 用）などがあり、「自分が主催・受付係をした会の一覧」を直接出す関数は見当たらない。10章の問いはそのまま開いているが、受付と同じく event にも小さな PR が要る見込みが高いと 6章・7.1 に書いておくとよい。
- **必要な章**：個人で使う段階に要る章（ねらい・使う人・ことば・機能・守ること・範囲・成功の基準・未決）はそろっている。
