# PRD 人物メモ：敵対的レビュー

## 結論

このまま仕様に渡すと、**検索語や名前がログと URL に残る作り**・**退会に失敗してもメモだけ消える作り**・**形の決まらない「会った場」**ができやすい。また、「Constitution の改訂は要らない」（6章）は言い切りすぎ。致命の1つと高い7つを直してから仕様に進むのがよい。

| 重さ | 数 |
|---|---|
| 致命（critical） | 1 |
| 高い（high） | 7 |
| 中くらい（medium） | 9 |
| 低い（low） | 6 |

確かめたもの：PRD・`.memlog.md`・Constitution 1.3.1・構成の決めごと（AD-2・3・5・7・9・10・15・16・19・20・22・23・25）・いまのコード（`apps/api/src/kernel/logger.ts`・`modules/reception/index.ts`・`modules/event/index.ts`・`modules/event/withdrawal.ts`・`modules/account/withdrawal.ts`・`packages/csv`）。

---

## 致命

### C-1 検索語と名前が URL に乗り、ログ・履歴・外のサイトに残る

- **場所**：FR-P10、5章「メモの本文と人の名前はログに書かない」、6章の最後（ログに書かないもの）
- **何が起きるか**：
  - 仕様を書く AI は、検索をふつうに `GET /api/v1/people?q=田中` と作る。Cloud Run は、アプリのログとは別に、要求の URL を**問い合わせの文字列ごと**要求のログ（`httpRequest.requestUrl`）に残す。アプリのログで名前を消しても、ここに名前が残る。画面の道を `/people?q=田中` にすれば、端末の履歴にも残る。
  - いまの `kernel/logger.ts` の redact は `name`・`email`・トークン類のキーだけを消す。人物メモの欄（フルネーム・LINE の名前・見た目・話したこと・次に話したいこと・タグ・アカウント・会った場の名前）はキーの名前が違うので、エラーのログに出たら素通りする。
  - PRD が「ログに書かない」と挙げているのは「本文と名前」だけ。**アカウント（X の名前・LINE ID）・タグ・会った場の名前・見た目**も、人を特定できる・中身を表す値なのに入っていない。
  - アカウントのリンクを押すと、Referer で人物メモの画面の URL が相手のサイト（X・GitHub など）に送られうる（今のブラウザの既定では源だけだが、PRD は決めていない）。
- **直し方**：
  - 5章に足す：「人物メモの値（すべての欄と検索語）は、URL の道と問い合わせの文字列に入れない。道に入れてよいのは人と会った場の ID だけ。検索は本文（POST）で送るか、画面の中で絞る」。
  - 「ログに書かないもの」は、欄の名前を全部並べる（本文と名前だけにしない）。共通の小さな PR で、構成の決めごとの「ログ」の行と `logger.ts` の redact の道を直す。
  - アカウントのリンクに `rel="noopener noreferrer"` を付ける（または人物メモの道で `Referrer-Policy: no-referrer`）。
  - 受け入れのテスト：架空の名前と本文で一連の操作をし、出たログに、その文字列が1つも入っていないことを確かめる。

## 高い

### H-1 「会った場」が、1人ごとの行なのか、持ち主の一覧なのか決まっていない

- **場所**：3章「会った場」、FR-P6・FR-P7・FR-P13
- **何が起きるか**：3章は「1人に何回でも付く」（＝人ごとの行）と読めるが、FR-P7（会った場を1回選んで続けて何人も足す）と FR-P13（会った場ごとに並べる）は、会った場が**持ち主の一覧の1件**であることを前提にしている。人ごとの行で作ると、手で書いた「〇〇勉強会」と「○○勉強会 」が別の場になり、FR-P13 で割れる。次の場合も決まっていない。
  - 同じ人に同じ会った場を2回付けたとき（重ねるか、止めるか）。
  - 持ち主が**主催者でもあり、チェックインもした**会（候補に2回出るか、1つにまとめるか）。
  - 手で書いた会った場を、ほかの人にもう一度選べるか（毎回打ち直すのか）。
- **直し方**：3章とFR-P6に、形を決めて書く。案：「会った場は持ち主ごとの一覧（kanaeru の交流会の ID〈任意〉・名前・日付）。人と会った場の組は1つだけ（同じ組は足さない）。手で書いた会った場も一覧に残り、次から選べる。kanaeru の交流会の候補は交流会の ID で1つにまとめ、『主催』『受付係』『参加』の印を並べる」。

### H-2 FR-P4（電波が切れても失わない）と 7.2（電波がないときは作らない）・夜の停止が食い違う

- **場所**：FR-P4、7.2「電波がないときに書いて後で送ること」、5章の費用（0時〜8時）
- **何が起きるか**：FR-P4 は「電波が切れる場面」で失わないと言い、7.2 は電波がないときの後送りを作らないと言う。仕様を書く AI は、後送りの仕組み（範囲の外。原則 IV）を作るか、何も作らないかのどちらかに振れる。ほかにも次が抜けている。
  - 23時59分に書き始め、0時に保存すると `503 DB_UNAVAILABLE` になる場面。
  - 下書きを端末のどこに置くか（他人の情報が端末に平文で残る。ログアウト・退会・別のアカウントでのログインで消すか）。
  - FR-P7 の続けて10〜20人を足す流れで、途中で送れずにもう一度押したときに、同じ人が2人できる（重ねない印がない）。
  - 2つの端末・2つのタブで同じ人を直したとき、続けて書き足した文が、あとの保存で黙って消える。
- **直し方**：FR-P4 を書き直す。案：「書いているものは、送るまで端末（その account の分だけ）に残す。送れなかった（電波・503）ときは残したまま『送れませんでした。もう一度送る』を出す。自動で後から送ることはしない。下書きはログアウトと退会で消す」。FR-P7 には、足す要求ごとに重ねない印（端末が作る乱数）を付けることを、FR-P3 には、版の番号で上書きを止める（食い違えば `409` で、書いた文を残したまま知らせる）ことを足す。

### H-3 退会の手順のどこで消すかを決めておらず、退会が失敗してもメモだけ消えうる

- **場所**：FR-P17、6章 AD-22
- **何が起きるか**：いまの退会は、各領域の `prepare`（account を消すトランザクションの**外**で先に流す）と `finalize`（中で流す）の2段（`modules/account/withdrawal.ts`）。6章の「`withdrawal` を出し、本人のメモをすべて消す」を読んだ AI が `prepare` で消すと、そのあと account を消す段で `409 ACCOUNT_OWNS_SHARED_RECORDS`（チェックインのある交流会を持っているなど。AD-23）になったとき、**退会はできていないのに人物メモだけが消える**。戻せない（FR-P5）。
- **直し方**：6章に「人物メモの表は、すべて持ち主の account への外部キー `ON DELETE CASCADE` で消す（人と会った場は人・持ち主から CASCADE）。`prepare` では消さない。人物メモの領域が出すのは、退会の確かめの中身（『人物メモ N 人が消えます。先に書き出せます』）だけ」と書く。テスト：退会が `409` で止まったとき、人物メモが1件も消えていないこと。

### H-4 Constitution II とぶつかる所を「改訂は要らない」で片付けている

- **場所**：6章の最後「Constitution：改訂は要らない」、5章、FR-P2
- **何が起きるか**：Constitution II は NON-NEGOTIABLE で、次の3つが人物メモと素直には合わない。`/speckit-analyze` が食い違いとして止めるか、仕様の AI が勝手に解釈する。
  1. 「電話番号は持たない」：話したこと・次に話したいこと・タグ・そのほかの URL（`tel:`）に、相手の電話番号やメールを書ける。memlog は「自由なメモに書くのは利用者の判断」としたが、PRD には書いていない。
  2. 「消してほしいと頼まれたら、その人のデータを消す」：メモの**相手**（kanaeru の利用者でもない第三者）から頼まれたら、どう果たすのか。運営者は中身を読まない約束（5章）なので、その人のメモを探せない。
  3. 「集めるのは PRD で決めたものだけ」：自由な文章は何でも入る。
- **直し方**：持ち主に、次のどちらかを決めてもらう。(a) Constitution を明確にする改訂（PATCH か MINOR）：「利用者が自分だけのメモに書いたものは、kanaeru が集めるものに数えない。運営者は読まず、第三者から消してほしいと頼まれたら、持ち主に伝える〈運営者は中身を探さない〉」。(b) 改訂しないなら、PRD に「電話番号・メールの形を見つけたら注意を出す」「第三者からの削除の頼みの受け方」を要件として足す。どちらにしても、6章の「改訂は要らない」は「要確認」に直し、7.3 の専門家の確かめに 2 を足す。

### H-5 アカウントと「そのほかの URL」に、どんな値を入れてよいか決まっていない

- **場所**：FR-P2「そのほかの URL」、FR-P15、3章「アカウント」
- **何が起きるか**：自由な URL をそのまま `href` に出すと、`javascript:`・`data:` で画面の中で動くもの（XSS）が入り、`tel:`・`mailto:` で「電話番号とメールの欄は作らない」（持ち主が決めた）を素通りする。X・GitHub などを「名前（@handle）」で持つのか「URL」で持つのかも決まっていないので、URL を貼った・名前を打ったで表示とリンクが壊れる。
- **直し方**：FR-P2 に書く。「X・connpass・GitHub・LinkedIn・LINE ID は**名前だけ**を持ち、リンクは決まった形（`https://x.com/{名前}` など）から作る。そのほかの URL は `https:` だけを受ける（zod で止める）。リンクは外のブラウザで開く（LINE の中では `liff.openWindow` の external）」。

### H-6 公開のリポジトリ・ステージング・CI・開発の AI に、本物のメモが入る道を止めていない

- **場所**：5章（書いていない）
- **何が起きるか**：リポジトリは公開（memlog「コミュニティの名前は公開リポジトリに書かない」）。持ち主は本物の知り合いのメモを本番に書く。次の道で、第三者の名前と中身が外に出る。
  - PR に貼る画面のスクリーンショット、通しのテストの記録（trace・スクリーンショット）、テストの固定のデータに、本物の名前を使う。
  - ステージングで「試しに」本物のメモを書く（ステージングは本番と同じ Cloud SQL の台。AD-8）。
  - 調べものの途中で、開発の AI（Claude Code など）に本番の DB やログを読ませる。これは「人物メモを外の AI に渡さない」（Constitution II・AD-20）に当たる。
- **直し方**：5章に足す。「本物のメモは本番にだけ書く。手元・テスト・ステージング・PR のスクリーンショットは架空の人だけ。調べもので本番の DB を読むときも `people_` の表の中身は読まない（数だけ）。開発の AI に人物メモの表とそのログを読ませない」。CLAUDE.md の「本物の利用者のデータをコミットしない」より踏み込んで、**第三者**のデータであることを書く。

### H-7 「主催した会・受付係をした会」の範囲が広すぎ、読み方の作業も1つ抜けている

- **場所**：3章「kanaeru の交流会」、FR-P6、6章 AD-3・AD-23、7.1、10章
- **何が起きるか**：
  - AD-5 の「主催者」は、交流会の持ち主に加えて、**交流会を入れた組織の管理者・編集者**も含む。そのまま使うと、組織の編集者は、行ってもいない組織のすべての交流会が候補に並ぶ。
  - いまの event の `index.ts` が出すのは、交流会ごとの役割（`getEventRole`）・組織の交流会（`listOrganizationEvents`）・退会のための `listPersonalEventIds`（組織に入れていないものだけ）で、「自分が持ち主か受付係の交流会の一覧」はない。event の領域にも小さな PR が要る見込みだが、7.1 は reception の PR しか挙げていない（並行開発の決まり：ほかの領域を直す前にユーザーに伝える）。
  - `uses: ["reception"]` にすると、受付アプリの領域（reception・booking）の入口がすべて読めるようになる。reception には参加者の名前を返す `listEventAttendees`、booking には申込みの名簿がある。「チェックインしたか」を確かめるために、AI がこれらを呼んで名前を人物メモの領域に読み込む作りをしうる（FR-P8 の考えに反する。lint では止まらない）。
- **直し方**：3章の定義を「持ち主の交流会・自分が受付係の交流会・自分が LINE でチェックインした交流会」に絞る（組織の役割は使わない）と持ち主に確かめる。7.1 に「event の小さな PR（自分が持ち主か受付係の交流会の一覧）」を足す。6章に「人物メモの領域は、交流会の ID・名前・日時だけを返す関数を呼ぶ。参加者の名前・名簿を返す関数（`listEventAttendees`・booking の名簿）は呼ばない」と書き、仕様の点検の項目にする。

## 中くらい

### M-1 「最近書いた・会った順」が、どの時刻で並べるのか決まらない

- **場所**：FR-P11
- **何が起きるか**：「書いた」は保存の時刻（時刻つき）、「会った」は会った場の日付（日付だけ・過去の日付もありうる）。両方あるとき、どちらを使うかで並びが変わる。例：3か月前の会を今日まとめて足した人は、「書いた」なら先頭、「会った」なら下のほう。タグを1つ付けた・誤字を直しただけで先頭に上がるのかも決まっていない。同じ時刻のときの並びもない。
- **直し方**：1つのキーに決めて書く。案：「最後に手を入れた時刻（本文・アカウント・タグ・会った場のどれかを変えた時刻）の新しい順。同じなら名前の順」。会った場の日付は一覧に出すだけにする。受け入れの例を2つ以上書く（過去の会をあとから足した人・誤字だけ直した人）。

### M-2 同じ名前の人を足したときの扱いがない

- **場所**：FR-P1・FR-P7
- **何が起きるか**：要るのはフルネームだけで、続けて10〜20人を足す。前に足した「田中太郎」を見落として新しく足すと、同じ人のメモが2つに割れる。本当に同名の別人もいる。まとめる機能もない。
- **直し方**：「足すとき、名前（前後と間の空白を除き NFKC でそろえる）が同じ人がいれば、その人の見た目の特徴と会った場を出して『この人ですか』を聞く。別人として足すこともできる。この版ではまとめる機能は作らない」と書く（そろえ方は reception の約束と同じ考えだが、領域の中に写す。AD-18）。

### M-3 kanaeru の交流会の名前と日付の写し、消えたときの外部キーが曖昧

- **場所**：FR-P9、6章 AD-7・AD-19
- **何が起きるか**：
  - 選んだときに名前と日付を**写す**のか、いつも交流会から読むのかが書いていない。写すなら、主催者があとで名前や日時を直したときにどちらを出すか。交流会の日時から「日本時間の日付」を出す関数（`packages/contracts/src/core`）を使うことも書いていない。
  - 交流会は持ち主の退会で消える（`event/withdrawal.ts` が account を消すトランザクションの中で消す）。人物メモの外部キーを既定の `RESTRICT` にすると、**ほかの人の退会**が `409` で止まり、しかも「誰かがこの会の人物メモを持っている」ことが相手に分かる。
  - 見られなくなった交流会（受付係を外された）を、人物メモから開こうとしたときの扱い。
- **直し方**：「選んだときに名前と日本時間の日付を写し、以後は写しだけを出す（交流会を直しても変えない）。交流会を指す外部キーは `ON DELETE SET NULL`。人物メモから交流会の画面には飛ばない」と書く。テスト：交流会の持ち主の退会が、人物メモがあっても通ること。

### M-4 CSV の書き出しの中身と守りが決まっていない

- **場所**：FR-P16
- **何が起きるか**：
  - 式として読まれない守り（`=`・`+`・`-`・`@` などで始まる値）は `packages/csv` にあるが、PRD は使うと書いていない。話したこと・見た目は自由な文なので、`=HYPERLINK(...)` が入りうる。
  - 1人に何個もあるアカウント・タグ・会った場を、列にどう並べるか（1行1人で区切るのか、1行1組か）が決まっていない。
  - 書き出したファイルは他人の情報の束で、kanaeru の守りの外に出る。画面で注意しない。ファイル名に名前を入れるかも決まっていない。
  - LINE の中のブラウザ（とくに iPhone）では、ファイルのダウンロードがうまく動かないことがある。どこで書き出す前提か書いていない。
  - 取り込みはないので、書き出しは「控え」にならない（戻せない）。
- **直し方**：FR-P16 に、`packages/csv` と `apps/web/src/lib/download.ts` を使う・列の形・ファイル名（日付だけ）・押す前の注意（「相手の情報が入っています。人に渡さない・AI に貼らない」）・PC のブラウザで使う前提（または確かめる）・取り込みはこの版で作らない、を書く。

### M-5 アプリの key「people」が AD-15 の「key は英小文字の単数」に合わない

- **場所**：6章 AD-15、`.memlog.md`「領域ID は people」
- **何が起きるか**：AD-15 と構成の決めごとの「名前」の行は、key・領域のフォルダを英語の単数にすると決めている。`people` は `person` の複数形。持ち主が決めた名前でも、決まりと食い違ったまま仕様に入ると、点検でもめる。
- **直し方**：持ち主に「`person` にするか、構成の決めごとに例外を書くか」を聞く。例外にするなら、共通の小さな PR で AD-15 に1行足してから仕様に進む。

### M-6 成功の基準が測れず、最初の1か月では届きにくい

- **場所**：8章
- **何が起きるか**：
  - 月に一度の振り返りで「言えた回数」を思い出して数えるので、数えもれと思いこみが大きい。使う前の回数（くらべる元）もない。
  - 最初の月はメモが空から始まり、「言えた」には**同じ人ともう一度会う**ことが要る。受付アプリの会は月に一度。1か月目に3回は、アプリのよしあしと関係なく届かないことがある。逆に、アプリを開かずに言えた回も数えてしまう。
  - 逆の目印の「1人を足すのに2分」は、どう測るか書いていない。
- **直し方**：「言えたら、その日のうちに数える（紙・メモなど、アプリの外でよい）」「アプリでメモを読み返したあとに言えた回だけ数える」「期間は最初の2か月」と書く。中身を読まずに DB から取れる目印（週に足した人数・次に話したいことが空でない人の割合）を足す。2分は「10人を続けて足す手の試し」で測ると書く。

### M-7 夜の停止の判断は「書く」場面だけで決めていて、場面Bの「読む」を見ていない

- **場所**：5章の費用、UJ-1 の4（場面B）、memlog「夜0時を過ぎて書くことはあまりない」
- **何が起きるか**：LINE の連絡は夜遅くに来やすい。場面B（連絡が来て、メモを見てから返す）が0時〜8時は使えない。持ち主の判断の理由は「書く」ことだけだった。また、止まっているときの文言を「今は使えません」と独自に決めているが、AD-10 は土台の1か所で「夜間（0時〜8時）は止まっています」と出す決まり。
- **直し方**：持ち主に「読む場面が夜に使えなくてよいか」をもう一度確かめる（memlog に残す）。文言は AD-10 の共通のものを使うと書き、9章の仮決め10を消す。

### M-8 要配慮の注意が「話したこと」だけに読め、見た目とタグが抜けている

- **場所**：5章の注意の仮決め、FR-P2・FR-P11
- **何が起きるか**：見た目の特徴（体の特徴・障害）やタグ（「要注意」「病気」など）にも、相手が知られたくないことが入る。体の障害は要配慮個人情報に当たる。FR-P11 は一覧の名前の横に見た目を出すので、帰りの電車の中で、相手の見た目のメモが一覧ごと人に見える。
- **直し方**：注意を、見た目・タグ・話したこと・次に話したいことの欄すべてに出すと書く。FR-P11 の「一覧に見た目を出す」は、持ち主に確かめる仮決めとして残し、出すなら1行で切る。

### M-9 バックアップに消したメモが残ることを、どこにも書いていない

- **場所**：FR-P5、FR-P17、5章、7.3
- **何が起きるか**：Cloud SQL の自動のバックアップは7日分残る（AD-9）。人を消しても退会しても、最大7日はバックアップに残る。DB をまるごと戻せば、消した人物メモも戻る。「消したら戻せない」（利用者には戻せない）と「運営者は戻せる」が食い違って見える。
- **直し方**：7.3 のプライバシーポリシーの節に「消したものはバックアップに最大7日残り、そのあと消える」を足す。運用の決まりとして「人物メモを読むため・1人のメモを戻すためにバックアップを戻さない」を5章に書く。

## 低い

### L-1 AD-3 の「表を作る順」に people を足していない

- **場所**：6章
- **直し方**：AD-3 の順（account → event → reception → survey → booking → match）の最後に people を足すことを、6章に1行で書く（共通の文書なので、共通の小さな PR で）。

### L-2 「LINE の名前」を account の表示名から埋めない、と明記していない

- **場所**：3章「人」、FR-P2、6章 AD-2
- **何が起きるか**：相手が kanaeru を使っていると、AI が「便利だから」と account の表示名やチェックインの名前で候補を出したり埋めたりしうる。AD-2（表示名を自分の表に写さない）と FR-P8 に反する。
- **直し方**：FR-P2 に「LINE の名前は持ち主が打つ。account・チェックインの名前から埋めない・照らし合わせない」と書く。

### L-3 かなの違いを吸収しても、漢字の名前は読みで探せない

- **場所**：FR-P10 の仮決め
- **何が起きるか**：名前はほぼ漢字なので、「たなか」で「田中」は当たらない。読みの欄がないため、かな・カナをそろえる仮決めはあまり効かない。また、検索の文字に `%`・`_` が入ったときの扱いも書いていない。
- **直し方**：「読み（任意）」の欄を足すかを持ち主に聞く（足さないなら、その旨を書く）。検索は、そろえた文字の部分一致で、`%`・`_` は文字として扱うと書く。

### L-4 運営者の画面に「中身を出さない」の範囲が曖昧

- **場所**：5章、9章の仮決め7
- **直し方**：「運営者の画面に出してよいのは、アプリ全体の人数の合計まで。account ごとの人数・名前・中身は出さない」と書く。

### L-5 外の AI に渡さないことを、共通の仕組みの側でも守る書き方がない

- **場所**：5章、6章 AD-20・AD-21
- **何が起きるか**：人物メモの領域は MCP のツールを出さないが、あとで suite などが作る「自分のデータをまとめて返す」ツールや、改善点を送る画面が、画面の中身を一緒に送ると、人物メモが外に出る。
- **直し方**：6章に「人物メモの `index.ts` から `mcpTools` を出さない。ほかの領域の AI・MCP・改善点の送信にも、人物メモの中身を含めない」と書く。

### L-6 端末をなくしたときの備えに触れていない

- **場所**：5章
- **何が起きるか**：セッションは30日（AD-4）。スマホをなくすと、他人の情報の束がそのまま見られる。
- **直し方**：この版で作らないなら 7.2 にそう書き、一般に公開する前（7.3）に「ほかの端末のログアウト」か「開くときの確かめ」を考える、と書く。
