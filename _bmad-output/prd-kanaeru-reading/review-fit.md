## 重大

### F1 公開の本棚の「変わらない URL」が、まだ決まっていないドメインに結びつく

- **PRD のどこ**：FR-R33（変わらない URL・アソシエイトに自分のサイトとして登録）・6章「公開の本棚の道…最初に形を決める」・10章「公開の本棚の URL の形」。
- **何が問題か**：PRD は道（`/r/<名前>/`）の形だけを「最初に決める」としているが、URL は**源（ドメイン）＋道**で、利用者が Amazon・楽天に登録するのは源を含む URL。構成の Deferred「独自のドメイン」はまだ取っておらず、最初は Cloud Run の既定の URL。さらに 2026-11-26 にサービス名を替えて資源を作り直しており（coding.md 2章）、ドメインの名前も決まっていない。既定の URL のまま公開すると、あとでドメインを替えたときに、全利用者のアソシエイトの登録・ブログや SNS に貼ったリンク・検索の評価がまとめて切れる。AD-14 の QR はミニアプリの URL なので源を替えても困らないが、公開の本棚はふつうのブラウザで開く URL なので、その逃げ道がない。
- **直し方**：
  - PRD 7.1 の段階2の前提に「独自のドメインを取り、公開の本棚をそのドメインで出す」を足す。10章の「段階2の前に確かめる」に、ドメインの名前（サービス名とは独立に長く使える名前か）を足す。
  - 構成の Deferred「独自のドメイン」に「公開の本棚（読書記録の段階2）の前に取る」を足す（今は「予約のメールを本番で送る前」「MCP を作る前」だけ）。前に Cloudflare を置く形（バックログ C1）と一緒に決めると、F2・F3 にも効く。
- **新しい AD の候補**：AD-32「公開の本棚の URL」（源は独自のドメインに固定し、Cloud Run の既定の URL では出さない。道の形・名前の決まり〈F5〉・道の頭〈F8〉もここに置く）。

## 高

### F2 夜の停止（0時〜8時）で公開のページが毎日8時間止まる

- **PRD のどこ**：5章「夜の停止（AD-10）…画面はほかのアプリと同じ『夜間は止まっています』」。公開のページについては書いていない。4.10 #10（人を集める入口）・FR-R34（検索に出す）。
- **何が問題か**：公開のページは、ブログ・SNS・検索から来る**ログインしていない他人**が開く。夜に開いた人には本の情報もリンクも出ず、利用者・持ち主の紹介料（4.10 の主な稼ぎ方）が1日の3分の1で失われる。Amazon アソシエイトの審査で、登録した URL を夜に見られると中身のないページに見える。今の作りでは画面（`index.html`）は 200 で返り、中身だけが「夜間は止まっています」になるので、検索のクローラーがその文を本文として拾うおそれがある（F3）。AD-10 はこの場面を想定していない（Cloud Run は動いているが、`requireApp` の判定〈`isAppVisible`〉から DB を読むので必ず 503）。
- **直し方**：PRD 5章に、公開のページの夜の扱いを足す。選び方は次のどれか（構成で決める）。
  1. 前に Cloudflare を置き（バックログ C1）、公開のページの HTML と答えを共有のキャッシュに持たせる（ログインなし・本人に依らない中身なので持たせてよい）。夜は覚えたものを出す。公開をやめた（FR-R35）ときは、キャッシュを消す（消す API を呼ぶ）か、持つ時間を短くする。core-020 の `stale-if-error` の形を広げる。
  2. 公開を選んだときに、ページの中身を DB の外（Cloud Storage など）に書き出し、Cloud Run は夜もそこから返す。費用は小さいが、資源が増える（AD-8・AD-9 を直す）。
  3. 夜は止まることを受け入れ、HTML を `503`＋`Retry-After` で返す（検索には一時の止まりと伝わる）。紹介料の取りこぼしは受け入れる。
- **新しい AD の候補**：AD-32（公開の本棚）の中に「夜の停止の間の出し方」を置き、AD-10 に例外の1行を足す。

### F3 公開のページを画面（SPA）の `index.html` で返すと、ページごとの題・OGP・正しい状態コードを返せない

- **PRD のどこ**：FR-R34（検索に出してよい・人を集める入口）・UJ-7（URL をブログや SNS に貼る）・6章（新しい決めごとの候補に描き方がない）。
- **何が問題か**：今は `/api` と `/.well-known` のほかはすべて同じ `index.html` を返し（AD-8・`platform/web`）、題や説明は画面の JavaScript が描く。SNS（X・LINE・Facebook）のリンクの見本（OGP）は JavaScript を動かさないので、どのページも同じ題・同じ画像になる。検索も、ない名前・公開をやめたページ・夜の止まりを 200 の「中身のないページ」として受け取る（soft 404）。「人を集める入口」と「URL を貼ってもらう」に、ページごとの題・説明・OGP・`canonical`・正しい状態コード（404・410・503）が要る。今の構成には、ログインなしでふつうのブラウザに出し、しかも検索に出すページがない（AD-26 は `noindex`）。
- **直し方**：PRD 4.9 に「公開のページは、ページごとの題・説明・OGP・状態コードを返す」を非機能として足す。構成で、公開のページの道（F8）だけ、`platform/web` が HTML を返す前に題・説明・OGP を差しこみ、ない・止めたページは 404・410 で返す形を決める（技術の道具は `platform/web`、中身は reading の `index.ts` が出す。AD-18 のとおり業務を共通に置かない）。Constitution の技術スタック（Vite＋React の画面）の中で済む形にし、別の描き方（SSR の枠組み）は入れない。
- **新しい AD の候補**：AD-32 に「公開のページの HTML の頭（題・説明・OGP・canonical）と状態コードは、領域が出す関数を組み立てが集めて `platform/web` で差しこむ」を置く（`publicReadPaths`〈core-016〉と同じ「領域が出し組み立てが集める」形）。`platform/web` を直すので、小さな共通の PR で先に入れる。

### F4 取りこみの上限（5,000件・20MB）が API の本文の上限（100KB）と合わない

- **PRD のどこ**：5章「1回の取りこみは、マーカー5,000件・ファイル20MB まで【仮決め】」・FR-R5（Kindle の書き出しのファイル・Web のノートブックの貼り付け）・FR-R6（PDF は端末の中で読む）。
- **何が問題か**：API は `/api/v1/*` のすべてに本文の上限 100KB をかけている（`apps/api/src/app.ts` の `MAX_BODY_BYTES = 100 * 1024`）。20MB のファイルは送れず、端末の中で読んでも、5,000件のマーカー（1件 数百字）は1回では送れない。FR-R6 は端末で読むと決めているが、Kindle の書き出しのファイル（HTML）と貼り付けをどこで読むかは書いていない。
- **直し方**：PRD FR-R5・FR-R7 に「Kindle の書き出しと貼り付けも端末の中で読み、読み取ったマーカーとコメントだけを送る（ファイルはサーバーに送らない）」を足す（FR-R6 とそろう・著作権の面でも本のファイルを持たない5章とそろう・本文の上限を変えずに済む）。5章の上限を「ファイルは端末で読める大きさ・送るのは 100KB ごとに分けて送る（何回目かを付け、途中で止まったら続きから）」に書き直すか、取りこみの道だけ上限を上げる（本文の上限の例外は `app.ts` の共通の PR が要る）。FR-R9（確かめてから入れる）は、分けて送る前の端末の画面で行う。
- **新しい AD の候補**：なし（PRD と仕様で足りる）。上限を上げるなら、AD-8 か Consistency Conventions に「本文の上限の例外は道ごとに組み立てで持つ」を足す。

### F5 公開の名前の決まりがない

- **PRD のどこ**：FR-R33（利用者が決めた名前で、変わらない URL）・FR-R36（開示の文は、利用者の名前で）・FR-R35（公開をやめられる）・5章（退会したら消す）。
- **何が問題か**：利用者が決めた名前を URL に使うのは、このリポジトリで初めて（AD-26・AD-30 は推測できない札）。次が決まっていない。
  - 使えない名前（`admin`・`kanaeru`・`amazon`・運営に見える名前・ほかの利用者に似せた名前）。
  - 名前を変えられるか（変えると Amazon の登録と貼ったリンクが切れる。変えた前の名前を転送するか）。
  - 退会・名前の変更のあと、**同じ名前をほかの人が取れるか**。取れると、前の人のブログのリンクと Amazon の登録が新しい人のページに向く（なりすまし・他人の紹介料の取り込み）。取れないようにするには、名前（かその SHA-256）を退会のあとも持つことになり、原則 II・AD-19（消してほしいと頼まれたら消す）との兼ね合いを決める要がある。
  - 開示の文と公開のページに出す「利用者の名前」が何か。account の LINE の表示名を出すと、LINE の名前がログインなしで検索に載る。AD-2 は LINE の表示名をほかの領域に写さないとしている。
- **直し方**：PRD 4.9 に、公開の名前を **LINE の表示名と別に本人が入れる**こと・使える文字と長さ・使えない名前・変える形・退会のあとの扱いを足す（【仮決め】でよい）。開示の文に出す名前も、この公開の名前にする。
- **新しい AD の候補**：AD-32 に「公開の名前（一意・予約語・変えたときの転送・退会のあと再利用させない期間と、持つものは SHA-256 だけ）」を置く。

### F6 FR-R35「運営者がページを止める」が AD-19 に反する

- **PRD のどこ**：FR-R35「持ち主（運営者）は、規約や法に反するページを止められる」。
- **何が問題か**：AD-19 は「運営者だけに許すのは AD-16 の台帳の操作だけで、新しいアプリは `isOrganizer` を使わない」と決めている。運営者がほかの利用者の記録（公開のページ）を止める窓口は、この決まりの外になる。ログインなしで誰でも見られる利用者の文章（感想）を出すのはこのリポジトリで初めてで、止める手段は要る。
- **直し方**：AD-19 に例外を足す（「運営者は、ログインなしで公開されている記録だけを、止める〈消さない〉ことができる。中身を読む・直すことはしない」など）。止めたことを本人に伝える形（画面に出す。知らせは送らない〈FR-R26〉）と、止めた記録を残すかを PRD 4.9 に足す。止める窓口は reading の領域に置き、運営者かは account の `isOrganizer` で読む（coding.md 6-3 の「運営者か」の読み方のまま）。
- **新しい AD の候補**：AD-19 を直す（運営者の止める権限の例外）。Constitution の改訂（F13）にも、止める者と止める理由を書く。

### F7 6章「段階1では共通の PR は要らない見込み」が外れる

- **PRD のどこ**：6章「共通の PR：段階1では要らない見込み。Google カレンダーのリンクは、予約の領域の形を読書の領域に写す（AD-18）」。
- **何が問題か**：段階1でも、次の共通のファイルを直す見込みが高い。並行開発の決まり 3-3 では、作る前にユーザーに伝え、人物メモのセッションには同じファイルを触らないよう伝えてもらう必要がある。
  - **画面の CSP**（`apps/api/src/platform/web/web.ts` の `WEB_CSP_DIRECTIVES`）：書影を書誌の API の画像の源から出すなら `imgSrc` に足す（F10）。PDF を読む部品（pdf.js など）の働き手と WebAssembly を使うなら `workerSrc`・`scriptSrc`（`'wasm-unsafe-eval'`）を確かめる（F11）。
  - **カレンダーの道具**：`googleCalendarUrl`・`calendarStamp` は `packages/contracts/src/booking/calendar.ts` にあり、reading は `uses: []` なので booking の contracts を読めない（AD-15）。AD-18 は「2つ目の領域が要り、形がもう固まったとき」に共通へ移すと決めている。`calendarStamp` と URL の組み立ては業務を知らない道具で、形は固まっている（交流会の既定の長さ `EVENT_DEFAULT_DURATION_MINUTES` だけは booking の業務）。写すより、先に `packages/contracts/src/core` か `packages/` の小さな包みへ移す共通の PR が AD-18 に沿う。
  - **本文の上限**：F4 で上限を上げる形を選ぶなら `app.ts`。
  - 段階2では、さらに `apps/web/src/lib/liff.ts` の `PATH_PREFIXES_WITHOUT_LIFF`（F9）と `platform/web`（F3）を直す。
- **直し方**：6章の「共通の PR」を、段階ごとの一覧（CSP・カレンダーの道具〈移すか写すかの判断〉・本文の上限〈選んだ場合〉／段階2：LIFF を始めない道・公開のページの HTML の頭）に書き直し、「作る前にユーザーに伝え、人物メモのセッションと順番を決める」を足す。

## 中

### F8 `/r/<名前>/` は AD-15 の道の決まりの外

- **PRD のどこ**：FR-R33「例：`/r/<名前>/`。形は構成で決める」。
- **何が問題か**：AD-15 は「新しいアプリの画面は `/<key>/…` の下」とし、例外は受付アプリの今の道と AD-14 の参加者の道だけ。`/r/` は `reading` の下ではなく、`r` は予約語にもないので、将来ほかのアプリと道の頭がぶつかりうる（AD-15 が止めたい事故）。
- **直し方**：構成で次のどちらかに決め、PRD FR-R33 の例を直す。(a) AD-15 に従い `/reading/<何か>/<名前>`（長いが決まりの中）。(b) 短い頭（`/r/` など）を AD-15 の例外として足し、予約語の一覧（テスト）に足す。どちらでも、`-` を含む参加者の道（AD-14）とぶつからないことを確かめる。F1 のとおり源とあわせて決める。

### F9 LIFF・ミニアプリの URL・ログインの扱い

- **PRD のどこ**：FR-R34（ふつうのブラウザ）・FR-R22（予定の説明に UJ-4 の画面へのリンク）・2.3（Kindle の書き出しのメール・GoodNotes の PDF を取りこむ端末が書かれていない）。
- **何が問題か**：
  - 組み立ては、`PATH_PREFIXES_WITHOUT_LIFF`（今は `/match` だけ）にない道ではいつも `liff.init()` を呼ぶ（AD-4）。公開のページを LIFF の中で開かせると、ログインのない他人に LINE の画面が出るうえ、アプリ（LINE）の中でアソシエイトのリンクを出す形になり、Amazon の「承認のないアプリ・WebView」の制約（補足 2章）に当たりうる。
  - 予定のリンクを画面の源の URL にすると、スマホではふつうのブラウザが開き、LINE ログインをし直すことになる。ミニアプリの URL（`miniAppPermalink`）にすると LINE の中で開く。どちらにするかが書かれていない。
  - Kindle の書き出し（メールの添付の HTML）と GoodNotes の PDF は、PC か iPad で扱う場面が多い。PC のブラウザでのミニアプリの LINE ログインは構成の Open Questions 3 で未確かめ。LINE の中のブラウザで PDF のファイルを選べるかも確かめていない。
- **直し方**：PRD 4.9 に「公開のページは LIFF を始めない道に置き、共有する URL はミニアプリの URL にしない」（AD-4 の例外・AD-14 の例外。AD-26 と同じ扱い）を足す。FR-R22 に「予定のリンクはミニアプリの URL（`miniAppPermalink`）」を足す（AD-14 の関数を使う）。2.3 か 10章に、取りこみに使う端末と、Open Questions 3・LINE の中でのファイル選びの確かめを足す。

### F10 外の書誌の API を呼ぶ形が決まっていない

- **PRD のどこ**：FR-R1（openBD・Google Books・国立国会図書館サーチのどれか【仮決め】）・FR-R32（書影）・6章「書誌の API」・10章（利用条件）。
- **何が問題か**：外のサービスは、領域から `deps.fetch` で呼ぶ決まり（coding.md 6-6。テストは差しかえ）。Cloud Run の出口は Direct VPC egress で「VPC に出るのは内部の宛先だけ」（AD-8）なので、外への呼び出しは NAT なしでそのまま出られ、通信の費用もごく小さい（原則 V に収まる）。決めていないのは次。
  - 画面から直接呼ぶか、API を通すか（画面から呼ぶなら CSP の `connectSrc` を直す共通の PR。API を通すなら、外の API の答えの待ち時間・失敗の扱い・回数の上限〈1つの IP から呼ぶので、鍵のない Google Books は上限に当たりやすい〉）。
  - 鍵が要る API（Google Books の API キー）を使うなら、Secret Manager に置き、`DomainConfig` に入れず道具として渡す（coding.md 6-6・AD-9）。
  - 書影を画面に出すなら、画像の源を CSP の `imgSrc` に足す（F7）。書影を kanaeru に写して持つかは利用条件しだい。
  - 書誌を DB にどこまで持つか（選んだ本の書名・著者・ISBN・書影の URL だけか）。
  - Amazon のリンクには ASIN が要る。紙の本は ISBN-10 で足りるが、Kindle 版は ASIN が別（B0…）。Amazon の商品の情報の API（PA-API）は売上の実績が条件で、すぐには使えない。
- **直し方**：PRD FR-R1 に「API を通して呼ぶ・持つのは選んだ本の書誌だけ」【仮決め】と、Kindle 版のリンクの作り方（ISBN のリンクで紙の本に向けるか）を足す。10章の利用条件の確かめに、書影の表示・保存・商用・帰属の表示を足す。
- **新しい AD の候補**：AD-33「外の書誌の API は reading が `deps.fetch` で呼び、持つのは選んだ本の書誌だけ。書影は利用条件で許されるときだけ源から出す（写さない）」。

### F11 端末の中で PDF を読む部品

- **PRD のどこ**：FR-R6・6章「PDF を端末の中で読む部品：画面の領域に置く」。
- **何が問題か**：画面の領域（`apps/web/src/features/reading/`）に置くのは AD-18 に合う（使う領域が1つのうちは写さず、領域の中でよい）。ただし、
  - 画面の CSP は `eval`・`new Function` を止め、E2E が CSP の違反を落とす（coding.md 6-3）。pdf.js は `isEvalSupported: false` で使い、働き手（worker）は自分の源のファイルとして組み立てる。画像の復号に WebAssembly を使う版では `'wasm-unsafe-eval'` が要る（マーカーと文だけを読むなら要らない形を選ぶ）。
  - 部品は大きいので、取りこみの画面を開いたときだけ読む（`lazyRouteComponent`）。
  - 20MB の PDF をスマホの LINE の中で読むと、メモリーが足りないことがある。
- **直し方**：PRD FR-R6 に「PDF を読む部品は取りこみの画面を開いたときだけ読み、CSP を緩めない形を選ぶ」を足し、10章の GoodNotes の確かめに「使う部品で、マーカーの位置と下の文・テキストボックスが取れるか」を足す。CSP を直すなら F7 の共通の PR に入れる。

### F12 原則 II：5章の「持つもの」の一覧が足りない

- **PRD のどこ**：5章「持つものは、この PRD で決めたものだけ：本・分かりたいこと・マーカー・コメント・調べて分かったこと・説明の材料・やってみることと結果・自分の ID・公開の本棚の名前」。
- **何が問題か**：Constitution II は「集めるのは、各アプリの仕様（PRD）で決めたものだけ」。PRD の FR が持つのに一覧にないものがある。
  - 書誌（書名・著者・ISBN・書影の URL）・読む場所と状態（FR-R3）・貼った目次（FR-R14）
  - やってみることの予定日・「やった・まだ・やめた」の時刻（FR-R22・FR-R25）
  - 思い出す画面で「まだ見せていない」を決めるための、見せた記録（FR-R24）
  - 調べる先の選び（FR-R18）・ブログの下書き（FR-R28）
  - 公開の**感想**と、出す・出さない・選んだ引用（FR-R31・FR-R32）・「URL をアソシエイトに登録した」の確かめの印（FR-R36）・開示に出す名前（F5）
  - 段階2の数（8章。名前を含まない）
- **直し方**：5章の一覧を FR と1対1になるよう書き足す。あわせて `apps.list.ts` の `accountData`（アカウントに結びつくデータの説明）に入れる文を6章に書く。ログには、マーカー・コメント・感想の本文を出さない（coding.md 6-3 の「要求と応答の本文を出さない」のまま）ことを5章に1行足す。

### F13 Constitution の改訂の中身が書き下されていない

- **PRD のどこ**：6章「Constitution の改訂…別の例外を足す必要がある【段階2の前】」。
- **何が問題か**：要ることは正しく挙げているが、改訂の中身がない。今の例外（技術スタック制約の「認証」）は、出すもの・URL の形・期限・検索に出さないことまで書き下してある。公開の本棚は、それと逆の条件（推測できる名前・期限なし・検索に出す）で、しかも**利用者が書いた文章をログインなしで出す**のはこのリポジトリで初めて。
- **直し方**：6章に改訂の叩き台を書く。中身の候補：ふつうのブラウザ・ログインなしで開ける／出すのは本人が出すと選んだ本ごとの書誌・感想・出典つきの短い引用・本のリンクだけ（マーカーの一覧・説明の材料・`?` の印・LINE の名前・account は出さない）／既定は出さない／本人はいつでもやめられる・運営者は規約や法に反するものを止められる（F6）／独自のドメインの上の変わらない URL（F1）／回数の制限をかける。原則の拡張なので版は MINOR（1.4.0）で、`/speckit-constitution` で Sync Impact Report を残す（Governance）。原則 II の文（「勉強会やアプリにするときに名前を出さない」は困りごとのこと）と食い違わないことも確かめる。

### F14 構成の Deferred「暮らしのアプリを出すときに AD-10 を見直す」に当たる

- **PRD のどこ**：5章「夜の停止（AD-10）：0時〜8時は DB が止まる」・10章（夜の停止の見直しがない）。
- **何が問題か**：構成の Deferred に「0時〜8時は DB が止まるので、MCP と暮らしのアプリも使えない。暮らしのアプリか MCP を出すときに AD-10 を見直す」とある。読書記録は暮らしのアプリで、寝る前に読んで、そのあと取りこむ・思い出す場面がありうる。人物メモの PRD は「一般に公開する前に AD-10 を見直す」と書いている。
- **直し方**：PRD 5章に「段階1（持ち主だけ）は夜の停止を受け入れる」を、10章の「段階2の前に確かめる」に「夜の停止の見直し（AD-10 の Deferred）」を足す。8章の逆の目印に「夜に使おうとして止まっていた回」を足すと、見直しの材料になる。F2（公開のページ）とは別に、利用者自身の画面の話として書く。

### F15 人物メモと並行するときのぶつかり

- **PRD のどこ**：6章「DB の変更（AD-17）：人物メモ（B7）のセッションと並行するので、DB の変更のある PR は同時に1本だけ。表を作る PR を先に小さく出す」。
- **何が問題か**：DB の PR の数え方は正しい。ほかに次がぶつかる。
  - 構成の文書（AD-3 の表の持ち主の表・表を作る PR の並び「account → … → match」・Capability map・AD-15 の予約語）は `merge=union` ではない。人物メモの PRD は、並びの match の後ろに `person` を足すと書いている。読書記録も `reading` を足すので、2つのセッションが同じ行を直す。
  - Constitution（技術スタック制約の AD の一覧の文・例外）も `merge=union` ではない。人物メモは公開の前に見直すと書き、読書記録は段階2の前に改訂する。
  - `docs/README.md` 2章の領域の地図の行（coding.md 6-6 の 7）も `merge=union` ではない。
  - `apps.list.ts`・`modules.list.ts`・`features.list.ts`・`docs/decisions.md` は `merge=union` なので1行ずつならぶつからない（`packages/contracts/package.json` は `./*` で出すので直さなくてよい）。
  - 人物メモは reception と event の `index.ts` に関数を足す PR を出す。読書記録の段階1は reception・event を読まないので、ここはぶつからない。
- **直し方**：6章に「構成の文書と Constitution の直しは、人物メモの分と1本の共通の PR にまとめるか、先に入った方のあとに直す。どちらにするかはユーザーが決める」を足す。表を作る並びは、読書記録はほかのアプリの表を参照しない（account だけ）ので、並びのどこに置いても外部キーは困らないことを書いておく。

### F16 FR-R37（運営者の ID）の景品表示法の確かめが段階4にしかない

- **PRD のどこ**：FR-R37（段階2：ID のない利用者のページに運営者の ID のリンク）・10章「段階4の前に確かめる：景品表示法のステマ規制…持ち主の ID の『買う』リンク（FR-R47）と、組織の本棚での紹介が対象」。
- **何が問題か**：運営者の ID のリンクを、利用者の感想のページに置くのは段階2から。補足 3章のとおり、運営が見返りを得る表示が利用者の感想に混ざると、運営の表示とみなされるおそれがある。確かめが段階4にしかないと、段階2で入れてしまう。運営者の ID は秘密ではないので、設定（環境変数）に持てる（Consistency Conventions「設定」）。
- **直し方**：10章「段階2の前に確かめる」に、FR-R37 の景品表示法の当てはめと、「広告」「PR」の表示の要否を足す。

### F17 FR-R45：読書記録から交流会を作るのは AD-23 の外

- **PRD のどこ**：FR-R45「読書記録は、予約の領域の `index.ts` を通して交流会を作る・選ぶ【仮決め】」・6章「段階4の輪読会で予約・受付を使うときに、`uses` を足す」。
- **何が問題か**：AD-23 がほかのアプリに許しているのは、reception の `index.ts` から「チェックインした人」、booking の `index.ts` から申込みの名簿を**読む**ことだけ。交流会の表は event が持ち（AD-3）、作るのは event の窓口。ほかのアプリから交流会を作る・予約を開くことは、受付アプリの PRD と予約の PRD の範囲の外で、原則 IV は「範囲を変えるときは、先に PRD を直してから」と決めている。
- **直し方**：PRD FR-R45 に「作る前に、受付アプリ（予約）の PRD を直し、AD-23 に『ほかのアプリが event・booking の `index.ts` から交流会を作る・選ぶ』を足す」を書く。読むだけで済む形（利用者が受付アプリで交流会を作り、読書記録はそれを選んで説明の材料をつなぐだけ）なら、AD-23 の今の向きのまま済むので、まずその形を候補にする。

### F18 カレンダーの予定の時刻

- **PRD のどこ**：FR-R28（ブログの下書きを AI で作る）・FR-R29（自分の ID の付いたリンクを入れる）。

### F20 探す（FR-R15）

- **直し方**：account で絞った部分一致（`ILIKE`）で、1人分の量なら足りる。日本語の全文の索引（Cloud SQL の拡張 `pg_bigm` など）を入れるなら、DB の変更の PR として別に出す、と仕様で決める。

### F21 取りこみ直しで重ならない（FR-R8）

- **直し方**：「位置と文で同じもの」は DB の一意の制約（本・読む場所・位置・文の SHA-256 など）で守り、違反を領域のエラーに読みかえる（coding.md 6-4）。分けて送る（F4）ときに2回送っても重ならない形になる。

### F22 調べる文を URL で外の AI に渡す（FR-R18）

- **直し方**：kanaeru からは何も送らないのは正しい（利用者のブラウザが開く URL に入る）。ただし、URL に入った文は外のサービスの記録に残り、長さの上限で切れることがある。長い文はコピーに切りかえる・URL に入る旨を画面で知らせる、と仕様で決める。

### F23 組織の本棚と AI（段階4）

- **PRD のどこ**：FR-R46（組織の人は、ほかの人の説明の材料と感想を見られる）。
- **直し方**：AD-20・Constitution II のとおり、段階2の AI と MCP に渡すのは本人の記録だけ。組織で見えるほかの人の材料は、AI の頼む文・MCP のツールに入れない、と FR-R46 に書く。

### F24 退会の前の手順と MCP の範囲を6章に書く

- **PRD のどこ**：6章「記録の持ち主（AD-19）」「AI（AD-20）…MCP（AD-21）…は利用者の声を見てから」。
- **直し方**：段階1〜3は組織に入れないので、退会の前の手順（AD-22）は持たず、account を消すと外部キーの CASCADE で消える（人物メモの FR-P18 と同じ形）、と書く。段階4で組織に入れると、AD-19・AD-22 の引き継ぎが要る。MCP を作るときの範囲は `reading:read`、ツールは1行に1つの一覧に足す（AD-21）。公開のページの道は `publicReadPaths` で出す（core-016。60秒に600回・IP ごと）。
