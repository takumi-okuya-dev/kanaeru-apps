# PRD Quality Review — 試合表アプリ（prd-kanaeru-match）

対象：`prd-kanaeru-match.md`（status: draft・2026-11-21）と `.memlog.md`。
重さの見立て：社内・小さく出す道具（使う人は実在のサークルの運営1つ・作るのは1人と AI・あとで SaaS の見込み）。5〜8ページで足りる前提で見た。

## Overall verdict

ねらい（§1）・今の流れの表・決めた理由つきの判断（LINE の知らせを使わない・1行に4人の表だけ・ふつうのブラウザ）は具体的で、この規模の PRD としては筋が通っている。一方で、作る人がいちばん頼る「組み方」（FR-M6・FR-M7）と「電波なし・担当の端末・同期」（FR-M13・FR-M19・FR-M20）の終わりの形が決まっておらず、このままでは仕様（spec-kit）に落とすときに作る側が大事なことを推測で決めることになる。さらに、一番の困りごと（§10 の1つ目）と「タブレットを持ってくる」前提（§2.3）が確かめられていないのに、作る順（§7.1）がそれに賭けている点を、リスクとして書いておくべき。

## Decision-readiness — adequate

決めたことは「主催者が決めた」「運営の方の答え」と出どころつきで書かれており（FR-M9・FR-M15・§2.3・§5 の費用）、LINE の知らせを使わない理由（無料の枠は月200通）のように、何を捨てたかも一部は書けている。【仮決め】と §10 の未決も、本当に開いている問い（点数・人数・男女）になっていて、答えが次の文に書いてあるだけの問いはない。

弱いのは、PRD の土台に関わる前提が「前提にする」の一言で済まされ、外れたときにどうなるかが書かれていない点。§2.3「運営はタブレットかノート PC を1台持ってくる前提にする（今は持っていないが、ある前提で作る）」は、当日の組み直し（FR-M11〜M14）と大きく映す（FR-M14）がすべて乗る前提なのに、持ってこなかった日に何が残るか（印刷だけの使い方で足りるのか）が書かれていない。同じく §10「一番の困りごとは、組むことか、当日に直すことか、両方か」は答え次第で §7.1 の作る順が変わるのに、7.1 は「組む → 直す」の順を【仮決め】としているだけで、その賭けを言葉にしていない。

もう1つ、捨てたものが書かれていない判断がある。FR-M13「直せるのは担当の端末1台」は同期を簡単にするための良い判断だが、引き換えに「担当が端末ごと帰った・電池が切れた」ときに誰も直せなくなる。この代償と、そのときの逃げ道を書いておくと、運営の方に確かめるときにも話が早い。

### Findings
- **[high]** 端末を持ってこない日の扱いと、一番の困りごとへの賭けが書かれていない（§2.3・§7.1・§10）— 当日の機能の半分が「今は持っていない端末」に乗っており、作る順も確かめていない仮説に乗っている。*Fix:* §2.3 か §7 に「リスク」を足し、(a) 端末がない日は印刷（FR-M16）＋スマホ（FR-M15）だけで回る、(b) §10 の1つ目の答えが「当日に直すこと」なら 7.1 の2を先にする、と書く。`[NOTE FOR PM]` の形でもよい。
- **[medium]** 担当の端末1台の代償が書かれていない（FR-M13）— 受け渡し（「運営どうしで受け渡せる」）は、渡す側の端末がつながっていない・手元にないときにできるのかが分からない。*Fix:* 「受け渡しは両方の端末がつながっているときだけ／持ち主はサーバーから担当を取り上げられる」など、取れる手を1つ決めて書く。
- **[low]** 費用の判断（§5）は「使う人が増えてから考える」で良いが、SaaS の見込みがあるなら、どの数になったら考えるか（例：サークル何団体）を一言置くと、あとで迷わない。

## Substance over theater — strong

飾りはほとんどない。使う人（§2.1）は3つで、どれも FR を動かしている（声をかける係 → FR-M10・FR-M14、参加者 → FR-M15・FR-M17）。「相手にしない人」（§2.2）も、大会・シングルス・ほかの競技と具体的。非機能（§5）は「安全に・速く」の決まり文句ではなく、Constitution II・III・V を、この道具で何を持たないかに落としている。

少しだけ気になるのは、§5 が「守ること（非機能）」と名乗りながら、数で測れる上限が1つもない点（速さは §8 の成功の基準に置かれている）。これは飾りではなく置き場所の問題なので、Done-ness で扱う。

### Findings
- **[low]** §5 に、端末の種類（iPad の Safari か、Windows の Chrome か）と、計算・表示の速さの上限がない — §8 の「1分以内」「30秒以内」は成功の基準で、作る側が守る上限としては読みにくい。*Fix:* §5 に「動かす端末とブラウザ」と「計算の上限」を移すか、§8 から参照する。

## Strategic coherence — adequate

筋はある：「紙と手の作業を、偏りの少ない自動の組み合わせと、刷り直さない配り方に置き換える」。FR は名簿 → 組み方 → 表 → 当日 → 見せ方 → 電波なし、と1本の流れになっていて、思いつきの一覧には見えない。最初の版の種類は「困りごとを片づける版」で、作る順（§7.1）も印刷だけで価値が出る1から始まっていて、その種類に合っている。

足りないのは、成功の基準（§8）が「ねらいが当たったか」を測る形になっていない点。4つとも作る側の速さと決まりの守り具合で、実在のサークルが使い続けたか（例：続けて3回の練習日で使った・紙を刷り直さなかった・参加者の何人がスマホで開いたか）がない。「刷り直しがなくなる」はねらいに一番近いが、いつ・どう数えるかがない。逆の指標（これが悪くなったら失敗）もない。この道具なら、たとえば「運営が手で入れ替えた回数」（組み方が気に入らずに直した数）が、組み方の質の逆の指標になる。

また、組み方の決まり（FR-M7）とレベルの扱い（FR-M6）はこの PRD の中心なのに、「偏りが少ない」が何を指すかが §1・§2.1・FR-M7 で少しずつ違う（§2.1 は「同じ人と何度も組まない・休みが偏らない」、FR-M7 は「同じペア・続けて休む・試合の数の差」、対戦相手の偏りはどこにもない）。

### Findings
- **[medium]** 成功の基準が、ねらいの当たり外れを測っていない（§8）— 速さと決まりの守り具合だけで、使い続けたかがない。逆の指標もない。*Fix:* 「最初のサークルで、続けて N 回の練習日に、紙の刷り直しなしで使えた」を足し、逆の指標として「運営が手で入れ替えた組の数」を置く。数え方（アプリが記録するのか、運営に聞くのか）も一言。
- **[medium]** 「偏りが少ない」の中身がぶれている（§2.1・FR-M7）— 同じ相手と何度も当たることを避けるかが書かれていない。サークルの練習では、ペアより相手の偏りのほうが不満になりやすい。*Fix:* FR-M7 に「同じ相手（対戦）は○回まで」を入れるか、入れないなら §7.2 に作らないものとして書く。

## Done-ness clarity — thin

この PRD でいちばん弱いところ。FR の多くは何をするかは分かるが、終わりの形（確かめられる条件）がない。とくに組み方と同期は、作る側が推測で決めると、あとで運営の方の思いと違う結果になりやすい。

**組み方（FR-M5〜M7）**
- FR-M6 の3つのうち、「4人のレベルの合計をそろえる」はどこまでの差を許すのか（ペアどうしの合計の差が1以内か）、「近いレベルで組み、ときどき混ぜる」の「ときどき」は何回に1回か、が決まっていない。「コートをレベルで分ける」も、レベルごとの人数が4の倍数でないときにどうするかがない。
- FR-M7 の3つの決まりは、同時に守れないことが普通に起きる。たとえば3面（1回12人）で25人以上だと、1回に13人以上が休むので「2回続けて休まない」は数の上で守れない（休む人が全体の半分を超えると、続けて休む人が必ず出る）。§10 でメインの会の人数がまだ分からない以上、どの決まりを先に守るか（優先の順）と、レベルの扱い（FR-M6）との兼ね合いを決めておかないと、「守れないときはどれを守れなかったかを出す」だけでは作れない。
- FR-M5 の回の数は「試合の時間 ÷ 1試合の長さ」で、入れ替えの時間を含むか、余りをどうするかがない（小さいことだが、印刷の行の数に響く）。

**当日の組み直し（FR-M11・FR-M12）**
- 「それまでの試合の数は引き継いで均す」と FR-M7「試合の数の差は1回まで」が、遅れて来た人で食い違う。3回目から来た人は、残りの回で多めに入れて差を縮めるのか、来てからの回の中で均すのか。差はその日全体で数えるのか、いる人の中で数えるのかを決める必要がある。
- 「帰る」を付けたとき、すでに表に入っている今の回（進行中の回）はどうなるか。「今より先の回だけ」とあるが、「今」が今の回を含むのかが分からない。
- 組み直しで、まだ始まっていない次の回が大きく変わると、声をかける係とスマホを見た人が混乱する。次の回はできるだけ変えない、などの決まりがあるか。

**見せ方（FR-M14〜M17）**
- FR-M14「大きな字で」は形容詞のまま。何メートル離れて読めるか、1画面に何コートまで出すか、を決める。
- FR-M16「同じ表を1枚に」は、8回×3面＋休みの行が A3 に入るかは人数とコートの数次第。入らないときの扱い（2枚に分ける・字を小さくする）がない。

**電波なし・同期（FR-M18〜M20）**
- FR-M19「つながったらサーバーに送る」で、送る前に別の端末（受け渡し後の担当）が直していたらどうするかがない（§6 に「版の番号」とあるが、PRD としての決まり〈後から来たほうを捨てる・知らせる〉がない）。
- FR-M20 で二次元コードから入れた表は、そのあと組み直しがあっても変わらない。読んだ人のスマホに「この表は○時○分のもの。最新ではないかも」と出すのかが書かれていない（FR-M19 の「その時刻を出す」が、二次元コードで入れた表にも効くのかが不明）。
- §4.5・§4.6 の末尾にある ID のない2つ（LINE の知らせは使わない・ホーム画面に置いてネットなしで開く）は、守る決まりなのか背景の説明なのかが分からない。後者は「作る前に実機で確かめる」とあり、確かめた結果だめだったときの代わり（そのときは常につながる前提にする、など）もない。

### Findings
- **[high]** 組み方の決まりの優先の順と、守れないときの動きがない（FR-M6・FR-M7）— 3面で25人以上なら「2回続けて休まない」は必ず破れ、レベルの扱いとも食い違う。作る側が優先の順を勝手に決めることになる。*Fix:* FR-M7 に「守る順：1. 試合の数の差 1回まで → 2. 続けて休まない → 3. 同じペア1回まで → 4. レベルの扱い」のように順を書き、各モードの許す差（例：合計の差1以内・混ぜるのは3回に1回）を数で書く。人数と面の数から「守れない決まり」を作る前に出す、も足すとよい。
- **[high]** 同期と食い違いの決まりがない（FR-M13・FR-M19・§6）— 担当の受け渡しと、つながっていない間の直しが重なったときの扱いが PRD にない。§6 で構成の決めごとに投げているが、どちらを残すかは利用者から見える振る舞いなので PRD で決めるもの。*Fix:* 「サーバーにある版より古い版から直したものは送らず、担当の端末に知らせる」などの振る舞いを FR として足す。
- **[medium]** 遅れて来た人・帰る人の均し方が FR-M7 と食い違う（FR-M11）— *Fix:* 「試合の数の差は、その回にいる人の中で、来てからの回の数で割った率で均す」など、数え方を1つ決めて書く。今の回は組み直さない、次の回は変える数を最小にする、も決める。
- **[medium]** 形容詞のままの要件（FR-M14「大きな字」・FR-M16「1枚に」）— *Fix:* 「5m 離れて読める字（目安：画面の高さの○分の1）・1画面に4面まで」「A3 に入らないときは回で2枚に分ける」と上限で書く。
- **[medium]** 二次元コードで入れた表が古くなることの扱いがない（FR-M20）— *Fix:* 「入れた時刻を出す・組み直しがあっても変わらないことを画面に出す」を FR-M20 に足す。
- **[low]** ID のない要件が2つある（§4.5 末尾・§4.6 末尾）— *Fix:* 前者は §7.2 の作らないものへ移し、後者は FR-M21 にして、実機で確かめてだめだったときの代わりを書く。

## Scope honesty — adequate

作らないもの（§7.2）は具体的で、空いたコートに入れる形・読み上げ・点数・シングルス・お金と、利用者が「あるだろう」と思いそうなものを押さえている。【仮決め】も §9 にまとめてあり、この重さなら未決の数（仮決め6・未決6）は多すぎない。

穴は3つ。(1) memlog の仮決めにある「電波なしで渡す二次元コードを最初の版に入れる」が、PRD では【仮決め】の印も §9 の一覧にもない（FR-M20 は決まったことのように書かれている）。(2) memlog の決めたこと「見た目は受付アプリと同じ（墨・tokens.css・上の帯とサイドバー）」が PRD に1行もない。見本（mockups）を作り直した理由そのものなので、落とすと次の見本でまた同じ外れ方をしやすい。(3) 交流会（event）との関係が書かれていない。§5 の権限は「その交流会の主催者」で、試合表が受付アプリの交流会の下にある前提だが、FR-M1 の CSV だけで作る使い方（受付アプリを使わないサークル）でも交流会を作る必要があるのかが分からない。今の最初のサークルは受付アプリを使っていないので、ここは利用者の手間に直結する。

個人の情報も、言葉の上では §5 で守っているが、決めきれていないところが残る。見るだけのリンク（FR-M15）はログインなしで、呼び名（姓）と組み合わせを、リンクを知る人なら誰でも見られる。リンクの有効期限・推測できない作り・あとで消せるか、と、試合表をいつまで残すか（Constitution II の「消してほしいと頼まれたら消す」）が書かれていない。レベルを参加者の画面や印刷に出すかも書かれていない（上級・入門が貼り出されるのを嫌がる人はいる）。

### Findings
- **[medium]** 交流会と試合表の関係がない（§5・FR-M1・FR-M4）— CSV だけで使うとき、交流会を作る手間があるのかが分からない。*Fix:* 「試合表はいつも1つの交流会の下に作る。CSV から作るときは、日付と名前だけの交流会をその場で作る」のように決めて書く（AD-23 の形に合わせる）。
- **[medium]** 見るだけのリンクの寿命と、試合表を残す期間がない（FR-M15・§5）— *Fix:* 「リンクは推測できない作り・主催者が止められる・交流会の○日後に見られなくなる」「試合表は○日で消す、または主催者が消せる」を足す。レベルを参加者に見せるかも決める（見せない、が無難）。
- **[low]** memlog の仮決め・決めたことが2つ落ちている（FR-M20 の【仮決め】・見た目は受付アプリと同じ）— *Fix:* FR-M20 に【仮決め】を付けて §9 に足し、§5 か §0 に「見た目は受付アプリと同じ（tokens.css・上の帯とサイドバー）」を1行入れる。

## Downstream usability — thin

この PRD は §6 のとおり構成の決めごと（`/bmad-architecture`）と、そのあと spec-kit の仕様に流れるので、この観点は軽くない。FR の番号は M1〜M20 で抜けも重なりもなく、参照先（予約の PRD の FR-B103・AD-19・AD-23・見本・B6 の調べ）はすべて実在していた。

ただ、言葉の表（§3）に、本文で使う大事な名詞が足りない。「交流会」（§5・FR-M15）、「練習日」（§1）、「進み具合」（FR-M12・M13・M20）、「運営」と「主催者」が表にない。とくに「主催者」は §0・FR-M9・FR-M15・§5 の費用では「kanaeru の持ち主」の意味で使われ、§5 の権限では「その交流会の主催者（持ち主か組織の管理者・編集者）」という役割の意味で使われていて、同じ言葉が2つの意味になっている。spec-kit で権限を書くときに取り違えやすい。

FR-M4 には中身の穴がある。予約の PRD の FR-B103 が出すのは「名前・チェックインの ID」だけで、レベルは出さない。受付のチェックインから作った名簿にはレベルがないので、FR-M6 の組み方がそのままでは動かない。また、受付での名前は LINE の表示名なので、FR-M2 の「姓から呼び名を作る」も効かない。

### Findings
- **[medium]** 受付からの名簿にレベルと氏名がない（FR-M4 と予約の PRD FR-B103）— *Fix:* 「チェックインした人には、運営がその場でレベルと呼び名を付ける（前回の試合表の名簿から引き継ぐ）」など、足りないものの埋め方を FR-M4 に書く。作る順の5番目なので、決めるのは後でもよいが、穴があることは書いておく。
- **[medium]** 「主催者」が2つの意味で使われている（§0・FR-M9・§5）— *Fix:* kanaeru の持ち主は「kanaeru の持ち主」か「作る人」と書き分け、「主催者」は §5 の役割の意味だけにして §3 に足す。「運営」との関係（運営＝サークルの人で、kanaeru の上では主催者の役割を持つ）も §3 に書く。
- **[low]** 言葉の表に「交流会」「進み具合」「練習日」がない（§3）— *Fix:* 足す。「進み具合」は「今の回の番号と、終えた回」と決めておくと FR-M12・M20 の中身がはっきりする。

## Shape fit — strong

運営1人が操作する道具で、利用者の旅（UJ）を立てていないのは正しい。代わりに §1 の今の流れの表と §2.1 の片づけたい用事が、旅の役目を短く果たしている。参加者側の動き（入口の二次元コード → ふつうのブラウザ → 自分の名前に印）は FR-M15・FR-M17 に収まっていて、これ以上の形式は要らない。長さも、この重さに合っている。

1つだけ足すとよいのは、当日の1日の流れ（受付 → 試合表を作る → 回を進める → 欠席・遅刻で組み直す → 終える）を5行ほどの手順で書くこと。UJ ほど重くせず、FR-M11〜M14 と FR-M19 の順番の前提（どの時点で誰の端末がつながっているか）がはっきりする。

### Findings
- **[low]** 当日の流れが FR に散らばっている（§4.4〜§4.6）— *Fix:* §2.3 の下に「当日の流れ」を5行ほど足し、各段で使う FR を添える。

## Mechanical notes

- **ID の続き**：FR-M1〜M20 は抜け・重なりなし。ID のない要件が2つ（§4.5 末尾の LINE の知らせ・§4.6 末尾のネットなしで開く）。
