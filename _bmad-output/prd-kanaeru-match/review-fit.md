# 点検：試合表の PRD が、原則・構成の決めごと・今のアプリに合っているか

作成：2026-11-21（AI のレビュー。対象は [PRD 試合表](./prd-kanaeru-match.md) の叩き台〈2026-11-21〉）。照らし合わせたもの：[Constitution](../../.specify/memory/constitution.md) 1.2.0・[構成の決めごと](../architecture-kanaeru/architecture-kanaeru.md)（AD-3・AD-4・AD-5・AD-8・AD-10・AD-14〜AD-24・Capability map・Deferred）・[PRD 受付アプリの予約](../prd-kanaeru-booking/prd-kanaeru-booking.md)（4.7・4.8・FR-B22・FR-B103）・[コードの書き方](../../docs/rules/coding.md)（2・6-6）・[並行開発の決まり](../../docs/rules/parallel-development.md)・[文書の決まり](../../docs/rules/documents.md)・[土台の DESIGN.md](../../docs/design/DESIGN.md)・[EXPERIENCE.md](../../docs/design/EXPERIENCE.md)・[受付アプリの DESIGN.md](../ux-kanaeru-reception/DESIGN.md)。今のコード（`apps/web/src/main.tsx`・`apps/web/src/lib/liff.ts`・`apps/web/src/features/booking/csv-read.ts`・`apps/api/src/modules/reception/index.ts`）も読んだ。

## まとめ

ねらいと範囲は小さく、Constitution の I（お金を預からない）・III（気軽さ）・V（費用）とよく合っている。LINE の知らせを使わない判断も、費用の面で筋が通っている。一方で、PRD のいちばんの前提である「電波がなくても動く」と「参加者はログインなしで、ふつうのブラウザで見る」は、**今の構成の決めごと（AD-4・AD-14）と Constitution の技術の制約にまっすぐぶつかる**。6章の「構成の決めごとに要る改訂」は、この2つを Service Worker の範囲と同期の話だけに縮めていて、要る改訂の半分ほどが抜けている。持ち主の形（AD-19）と、公開の見るだけのリンクの守りも決まっていない。仕様（spec-kit）に進む前に、6章を広げて `/bmad-architecture` で新しい AD を足すのがよい。

## 良いところ（このまま残す）

- 持つ情報を呼び名・レベル・試合表に絞り、メールアドレスや要望の列を読まない（Constitution II）。
- 計算を端末で行い、サーバーは保存と配るだけにする（Constitution V）。
- LINE の知らせを使わない理由（無料の枠が月200通）を書いている。
- reception の `index.ts` からチェックインした人を読む形（FR-M4）は、AD-23 の「ほかのアプリには reception が出す。booking は出さない」と、予約の PRD FR-B103 にそのまま合う（`listEventAttendees`・`hasCheckedIn` はもうある）。
- 実在のサークル・人の名前・フォームの URL を書かない（文書の決まり 3・コードの書き方 2）。
- アプリの key `match` は AD-15 の予約語とぶつからず、英小文字の単数。

## 指摘

### F1【critical】ネットなしで開くには、今の画面の始め方（AD-4）を直す必要がある

- **場所**：4.6（FR-M18・FR-M20・最後の項目）、6章 2つ目
- **何が問題か**：AD-4 は「`liff.init()` を組み立てがルーターより先に呼ぶ」と決めていて、今の `apps/web/src/main.tsx` も `initLiff()` が失敗すると `StartupErrorPage` を出し、ルーターを作らない。ネットがないと LIFF の SDK を読めない・`liff.init()` が通らないので、Service Worker で画面のファイルを持っていても、**試合表の画面は開かない**。参加者の見るだけのページ（ログインなし）でも、ふつうのブラウザで LIFF を始めると LINE のサーバーへの往復が増え、電波の弱い体育館で遅くなる・落ちる。6章は Service Worker の範囲だけを書いていて、この点が抜けている。
- **直し方**：6章に「AD-4 を直す：試合表の道（運営のネットなしの画面と、参加者の見るだけのページ）では、LIFF を始めずにルーターを作れるようにする（または LIFF の失敗を、ネットなしの扱いに落とす）」を足す。これは組み立て（`main.tsx`・`lib/liff.ts`）を直す共通の PR になるので、[並行開発の決まり](../../docs/rules/parallel-development.md) 3-3 のとおり領域の PR と分けて先に入れる、と書く。運営の端末が、ネットなしのあいだ自分のセッション（クッキー）を確かめられないことの扱い（画面だけで動き、つながったら送る）も、同じ AD に書く。

### F2【high】参加者の画面を「ふつうのブラウザ・ログインなし」にするのは、Constitution の技術の制約と AD-14 にぶつかる

- **場所**：4.5（FR-M15・FR-M16・FR-M17）、5章「気軽さ」、6章
- **何が問題か**：
  - Constitution の技術の制約は「参加者の画面は未認証の LINEミニアプリ」と書いている。FR-M15 は、参加者の画面を LINE の外のふつうのブラウザにすると決めている。Constitution は PRD より優先する（Governance）ので、このままでは PRD が負ける。
  - AD-14 は「参加者が外から開く URL の形は `packages/contracts/src/core` に1つ」「QR にはミニアプリの URL を入れる。Cloud Run の URL を直接入れない」と決めている。理由は、置き場所の URL を変えても印刷した QR を使えるようにするため。FR-M17 は「毎回同じ紙でよい」入口の紙を前提にしていて、その紙に Cloud Run の既定の URL を入れると、独自のドメインを取ったとき（Deferred：メールを本番で送る前に取る）に紙がすべて使えなくなる。
  - 今のスイートで、ログインなしで**人の名前**を見せる画面はない（予約の申込みページ `/e/{eventId}` はログインなしだが、名前は出さない。FR-B40）。新しい種類の公開の画面になる。
- **直し方**：
  1. `/speckit-constitution` で、技術の制約の「参加者の画面は未認証の LINEミニアプリ」を「受付アプリの参加者の画面は…」に絞るか、「試合表の見るだけのページは、ログインなしのふつうのブラウザで開く」を足す（言い直しなら PATCH、例外を足すなら MINOR）。
  2. 新しい AD（例：「ログインなしで見る公開のページ」）を足し、AD-14 の例外として、道の形（`/match/…` の下に置くか、`-` を含む参加者の道にするか）・QR に入れる URL（独自のドメインを取るまで紙を配らない、または源が変わっても生き残る短い道にする）を決める。
  3. 6章に、AD-14・AD-15（参加者が開く道の置き場所）と Constitution の改訂を足す。

### F3【high】見るだけのリンクの守りが決まっておらず、FR-M15 と FR-M17 が食い違う

- **場所**：FR-M15・FR-M16（印刷の「最新はスマホで」の二次元コード）・FR-M17、5章「個人の情報」
- **何が問題か**：
  - FR-M15 は「交流会ごとの見るだけのリンク」、FR-M17 は「毎回同じ紙でよい」。毎回同じ紙なら、リンクは交流会ごとではなく、サークル（持ち主か組織）ごとに固定で、その日の試合表に飛ぶ形になる。体育館に貼りっぱなしの紙や、写真に撮られた紙から、**いつでも、誰でも、その日の名前の一覧を見られる**ことになる。
  - 札（トークン）の作り方・期限・作り直し・検索に出さないこと・過去の回を見せないこと・何を返すか（呼び名と組み合わせだけ）・回数の制限が書かれていない。`eventId`（`uuidv7()` は時刻の順に並ぶ）を札に使うと推し量られやすい。
- **直し方**：新しい AD（F2 の2）か FR に、次を書く。
  - 札は推し量れない乱数にし、交流会（試合表）ごとに作り直せる。固定の入口の紙は「今日の試合表へ飛ぶ道」にして、**その日（日本時間の日付）が終わったら何も出さない**【仮決め】。
  - 返すのは呼び名・組み合わせ・進み具合・最後に直した時刻だけ。レベル・氏名・account は返さない。
  - ページに `noindex` を付け、API は回数の制限の内側に置く。
  - FR-M15 と FR-M17 のどちらの形にするかを決め、9章の仮決めに足す。

### F4【high】持ち主と権限の形が AD-19・AD-22・AD-23 の形になっていない

- **場所**：5章「権限」、4.1 FR-M4、7.1
- **何が問題か**：5章は権限を「その交流会の主催者（持ち主か、入れた組織の管理者・編集者。AD-19・AD-23）」と書き、試合表を受付アプリの交流会（`event`）に結びつけている。しかし、
  - AD-19 は「新しいアプリは、最上位の記録（例：…**試合表**…）に最初から持ち主の `account_id` を持つ」「記録を組織に入れる表と担当は、そのアプリが持つ」「権限はそのアプリの領域の中の1つの関数で決める」と決めている。
  - 作る順の1番（CSV と手で足す）は交流会なしで動く。交流会に結びつけると、受付アプリが見えない・契約がない人（AD-15「相手のアプリが使えないときは、その部分を出さない」・AD-16）は試合表を作れなくなる。
  - 2026-11-21 に AD-22 に足した「組織の中のチーム」（記録をチームに入れる）にも触れていない。
- **直し方**：5章と6章に、次の形を書く【仮決め】。
  - 最上位の記録は試合表の1日分（例：`match_day`。名前は仕様で決める）で、`owner_account_id` を持つ。交流会とのつながりは任意の `event_id`（FR-M4 を使うときだけ）。
  - 組織（かチーム）に入れる表は match が持ち、`organization_member`（`team_member`）を指す複合の外部キーを CASCADE（AD-22）。
  - 権限の判定は match の1つの関数：持ち主か、入れた組織の管理者・編集者（チームに入れていればチームの人）。FR-M4 で読むときは、event の判定でもその交流会の主催者であることを確かめる。
  - 退会の手順（AD-22 の (2)）：組織に入れた試合表は管理者に引き継ぎ、入れていないものは消す。
  - 「声をかける係」が直せない（見るだけのリンクで見る）ことを 2.1 に書く。

### F5【high】端末とサーバーの食い違いの扱い（担当の端末1台・版の番号）は、新しい AD が要るのに中身がない

- **場所**：FR-M13・FR-M19、6章 4つ目、9章「組み直せるのは担当の端末1台」
- **何が問題か**：スイートで初めての「端末で直して、あとで送る」記録になる。今の約束（一覧は5秒おきに読み直す・領域をまたぐトランザクションを作らない）だけでは足りない。次が決まっていない。
  - 担当をどう持つか（account ではなく端末なのか、端末の印をどこに持つか）。担当の端末がネットなしのまま、ほかの運営が担当を取りたいとき（電池切れ・忘れ物）にどうするか。取られた端末があとでつながったときに、送り待ちの直しをどう扱うか（捨てる・見せる）。
  - 版の番号が合わないときの返し方（エラーの code。Conventions の表に足すもの）。同じ直しを2回送っても1回分になる形。
  - 送るのは表のまるごとか、直しの一つずつか。
  - Service Worker で古い画面が長く残るので、API は古い版の画面からの送りも受けられる形にする（DB の変更の「前の版のアプリでも壊れない形」と同じ考え）。
  - DB の夜間停止の `503 DB_UNAVAILABLE` を「つながっていない」と同じに扱うこと（F10）。
- **直し方**：6章 4つ目を、上の項目を並べた「新しい AD で決めること」に広げる。PRD では利用者から見える決まり（例：担当を取ると、前の端末の送っていない直しは使われず、その旨が出る【仮決め】）だけを FR-M13 に足し、細かい形は AD と仕様に回す。

### F6【high】電波なしで渡す（FR-M20）と、コートの横の端末（FR-M14）が、電波なしでは成り立たない

- **場所**：FR-M14・FR-M20、2.3
- **何が問題か**：
  - FR-M20：二次元コードをスマホで読むと URL が開くが、電波のないスマホは、**一度も開いたことがなければページそのものを読めない**。表の中身を URL に入れても、ページの入れ物がない。人数とコートが多いと、中身が増えて二次元コードが細かくなり、タブレットの画面から読みにくくなる。
  - FR-M14：「コートの横に置いた端末」が担当の端末と別の端末なら、電波なしでは担当の端末の組み直しが届かない。2.3 は「運営は1台」の前提で、2台目がどこから来るかもない。
- **直し方**：
  - FR-M20 に「前に一度でも試合表を開いたスマホ（画面のファイルを持っているもの）で使える」と条件を書くか、作る順の4番を「実機で確かめてから入れるか決める」にする。中身は URL の `#` の後ろに入れ、サーバーに届かない形にする（個人の情報の面でもよい）。人数の上限（例：何人・何面までなら1つの二次元コードに入るか）を作る前に確かめる。
  - FR-M14 に「大きく映すのは担当の端末の画面を切り替えて行う。別の端末なら、電波があるときだけ最新になる」を書く。

### F7【medium】組み合わせの計算を「共有のパッケージ」に置くのは AD-18 に反する

- **場所**：6章 3つ目
- **何が問題か**：AD-18 は「共通にしてよいのは、業務を知らず、状態を持たない技術の道具だけ」「業務の共通は作らない」と決めている。ダブルスの組み合わせの計算は試合表の業務そのもので、`packages/` の共有の包みには置けない。
- **直し方**：「組み合わせの計算は match の領域の中に置く（画面だけで使うなら `apps/web/src/features/match/`、サーバーでも確かめるなら `packages/contracts/src/match/`。AI の作業を contracts に置く AD-20 と同じ考え）」に書き直す。計算が重いときに画面を止めないよう Web Worker で動かすなら、画面の CSP（`worker-src`。AD-8・AD-21 の `platform/web`）の共通の PR が要ることも書く。

### F8【medium】氏名をサーバーに送るのか、どの端末が持つのかが食い違う

- **場所**：FR-M1・FR-M2・FR-M4、5章「個人の情報」、9章 2つ目
- **何が問題か**：FR-M1 は「読む：氏名」「読まない列はサーバーに送らない」と書き、氏名は送るように読める。5章は「持つのは呼び名・レベル・試合表だけ」で、氏名は持たないように読める。FR-M2 は同じ姓の見分けに氏名が要り、FR-M13 の担当の受け渡しで別の端末に移ると、氏名がなければ呼び名を作り直せない。FR-M4 は reception から氏名（チェックインの名前）を受け取る。
- **直し方**：どちらかに決めて、FR-M1・5章・9章をそろえる。おすすめは「氏名はサーバーに持つ（主催者だけが見る。見るだけのリンクと二次元コードには出さない）」で、Constitution II の「PRD で決めた、そのアプリに要るもの」として 5章に書く。持たないなら、担当の受け渡しと FR-M4 の突き合わせができないことを書く。

### F9【medium】名簿を消す時期・消してほしいと頼まれたとき・運営の端末に残るものが書かれていない

- **場所**：5章「個人の情報」、4.6 FR-M19
- **何が問題か**：Constitution II は「消してほしいと頼まれたら、その人のデータを消す」を求める。参加者は account を持たないので、本人が自分で消す道がない。名簿（氏名・レベル）を次の回に使い回すのか、その日だけなのかもない。運営の端末（共用のタブレットのこともある）のブラウザの中に、名簿と表が残り続ける。
- **直し方**：5章に次を足す【仮決め】。
  - 参加者から頼まれたら、主催者が名簿からその人を消す（試合表の行は呼び名を消して「（消した人）」にする、など）。
  - 名簿を持つ期間（例：その日の試合表は N 日で消す、名簿を使い回すならその旨）。
  - 運営の端末に残すのはその日の分だけにし、ログアウトや担当を外れたときに端末の中を消す。
  - AD-19 の消し方：試合表は持ち主のデータとして CASCADE（参加者は account を持たないので `409` にはならない）。

### F10【medium】DB の夜間停止（0時〜8時）のあいだ、見るだけのリンクと送りが止まる

- **場所**：4.5・4.6、5章「費用」
- **何が問題か**：AD-10 で、0時〜8時は API が `503 DB_UNAVAILABLE` を返す。朝の早い練習や、前の夜遅くに表を作る運営には、見るだけのリンクが開かない・送りが届かない時間がある。8時ちょうどは DB の起動を待つ（AD-24 の注）。また、見るだけのリンクも `requireApp`（AD-16）で suite の表を読むので、夜は 404 ではなく 503 になる。
- **直し方**：4.6 に「`503 DB_UNAVAILABLE` はつながっていないのと同じに扱い、端末に残して8時以降に送る。見る側は最後に読んだ表と時刻を出す」を足す。2.3 に「練習は8時〜24時の中」【仮決め】を足し、外れる会があれば AD-10 の「その日の停止を止める」の手順を使う、と書く。AD-10 の Deferred（暮らしのアプリでの見直し）に試合表を足すかを 6章で聞く。

### F11【medium】Google フォームの CSV を読む処理が booking と二重になる。booking の名簿とも重なる

- **場所**：FR-M1、6章
- **何が問題か**：
  - booking はもう Google フォームの CSV を画面の中で読む（FR-B22・`apps/web/src/features/booking/csv-read.ts`。文字コードの判定・RFC 4180 の切り方・見出しの重なり）。そのファイルは「使うのは booking だけなので、ほかの領域が要るまでここに置く（AD-18）」と書いている。試合表が2つ目の領域になる。
  - 同じ氏名の見分け（FR-M1 の「同じ氏名が2回あれば新しいほう」）は、Conventions の「同じ名前」の比べ方（reception の contracts の `normalizeCheckinName`。booking の FR-B24 も使う）とそろえるべき。
  - 予約の PRD の UJ-1（名簿だけを使う）は、まさにこのサークルの流れ（フォーム → CSV → 名簿）で、運営は同じ CSV を booking と試合表の2か所に取り込むことになりうる。AD-23 は「ほかのアプリには booking は出さない」と決めている。
- **直し方**：
  - 6章に「CSV を読む道具を、領域の PR の前に小さな共通の PR で `apps/web/src/lib`（か `packages/csv`）に移す（AD-18・並行開発の決まり 3-3）」を足す。
  - FR-M1 の同じ氏名の判定は reception の contracts の比べ方を使う、と書く。
  - booking の名簿から試合表の名簿を作る形を「この版では作らない」（7.2）に書くか、作るなら AD-23 の直しを 6章に足す。どちらにしたかを予約の PRD の 4.8 にも1行で返す。

### F12【medium】チェックインからの名簿（FR-M4）は、レベルがなく、名前が LINE の表示名のことがあり、ネットが要る

- **場所**：FR-M4、7.1 の5番
- **何が問題か**：reception の `listEventAttendees` が返すのは、チェックインの ID・名前・account・入れ方・時刻だけで、レベルはない。名前はチェックインのときの名前（初めは LINE の表示名。AD-6）で、ニックネームや空白なしのことが多く、FR-M2 の「姓から呼び名」が働かない。CSV の名簿との突き合わせの決まりもない。チェックインも読み出しもサーバーが要るので、「どの体育館も電波がつながりにくい」（2.3）と合わない。受付アプリが見えないときに出さないこと（AD-15）も書かれていない。
- **直し方**：FR-M4 に「CSV の名簿と、名前（reception の比べ方）で突き合わせて『来た』を付ける。当たらない人はレベルを運営が選ぶ」「受付アプリが使えないときは出さない」「読むときにネットが要る」を足す。5番目に作る理由（電波がある会場向け）を 7.1 に書く。

### F13【medium】Service Worker・ホーム画面に置く仕組みは、共通の PR と止め方が要る

- **場所**：FR-M18 の後ろの項目、6章 2つ目
- **何が問題か**：
  - 画面は1つ（`index.html` と組み立てたファイルはスイートで共通）なので、ホーム画面に置くための設定（manifest）を `index.html` に書くと、受付アプリなどほかのアプリの画面にも効く。Service Worker の置き場所（`/match/` の下に置くか、`Service-Worker-Allowed` の見出し）と、画面の CSP（`worker-src`）は、組み立て（`app.ts`・`platform/web`）の共通の変更になる。
  - Service Worker は、一度入ると設定の印（`DOMAIN_FEATURES`）やアプリの公開（`app_setting`）を切っても端末に残る。コードの書き方 2「大きな機能は、設定で止められるように作る」を満たすには、自分で外れる仕組みが要る。
  - Constitution IV「共通の機能は先に PRD を作る」に当たるかもしれない。
- **直し方**：6章に「manifest・Service Worker の置き場所・CSP は、試合表の道でだけ効く形にして、共通の PR（`specs/core/NNN-…`）で先に入れる」「Service Worker には、設定で止めたときに自分を外す仕組みを入れる」を足す。

### F14【medium】ことばが、ほかの文書や PRD の中で食い違う

- **場所**：0章・3章・4.3（FR-M9）・4.5（FR-M15）・4.4（FR-M13）・5章
- **何が問題か**：
  - 「主催者」が2つの意味で出る。0章と FR-M9・FR-M15・5章「費用」では kanaeru を作る人、5章「権限」では交流会を管理する人（予約の PRD 3章の意味）。
  - 2章の使う人は「運営」だが、5章の権限は「主催者」。どちらが同じ人かが書かれていない。
  - 「交流会」を FR-M15 と 5章で使うが、3章のことばにない（予約の PRD では「練習日も含む1回の会」）。F4 で最上位の記録を交流会と分けるなら、別のことば（例：練習日）が要る。
  - 「担当の端末」の「担当」は、AD-19・AD-22 の「担当」（記録に人を割り当てること）と同じことばで、意味が違う。
  - 「二次元コード」は、受付アプリの DESIGN.md・構成の決めごとでは「QR」（「受付QR」など）。EXPERIENCE.md 2「同じものを、別のことばで呼ばない」。
- **直し方**：作る人の意味は「kanaeru の持ち主」か「運営者」（AD-16 のことば）に書き換える。3章に「運営＝この PRD の主催者（予約の PRD 3章）」「交流会（か練習日）」を足す。「担当の端末」は「操作する端末」など別のことばにする。「二次元コード」と「QR」はどちらかにそろえる。

### F15【medium】大きく映す画面と印刷の見た目が、今のデザインの値で足りない

- **場所**：FR-M14・FR-M16
- **何が問題か**：土台の DESIGN.md の文字の段は最大で `xxl` 32px で、「大きさは段からだけ選ぶ」。コートの横から読む文字には足りない。A3 横の印刷も、受付アプリの DESIGN.md には「印刷ではナビを出さない」以外の決まりがない。試合表のプロダクトの DESIGN.md・EXPERIENCE.md はまだない（見本だけ）。
- **直し方**：6章か7章に「試合表の DESIGN.md（受付アプリの DESIGN.md を引き継ぐ）で、大きく映すための文字の段と印刷の決まりを足し、`tokens.css` に写す」を足す。今の回・次の回・自分の名前の印は色だけで伝えない（EXPERIENCE.md 6）ことも FR-M10・FR-M15 に書く。

### F16【low】初めて使う技術の学びの文書が要る

- **場所**：4.6・6章
- **何が問題か**：Service Worker とホーム画面に置く仕組み、property-based のテスト（fast-check などの新しい依存）は、このリポジトリで初めて使う（`docs/study/` は gcp・line・terraform だけ）。文書の決まり 1 は、初めて使う技術を入れるときに学びの文書を、機能の PR と別の小さな PR で足すと決めている。
- **直し方**：6章か7章に「Service Worker と property-based のテストの学びの文書を、作る前に足す」を書く。

### F17【low】LINE の中のブラウザを避けきれない

- **場所**：FR-M15
- **何が問題か**：参加者が LINE のカメラやオープンチャットのリンクから開くと、LINE の中のブラウザで開く。「LINE の中のブラウザにしない」は画面の側だけでは決めきれない。
- **直し方**：「URL に `openExternalBrowser=1` を付けて、LINE から開いても外のブラウザに移す（要確認）。LINE の中で開いても見られる形にする」と書く。

### F18【low】外の AI に試合表を渡さないことを書く

- **何が問題か**：試合表は、ほかの人の名前の一覧。AD-20 と Constitution II は「外の AI に渡してよいのは利用者本人の記録だけ」。
- **直し方**：5章に「試合表と名簿を返す MCP のツール・AI の作業は作らない（AD-20）」を1行足す。

### F19【low】見るだけのリンクの読み直しの間隔と、回数の制限

- **場所**：FR-M19・FR-M15
- **何が問題か**：今の約束は「一覧画面は5秒おきに読み直す」。参加者20〜30人がそれぞれ5秒おきに読むと、同じ IP に見える会場（AD-8 の `RATE_LIMIT_MAX`）で受付と一緒に制限に当たりうる。db-f1-micro にも毎回届く。
- **直し方**：見るだけのページの間隔（例：15〜30秒、変わっていなければ中身を返さない）を、AD か仕様で決めると 6章に書く。

### F20【low】レベルで分けると、見るだけのページからレベルが分かる

### F21【low】名前が公開のページに出ることを、参加者が知る道がない

### F23【low】文の形と、6章の書き方

- **場所**：冒頭・6章・7.1・0章
- **何が問題か**：
  - 文書の決まり 3「冒頭に、作った日・直した日（と何を直したか）を書く」。前付け（frontmatter）と11章にはあるが、予約の PRD のような本文の冒頭の「作成：…」の行がない。
  - 6章が AD の番号を挙げていない。要る改訂は、少なくとも AD-4（F1）・AD-14 と AD-15（F2）・新しい AD（公開のページ・端末で直して送る記録）・AD-18 の当てはめ（F7・F11）・AD-19 と AD-22 の当てはめ（F4）・AD-3 の持ち主の表と表を作る順・Capability map・Conventions（エラーの code・道の頭 `/api/v1/match/*`・表の頭 `match_`）・Constitution の技術の制約（F2）。
  - `.memlog.md` は「電波なしで渡す二次元コードを最初の版に入れる」、7.1 は4番目。どちらが今の決めごとか分かるようにする。
