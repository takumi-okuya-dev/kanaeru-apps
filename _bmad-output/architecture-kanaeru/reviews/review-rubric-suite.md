## 判定

**直してから確かめに回す（中くらい）**。AD-15〜AD-21 は、バックログ A のおもな分かれ道（DB の変更の通し方・アプリという単位・使えるかの1か所での判定・共通の手伝い・AI の作業の1か所での定義・MCP の認可）を押さえていて、memlog の決めごとは全部文書に入っている。ただし、次のことが残っている。

1. AD-21 の道（`/mcp`・`/oauth/*`・`/.well-known/*`）が、AD-8 といまのコードの「`/api` 以外はすべて画面」と食い違う
2. バックログ A 8 の細かい点のうち、いくつかがどこにも入っていない（貼り戻しの形が崩れたとき・書く前の確かめ・トークンでのログイン〈AD-12〉・アカウントとログインの手段の表を分けること・アプリの中の AI）
3. Constitution の原則 I・II・IV と、文字どおりには食い違う所を Open Questions に上げていない
4. 「付け忘れ」で破れる Rule がある（`requireApp`）。アプリどうしの依存・予約した道の頭・`DOMAIN_FEATURES` との関係が決まっていない
5. 運用：夜間の停止と独自のドメインの後回しが、MCP や暮らしのアプリと両立しない。新しい秘密の値と、消すときの CASCADE（AD-7）が直されていない

## 2. 指摘

重さ：**高**＝並行して作るとぶれる・壊れる。**中**＝決まりの穴・食い違い。**低**＝書き方・小さなずれ。

### F-1（高）AD-21 の道が AD-8 といまのコードと食い違う

- **AD-8** は「`/api` 以外は `index.html` に戻す」「`/api` の下は API の CSP、ほかは画面の CSP」。コードも同じで、`apps/api/src/platform/web/web.ts` の `isApiPath` は `/api` と `/api/` の下だけを API とみなし、`app.ts` は `serveWeb` を platform と領域の道より**先に** `app.use("*", …)` でつないでいる。
- **AD-21** と Consistency の「道の頭」は、`/mcp`・`/oauth/*`・`/.well-known/*` を `/api` の外に置く。このままだと、`GET /.well-known/oauth-protected-resource`・`GET /oauth/authorize`・`GET /mcp`（Streamable HTTP の SSE）が画面の `index.html` を返し、画面の CSP がかかる。
- さらに、`app.ts` の守りはどれも `/api/v1/*` にだけかかる：本文の大きさの上限・IP ごとの回数の制限・CSRF と Origin の確かめ。`assertDocumentedRoutes`（createRoute を通さない道で起動を止める）も `/api` で始まる道だけを見る。`/mcp`・`/oauth/*` は、入力の確かめと文書の確かめから外れる。
- **直し方**：
  - (a) MCP と認可を `/api/mcp`・`/api/oauth/*` に置き、`/.well-known/*` だけを画面の外の例外にする。または (b) AD-8 を直して「画面に戻さない道の頭」（`/api`・`/mcp`・`/oauth`・`/.well-known`）を `packages/contracts/src/core` の1か所に並べ、`serveWeb`・CSP の分け方・AD-15 の予約した頭（F-4c）が同じものを読む。
  - AD-21 に「`/mcp` は Bearer のアクセストークンだけで確かめ、セッションのクッキーを受けない（CSRF を持ちこまない）」「本文の上限・回数の制限は `/mcp`・`/oauth` にもかける」を足す。
  - 回数の制限はいま IP ごとだが、MCP の接続する側（Claude・ChatGPT）はその会社のサーバーから来るので、多くの利用者が同じ IP に見える。`/mcp` はトークンごとにする旨を Deferred の「回数の制限」に書く。

### F-2（高）バックログ A 8 の細かい点が入っていない

- **(a) 貼り戻しの形が崩れたとき**（バックログの文言そのまま）。AD-20 は「同じ形で確かめる」だけ。アプリごとに見せ方と、段階2の失敗の返し方が変わる。**直し方**：AD-20 に「段階1：確かめは画面で、AI の作業の zod の形で行う。崩れていたら貼った文を残したまま、どこが違うか（`fields`）を出し、直して送り直せるようにする」「段階2：AI の会社のエラーと形の崩れは、`kernel/ai` が決まった code（例：`AI_PROVIDER_ERROR`・`AI_RESPONSE_INVALID`）に読みかえる」と足し、Consistency の「エラー」の行にその code を足す。
- **(b) 書く前に利用者が確かめる**。AD-21 は範囲を分けるだけ。領域ごとに「確かめ」の作り方が変わりうる。**直し方**：書くツールは MCP のツールの注釈（`destructiveHint` など）を付け、消すツールは出さない（または2段階にする）、を AD-21 に足すか、Deferred に「MCP を作るときに、書くツールの確かめの形を platform/mcp に1つ決める（領域は決めない）」と書く。
- **(c) トークンでのログイン（AD-12 を広げる）**。AD-21 は「ツールは窓口と同じ関数と権限を通る」と書くが、AD-12 の `requireSession`・`currentAccount(c)` はクッキーのセッションだけを読む。MCP の道で今の利用者をどう受け取るかが決まっていないので、領域ごとにトークンを読む処理を書きかねない。**直し方**：AD-12 に「account は `requireSession` と同じ形で、アクセストークン（範囲つき）から `currentAccount(c)` を出す middleware を出す。領域はトークンを直接読まない。範囲の確かめも account の関数で行う」と足す。
- **(d) アカウントとログインの手段の表を分ける**。決めた・後回し・未決のどれにもなっていない。AD-2・AD-3 は `account` に LINE のユーザーIDを持つまま。Web 用のチャネルは同じプロバイダーなので、いまは分けなくても動く。**直し方**：Deferred に「LINE 以外のログインの手段を足すときに、`account` から手段の表を分ける（account が持ち、AD-2 を直す）」と書く。
- **(e) AI が代わりに動く（アプリの中の AI）**。Deferred にはモデルと費用しかない。AD-20 の「どの段階も同じ領域の関数を通す」は3つの段階だけを縛る。**直し方**：AD-20 の最後の項目を「段階1〜3とアプリの中の AI のどれも」に広げる。
- **(f) 外の AI に送るときの同意**。Open Questions 7 は「主催者が参加者の困りごとを外の AI に送るか」だけ。バックログの例「次の交流会の参加者をまとめて」は、MCP を通して参加者の名前（チェックイン）を外の AI に出す。B7（人物メモ）も、ほかの人の情報を扱う。**直し方**：OQ 7 を「本人以外の個人の情報（参加者の名前・困りごと・人物メモ）を、段階2・3で外の AI に出すか」に広げる。決まるまでの仮の Rule として、AD-21 に「ほかの人の個人の情報を返すツール・段階2の作業は、OQ 7 が決まるまで作らない。本人のデータだけを返す」を足す。

### F-3（高）Constitution と文字どおりには食い違うのに、Open Questions にない

- **原則 I（お金を預からない。NON-NEGOTIABLE）**：「アプリの中で決済しない」。AD-16 の `entitlement`（サブスクで売る）は「お金は支払いの会社が扱い、kanaeru は預からない」と読みかえている。本文の「参加費は記録するだけ」「先払いや予約課金を求めない」は交流会のことで、サブスクの課金は原則がもともと考えていない。
- **原則 II**：「集めるのは、受付と困りごとに要るものだけ」。新しいアプリの記録（本・レシピ・人物メモ。AD-19）・利用者の API キー（AD-20 の `ai_credential`）・OAuth のトークン（AD-21）は、文字どおりにはこの外になる。
- **原則 IV（YAGNI）**：「MVP の範囲（PRD 6章）の外は作らない。先に PRD を直す」。core-005（suite・台帳・運営者の画面）は受付アプリの PRD の外なので、作る前に PRD（またはスイートの PRD）が要る。この順番が文書にない。
- Constitution の技術スタック制約は「AD-2〜AD-7・AD-12〜AD-14 に従う」とだけ書き、認証は LINE のIDトークンだけを挙げている（AD-15〜AD-21・自前の OAuth が出てこない）。
- **直し方**：Open Questions に「Constitution の改定（MINOR）：原則 I にスイートの課金（支払いの会社に任せ、カードの情報を持たない）を足す／原則 II を『それぞれのアプリが要るものだけ』に広げる／技術スタック制約に AD-15〜AD-21 と OAuth を足す。core-005 の前に `/speckit-constitution` で行う」を足す。core-005 の前に PRD（スイート）を作る、と backlog の「作る順番」にも書く。

### F-4（中）Rule が付け忘れで破れる・ぶれる所が決まっていない

- **(a) `requireApp` は各アプリが自分で付ける**（AD-16）。付け忘れても、テストも lint も止めない。`off` のアプリの API が開いたままになる。`apps.list.ts` が「アプリ → 属する領域」を持つので、**組み立て（`app.ts`）が、その領域の道を `requireApp(appKey)` で包んでからつなぐ**形にすれば、作りで守られる（領域を足しても `app.ts` は直さない、という今の決まりとも合う）。どのアプリにも属さない領域（account・suite・platform）だけが包まれない。あわせて、「どの領域もちょうど1つのアプリに属するか、共通か」を確かめるテストを置く（3-2 のとおり数は書かない）。
- **(b) アプリどうしの依存が決まっていない**。図は「次のアプリ → suite・account」だけ。B7（人物メモ）は reception のチェックインと、B6・B3 は event とつなげたくなる。ほかのアプリの領域の `index.ts` を読んでよいか、読む先のアプリが `off` のときどうするかを、どの AD も決めていない。**直し方**：AD-15 に「ほかのアプリの領域は `index.ts` からだけ読む（いまの lint のまま）。読む側の画面と道は、読む先のアプリの `canUseApp` も通す」か「アプリどうしは読まない。要るものは共通の領域に上げる」のどちらかを書く。
- **(c) 予約した道の頭がない**。AD-15 は新しいアプリを `/<key>/…` に置くが、いまの画面の道は `/`・`/admin/…`・`/e/…`・`/invite/…`・`/dev/login`、組み立てたファイルは `/assets/`、API は `/api`。AD-21 で `/mcp`・`/oauth`・`/.well-known` が加わる。`key` が `admin`・`e`・`dev`・`assets` などと重なれば壊れる。**直し方**：予約した頭を `packages/contracts/src/core` に並べ、`apps.list.ts` の key がそれと重ならないことをテストで確かめる（F-1 の一覧と同じもの）。
- **(d) `DOMAIN_FEATURES` との関係**。いまのコードには、設定 `DOMAIN_FEATURES`（`kernel/features.ts`。「<領域>.<名前>」で大きな機能を入・切する。coding.md 2「大きな機能は設定で止められるように作る」）がある。AD-16 は「公開の状態は設定にせず suite の表に持つ」だが、`DOMAIN_FEATURES` に触れていない。新しいアプリのセッションが、作りかけを `DOMAIN_FEATURES` で隠すか `app_setting` で隠すかがぶれる。**直し方**：Consistency の「設定」の行に「アプリ全体の公開は `app_setting`（AD-16）。アプリの中の大きな機能の入・切は `DOMAIN_FEATURES`（デプロイで変える）」と書き分ける。
- **(e) ナビの作り方**。いまのナビは `features.list.ts` の各領域が出す `nav`・`useNavItems` を外枠が並べる（`apps/web/src/lib/feature.ts`）。AD-15 は「外枠のナビは、一覧のうち `canUseApp` が通るアプリを並べる」。2段（アプリの切り替え＋アプリの中の領域のナビ）にするのか、置きかえるのかが書かれていない。画面が `canUseApp` の結果を知る窓口（例：`GET /api/v1/apps`）も決まっていない（suite の道の頭 `/api/v1/apps/*` だけ）。**直し方**：AD-15 に「アプリの切り替えは外枠、アプリの中のナビは今までどおり領域の `nav`。外枠は suite の `GET /api/v1/apps`（使えるアプリの key の並び）を読む」と書く。
- **(f) LINE ミニアプリのチャネル**。AD-4 は `VITE_LIFF_ID` を1つ埋める形。新しいアプリが LINE の中で開きたくなったとき、別のミニアプリのチャネル（別の LIFF ID）を作ると `lib/liff.ts` の1つの `liff.init()` が破れる。**直し方**：AD-15 か AD-4 に「LINE のミニアプリのチャネルはスイートで1つ。新しいアプリは同じチャネルのパーマリンク（`/<key>/…`）で開く。分けるならこの文書を直す」と書く。B1 を別のブランドにしたいとき（OQ 8）の判断材料にもなる。

### F-5（中）運用・環境の面

- **夜間の停止（AD-10）と MCP・暮らしのアプリ**。DB は0時〜8時に止まり、`canUseApp` も DB を引くので、その間はすべてのアプリと `/mcp` が `503` になる。AI エージェントやレシピのアプリは夜にも使われる。AD-10 は交流会だけを考えた決めごと。**直し方**：Deferred か Open Questions に「暮らしのアプリか MCP を公開する前に、夜間の停止を見直す（費用は原則 V・AD-9 の予算と比べる）」を足す。
- **独自のドメインの後回し**。Deferred の理由は「QR はミニアプリの URL なので、あとで変えても印刷した QR は使える」。しかし AD-21 では、OAuth の発行者（issuer）・保護資源のメタデータの URL・LINE ログイン（Web 用）の戻り先の URL・利用者の AI に登録された MCP の URL が、どれも源（`WEB_URL`）に結びつく。あとで変えると、つないだ AI がすべて切れる。**直し方**：Deferred のこの項目に「MCP と OAuth を公開する前に決める」を足す。
- **新しい秘密の値と設定**。AD-20 の暗号化の鍵（Secret Manager）・AD-21 の LINE ログイン（Web 用）のチャネルのシークレット（認可コードの交換に要る）は、AD-9 の「秘密の値」と Consistency の「設定」の行に出てこない。鍵の入れかえ（暗号文に鍵の版を持つか）も書かれていない。**直し方**：Consistency の「設定」の行に、名前は仮でよいので並べる。鍵の版を暗号文の隣に持つ、と AD-20 に一言足す。
- **消すときの CASCADE（AD-7）**。AD-7 は `ON DELETE CASCADE` を4つの外部キーに限っている。`ai_credential`・OAuth のトークン・AD-19 の新しいアプリの記録（AD-19 は CASCADE と書いた）・`entitlement` が AD-7 に出てこない。原則 II の「消してほしいと頼まれたら消す」に関わる。`entitlement` は、支払いの記録として残すかも決めておく。**直し方**：AD-7 を「本人のデータを指す外部キーは CASCADE（一覧は AD-3 の表で、持ち主の列に印を付ける）」に一般化するか、新しい表を足す。冒頭の「AD-1・AD-3・AD-5・AD-9 を直した」に AD-7 も加える。

### F-6（中）Deferred のうち、2つのアプリがぶれうるもの

- **アプリの中の AI のモデルと費用**：「kanaeru が費用を持つ AI を入れるときに決める」。2つのアプリが並行して、それぞれ AI の会社と費用の持ち方を選びうる。**直し方**：「決めるまで、kanaeru が費用を持つ AI は作らない（段階1・2だけ）」と、作ってはいけないことを書く。
- **人を共有する形（AD-19「そのアプリの仕様で決める」）**：B3（読書の共有）・B6（試合表）・B7 のどれも共有やグループを要りそうで、アプリごとに membership の表ができる。**直し方**：「2つ目のアプリが共有を要るときに、共通の形（account か suite）に上げるかを決める」と、上げる合図を書く。
- そのほか（監視・ステージング・Cloudflare・支払いの会社・操作の記録と回数の制限）は、置き場所が1つなのでぶれない。

### F-7（低）書き方・小さなずれ

- **AD-17 の守らせ方**：「同時に1本」は人が見て守る。`drizzle-kit check` は取り込んだあとのぶつかりを見つけるだけ。PR にラベル（例：`db-change`）を付け、開く前に `gh pr list --label db-change` で見る、を並行開発の決まり 4 に書くと守りやすい。`apps/api/drizzle/*.sql` の数と `_journal.json` の行の数がそろうかの確かめを `pnpm check` に入れると、片方の変更が journal から落ちたときにも止まる。
- **AD-15 の一覧の1行の形**：いまの2つの一覧は `export * as …` の1行。`apps.list.ts` は key・名前・領域・道の頭を持つので、1行に収める形の見本（例：`export const reception = { key: "reception", name: "受付", domains: ["event","reception","survey"], path: "/admin" } as const;`）を決めておかないと、整形の道具が複数行に割り、`merge=union` が壊れる。lint や整形から外す設定も要る。
- **受付アプリの key**：AD-16 は「受付アプリは `public` の行を DB の変更で入れる」だが、key が書かれていない（領域の `reception` と同じ名前にすると、文書で取り違えやすい）。
- **`docs/decisions.md` の `merge=union`**：表の前に説明の文がある。説明の行を2つのブランチが直すと、両方の行が黙って残る。3-1 の「一覧のほかの中身を足さない」とずれるので、説明の文を直す PR は共通の PR に限る、と一言足す。
- **AD-12 の試験用のログイン**：コードは設定 `TEST_LOGIN_ENABLED`（`APP_ENV` が staging・production なら起動で止める）。AD-12 の「`APP_ENV` が local・test のときだけ使える」と、ほぼ同じだが書き方がずれる（`docs/decisions.md` は「環境の名前で分けない」）。
- **ナビを作る時期**：memlog には「2つ目のアプリができたら作る」とあるが、AD-15 には時期がない。
