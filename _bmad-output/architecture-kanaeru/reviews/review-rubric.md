# レビュー：構成の決めごと — kanaeru

## 総評

**判定：条件つきで進めてよい（high 4件を直してから spec-kit に入る）**

骨組み（モジュラーモノリス・4つの領域・表の持ち主・LINE の ID トークンの確かめ・Cloud Run＋Cloud SQL・Terraform・夜間停止・DB の変更の当て方）は、テンプレートの決まり（一方向の依存・`index.ts` だけを読む・`uuidv7()`・`timestamptz`・エラーの形・pino）をそのまま引き継いでおり、テンプレートと食い違う所はほぼない。AD の多くは Rule が具体的で、守れているかを目で確かめられる。費用の大きな分かれ道（ロードバランサ・最小の台数1を足さない）も止められている。

一方で、spec-kit で領域ごとに別々に作ると **ぶれる継ぎ目** がいくつか残っている。とくに、

1. 各領域の道が「いまログインしている account」をどう受け取るか（と、テストでのログインの仕方）が決まっていない。4つの領域すべてが毎回ここを作り直す。
2. 受付QR・アンケートQR・招待のリンクの URL の形（event が作り、reception・survey・event の画面が受ける）が決まっていない。
3. AD-7 の「account を指す外部キーはすべて CASCADE」は、`checkin` の「入れた人」にも当たり、受付係の account を消すと他人の手でのチェックインまで消える。
4. 交流会の当日を止めうる一番の不確かさ（未認証のミニアプリが QR から開けるか・友だち追加を勧められるか）が、memlog では「要確認」なのに、文書には AD も未決の項目もない。

運用の外回り（置き場所・環境・デプロイ・秘密の値）は決まっているが、**バックアップ・費用の上限と知らせ・監視** は「決めた／後回し／未決」のどれにもなっていない。どれも Terraform に数行足すか、「後回し」と明記すれば済む大きさで、6日の期限に見合う直し方を下に書いた。

|---|---|
| critical | 0 |

チェックリストごとの見立て：

| 観点 | 見立て |
|---|---|
| 下の層（領域ごとの仕様）がぶれる継ぎ目を押さえているか | おおむね押さえているが、ログイン中の account の受け取り方・URL の形・取り消しの意味・領域をまたぐ外部キーが抜けている（H-1・H-2・M-2・M-3） |
| AD の Rule が守らせられ、ぶれを本当に止めるか | 多くは良い。AD-7 は Rule が害を生む（H-3）。AD-5 は関数の形がなく、止める力が弱い（H-1） |
| 後回しの項目が、領域どうしをぶれさせないか | 「PC で管理の画面を開くときのログイン」と「独自のドメイン」は、条件をつけないとぶれる（M-10・H-2） |
| テンプレートの決まりを追認しているか | コードの決まりは追認している。デプロイの合図のブランチが development-flow.md（`develop`→ステージング・`main`→本番）と噛み合っていない（M-11）。Better Auth を使わないことの書き換え先も書いておく（L-1） |
| FR-1〜FR-21 と 5章を覆っているか | FR-1〜FR-16・FR-21 は覆っている。FR-6 の仕組みと FR-17〜FR-20 の置き場所がない（H-4・L-2）。5章の「費用」は PRD の補足（Neon）から外れたことを文書に書いていない（L-3） |
| 運用の外回りがすべて「決めた／後回し／未決」になっているか | バックアップ・費用の上限と知らせ・監視・手元とテストでの LINE ログインが抜けている（M-4・M-5・M-6・M-7） |

## 指摘

### high

#### H-1：各領域が「いまログインしている account」と権限をどう受け取るかが決まっていない

- **場所**：AD-4・AD-5、Capability Map の FR-3・FR-21
- **問題**：AD-4 は「ログインしてセッションを出す」までで、出したセッションを **ほかの領域の道がどう読むか** を決めていない。テンプレートの決まりでは、土台が領域に渡すのは `db`・`logger`・`features` だけで（docs/architecture.md 3章・coding.md 6-6）、組み立て（`app.ts`）は「領域を足しても直さない」。このままだと、event・reception・survey の仕様が、それぞれクッキーを読んで `session` を引く処理を自分で書くか、account の `index.ts` に別々の関数を求めることになり、確かめ方がばらける（AD-4 の Prevents に書いた「領域ごとにログインの確かめ方が変わること」そのもの）。AD-5 の「event の `index.ts` が出す1つの関数」も、名前・引数・戻り値がないので、reception と survey の仕様が別々の形を想定しうる。さらに、**テスト（Vitest の結合・Playwright の E2E）でログインした状態をどう作るか** が決まっておらず、LINE の画面は自動のテストで通せないため、各領域が別々の抜け道を作る恐れが強い。
- **直し方**（AD-4 に足すか、AD-12 として足す）：
  - セッションの読み取りは、account の領域が出す **1つの Hono のミドルウェア**（例：`requireAccount`）だけで行う。組み立て（`app.ts`）が `/api/v1/*` に1度だけ付け、`c.get("account")`（`{ id, isOrganizer }`）を入れる。領域はクッキーと `session` の表を直接読まない。これは「組み立てを直さない」の例外として、ログインの仕様で1度だけ直すと書く。
  - 権限の関数の形を決める：`event` の `index.ts` が `roleIn(db, accountId, eventId): Promise<"organizer" | "staff" | "none">` を出し、窓口は `requireRole(...)` の形で使う。役割はセッションやクッキーに入れず、毎回 `event_staff` を引く（FR-21 の「外されたら次から使えない」を守る）。
  - テストでのログイン：`APP_ENV` が `local`・`test` のときだけ動く「テスト用のログイン」の道（例：`POST /api/v1/auth/test-login`）を account の領域に1つだけ置き、`kernel/config.ts` の既存の仕組みで staging・production では起動で止める（`SAMPLE_DATA_ENABLED` と同じ扱い）。LINE の確かめの先（`/oauth2/v2.1/verify`）は結合のテストで差し替える。

#### H-2：受付QR・アンケートQR・招待のリンクの URL の形が決まっていない

- **場所**：Capability Map の FR-2・FR-9・FR-21、Deferred の「独自のドメイン」
- **問題**：QR を作るのは event、QR から開く画面は reception（チェックイン）と survey（アンケート）、招待のリンクは event が作って account・event が受ける。領域ごとに仕様を作ると、QR に入れる URL（Cloud Run の URL か、ミニアプリのパーマリンク `https://miniapp.line.me/<LIFF ID>/…` か）と、画面の道（`/events/{id}/checkin` など）が噛み合わない恐れがある。さらに、Cloud Run の URL を QR に直接入れると、後で独自のドメインに変えたときに **印刷した QR がすべて使えなくなり**、ミニアプリの外のブラウザで開いてしまう（LINE ログインが効かない）。
- **直し方**：Consistency Conventions に「入口の URL」の行を足す。
  - QR と招待のリンクには、**ミニアプリのパーマリンク**（`https://miniapp.line.me/<LIFF ID>/<道>`）を入れる。Cloud Run の URL を直接入れない（ドメインを変えても QR が変わらない）。
  - 道の形を決めて `packages/contracts` に1か所で置く（例：`/e/{eventId}/checkin`・`/e/{eventId}/survey`・`/invite/{token}`。作る関数も contracts に置き、event と画面が同じものを使う）。
  - これを決めると「独自のドメイン」の後回しは、ほかの領域に響かなくなる。

#### H-3：AD-7 の「account を指す外部キーはすべて CASCADE」が、他人のチェックインを消す

- **場所**：AD-7（AD-3 の表の `checkin`「入れた人」、AD-6）
- **問題**：AD-7 の Rule は「account を参照する外部キーは `ON DELETE CASCADE`」。`checkin` には参加者の `account_id` のほかに「入れた人」（手でのチェックインをした受付係・主催者の account）がある（AD-3 の表・FR-7）。これも CASCADE にすると、**受付係が自分のデータの削除を頼んだときに、その人が手で入れたほかの参加者のチェックインが消え**、過去の交流会の合計が変わる（AD-6 が止めたいこと）。Rule どおりに作ると害が出る形。
- **直し方**：AD-7 の Rule を「**その人のデータ**を指す外部キー（`session.account_id`・`event_staff.account_id`・`checkin.account_id`）は CASCADE。記録した人を指す外部キー（`checkin` の入れた人など）は `ON DELETE SET NULL`」に書き換える。`survey_answer` は `checkin` を指す外部キーの CASCADE で消える、という今の書き方はそのままでよい。主催者が代わりに入れた回答（FR-10・A9）に「入れた人」を持たせるなら、同じく SET NULL。

#### H-4：未認証のミニアプリと友だち追加の不確かさが、AD にも未決の項目にもない

- **場所**：文書全体（AD の欠け・未決の節の欠け）、Capability Map の FR-4〜FR-6、memlog の constraint（ミニアプリ・友だち追加）と decision（未認証のミニアプリ）
- **問題**：memlog では「未認証の LINE ミニアプリで作る」が ADOPTED なのに、文書では AD-4 の括弧書きにしか出てこない。また memlog は「QR・パーマリンクからの起動は可能と読める＝要確認」「友だち追加は bot_prompt（ミニアプリでは Add friend option、効かないときは `liff.requestFriendship()`）」としているが、文書にはどちらもない。QR から開けなければ FR-4（受付の柱）が止まり、友だち追加が勧められなければ FR-6（テスターへの連絡）が成り立たない。交流会の当日を止めうる一番の不確かさが、未決の項目として追いかけられていない。FR-6 は Capability Map で AD-2・AD-4・AD-6 に結ばれているが、どれも友だち追加を決めていない。`@line/liff` は 2.31.1 未満が 2026-11-24 ごろ使えなくなる、という期限つきの事実も Stack の括弧書きだけ。
- **直し方**：
  - AD を1つ足す（例：AD-12「LINE の中の画面は未認証の LINE ミニアプリ1つ」）。Rule：チャネルは1つ、`@line/liff` は 2.31.1 以上、LIFF ID とチャネル ID は設定で持つ、友だち追加はチャネルの Add friend option を使い、画面に案内を重ねない（FR-6 の確かめ方）。
  - 「未決（作り始めの1日目に確かめる）」の節を足し、①未認証のミニアプリがカメラで読んだ QR（パーマリンク）から開けるか、②Add friend option が未認証でも効くか、③外のブラウザでログインできるか（今の Deferred の項目をここへ移す）を、確かめる日と、だめだったときの代わり（①がだめなら LIFF アプリに切り替えるか、など）とともに書く。11-25 までの日程なので、①は 11-20 中に結論を出すと書いておく。

### medium

#### M-1：最初の主催者の印をどう付けるかが決まっていない

- **場所**：AD-3（`account` の主催者の印）・AD-5・AD-11
- **問題**：主催者は `account` の印で決まるが、印を立てる道（窓口）は PRD にない。本番の DB を手元から直すのは AD-11 が止めている。account の仕様が、DB を手で直す・隠し窓口を作る・設定で決める、のどれを選ぶかで、ほかの領域の確かめ方とテストが変わる。
- **直し方**：AD-5 に「主催者は設定 `ORGANIZER_LINE_USER_IDS`（LINE のユーザー ID の並び。秘密ではない）で決め、ログインのたびに印を合わせる」のように1行足す。表に印を持たない形（設定だけで判定）でもよい。どちらかに決める。

#### M-2：チェックインの「取り消し」が消すのか印を付けるのかが決まっていない

- **場所**：AD-6・AD-7、FR-5・FR-8
- **問題**：FR-8 の取り消しを行の削除にするか、取り消しの印（`canceled_at`）にするかで、①FR-5 の二重防止の一意の制約（`event_id`＋`account_id`。coding.md 6-4 は DB の一意の制約で守る決まり）、②取り消した人の回答（`survey_answer` は CASCADE で消えるのか、残るのか）、③合計と書き出しの絞り込み、がすべて変わる。reception と survey が別々に決めるとずれる。
- **直し方**：AD-6 か AD-7 に1行足す。最小の手間なら「取り消しは行を消す（`survey_answer` も消える）。一意の制約は `checkin(event_id, account_id)`（`account_id` が空の手でのチェックインは制約の外）」。履歴を残したいなら逆に決める。どちらでもよいが、1つに決める。

#### M-3：領域をまたぐ外部キーの書き方が、境界の lint とぶつかる

- **場所**：AD-3・AD-7、Paradigm（`index.ts` からだけ読む）
- **問題**：`checkin.account_id` などの外部キーを Drizzle で書くには、reception の `schema.ts` が account の表の定義を読む必要がある。テンプレートの境界の規則は「領域どうしは相手の `index.ts` からだけ」なので、`../account/schema.ts` を直接読むと lint で止まる。一方 AD-3 は「ほかの領域の表は読み書きしない」と言っており、表の定義を `index.ts` から出してよいかがはっきりしない。各領域の仕様が別々の抜け方（外部キーを付けない・schema を直接読む・SQL で手書き）を選ぶ恐れがある。
- **直し方**：AD-3 に「外部キーのためだけに、持ち主の領域は `index.ts` から表の定義を出してよい。ほかの領域はそれを `references()` にだけ使い、読み書きには使わない」と足す（lint の例外は作らない）。

#### M-4：バックアップと戻し方が「決めた／後回し／未決」のどれにもない

- **場所**：AD-8・AD-9・AD-10（運用）
- **問題**：交流会の当日の清算の記録と困りごとは、作り直せないデータ。Terraform の `google_sql_database_instance` は、書かなければ自動のバックアップが切れたまま作られる。また夜間（0時〜8時）は止めているので、既定のバックアップの時間帯（夜中）だと取られない。消してしまう事故（`terraform destroy`・DB の変更の誤り）への守りもない。
- **直し方**（Terraform に数行）：AD-9 か AD-10 に「Cloud SQL は毎日の自動バックアップを有効にし、時間帯は動いている昼（例：12時 JST）にする。保持は7日。`deletion_protection = true`。戻し方は Cloud SQL のバックアップからの戻しだけ（時点の戻しは使わない）」と足す。費用は数十円の大きさ。加えて、交流会のあとに主催者が CSV（FR-15）を手元に落とすのを、手作業の控えとして書いてもよい。

#### M-5：費用の上限と、超えたときの知らせがない

- **場所**：AD-8（費用）、PRD 5章「費用」
- **問題**：費用の守りは「ロードバランサ・最小の台数1を足さない」だけで、思わぬ費用（Cloud Run の台数の暴れ・Cloud SQL の止め忘れ）に気づく仕組みがない。また Cloud Run の最大の台数を決めていないので、混んだときに台数が増え、一番小さい Cloud SQL の接続の上限（数十本）を超えうる。
- **直し方**：AD-8 に「Cloud Run の最大の台数は 2〜3、pg の接続のプールは1台あたり数本（合計が Cloud SQL の上限を超えない）」と、AD-9 の Terraform で持つものに「請求の予算（例：月 1,500 円）と、50%・100% でのメールの知らせ（`google_billing_budget`）」を足す。どちらも無料で数行。

#### M-6：監視と知らせを「決める」か「後回し」と書く

- **場所**：AD-10（DB を叩く監視は作らない）、Consistency Conventions「ログ」
- **問題**：AD-10 は「DB を叩く監視を作らない」と、作らないものだけ決めていて、何で異常に気づくかは書いていない。この大きさなら「当日は主催者が一覧画面を見て気づく」で十分だが、それが決めたことなのか抜けなのかが読めない。
- **直し方**：最小なら Deferred に「監視：最初は置かない。当日は主催者が一覧画面とCloud Logging を見る。交流会のあとに、5xx のログからの知らせ（ログの指標＋メール。無料）を足す」と書く。余裕があれば、それを最初から Terraform に入れてもよい（DB を叩かないので AD-10 と矛盾しない）。

#### M-7：環境が本番の1つだけのとき、LINE ログインをどこで試すかが決まっていない

- **場所**：Deferred「ステージングの環境」、AD-4
- **問題**：ミニアプリの LINE ログインは https の決まった URL でしか動かないため、手元（`localhost`）では本物のログインが試せない。環境が本番1つなので、ログインの流れを最初に通すのは本番になる。各領域の仕様が、手元での確かめ方（トンネル・偽の LIFF・本番で直接）を別々に選ぶ恐れがある。
- **直し方**：H-1 の「テスト用のログイン」を手元の開発にも使うと決め、本物の LINE ログインは「本番で、主催者の LINE で通しで試す（11-23 までに1回）」と書く。ミニアプリのチャネルが開発用の版（内部の別の LIFF ID）を持つなら、それを手元の確かめ用に使う、という候補を未決の節に入れる。

#### M-8：会場の回線（1つの IP）で回数の制限に当たりうる

- **場所**：AD-8、PRD 5章「会場の電波」、テンプレートの `platform/rate-limit`
- **問題**：テンプレートの回数の制限は「書く操作。IP ごとに 60 秒で 100 回」（`RATE_LIMIT_MAX`）。会場の Wi-Fi に乗った参加者は全員が同じ IP に見えるので、アンケートの時間に数十人が一斉に送ると（ログイン＋回答の保存）、上限に当たりうる。また Cloud Run の前の中継の数（`TRUSTED_PROXY_HOPS`）を正しく設定しないと、全員が Google の中継の IP として1つに数えられる。どちらも当日の受付を止める。
- **直し方**：Consistency Conventions の「設定」か AD-8 に「本番は `TRUSTED_PROXY_HOPS=1`（Cloud Run の前の中継）。回数の制限の上限は、交流会の人数を見て 300 回／分などに上げる（外さない。staging・production では外せない決まりがある）」と書く。

#### M-9：1つのコンテナで画面を返すときの守りの見出し（CSP）と、LINE の宛先

- **場所**：AD-8（1つのコンテナが画面と `/api` を返す）
- **問題**：テンプレートの画面の CSP は `vite preview` にだけ付き、`connect-src 'self'`。「画面から外の源を読むときは、ここの CSP と本番の置き場所の見出しを一緒に直す」（vite.config.ts）と決まっている。AD-8 で Hono が画面のファイルを返すようになると、①画面の守りの見出しを誰がどこで付けるか、②LIFF の SDK が呼ぶ LINE の宛先を `connect-src` などにどう足すか、が決まっていない。最初にログインを作る仕様と、画面を返す仕組みを作る仕様（インフラ）で別々に直してずれる恐れがある。
- **直し方**：AD-8 に「画面のファイルを返す道は組み立て（`app.ts`）に1つだけ置き、vite.config.ts と同じ守りの見出しを1か所の定数から付ける。LINE の宛先の許可は、その定数に1度だけ足す」と書く。

#### M-10：後で LINE のチャネルを足すと、同じ人が別の account になりうる

- **場所**：Deferred「PC で管理の画面を開くときのログイン」、AD-4（`client_id`＝チャネル ID）
- **問題**：後回しの代わりとして「LINE ログインの Web の流れを account に足す」とあるが、LINE のユーザー ID（`sub`）は **プロバイダーごと** に変わる。別のプロバイダーのチャネルを作ると、同じ人が別の `sub` になり、AD-2 が止めたい「同じ人が別人になる」が起きる。また AD-4 は `client_id` を1つのチャネル ID と書いており、2つ目のチャネルの ID トークンの確かめ方がずれる。
- **直し方**：AD-4 に「LINE のチャネルは、すべて同じプロバイダーの下に作る。確かめる `client_id` は設定の並び（`LINE_CHANNEL_IDS`）で持つ」と1行足す。これで後回しのままでも、ほかの領域はぶれない。

- **直し方**：AD-11 に「交流会までは `main` のマージで本番に出す（`develop`→`main` のリリースの PR を、まとまりごとに出す）。`develop` のマージでは何も出さない（ステージングを足したら出す）。文書・仕様だけの変更では出さない（`paths` で絞る）」のように決め、同じ PR で development-flow.md 5章を直す（決まりは `docs/rules/` に置く、という CLAUDE.md の決まり）。DB の変更・API・画面は1つのコンテナなので、「DB の変更 → 新しい版」の2段で決まりの順を満たす、と書き添える。
