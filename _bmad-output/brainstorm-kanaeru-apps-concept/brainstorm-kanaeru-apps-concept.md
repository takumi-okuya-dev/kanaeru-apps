# 意図：IT交流会から自然にユーザーが生まれる受付アプリ

作成：2026-11-19（ブレインストーミングのセッションで決まったことのまとめ。`/bmad-product-brief`に渡す材料）

全部の記録は[.memlog.md](./.memlog.md)、出発点は[構想メモ](../concept-memo.md)。

## 1. 中心の意図

**結局は、ユーザーを自然に獲得できる仕組みが大事だった。** 個人開発の壁は初期ユーザー集め。だから「需要収集アプリで集める」のをやめ、交流会にすでにある儀式（受付・名札づくり・自己紹介）の副産物として登録と需要が生まれる形にする。最初の利用者は主催者自身。毎回の受付で使うので「使われない」が起きない。受付で作るアカウントは最初からスイート共通のアカウントにし、参加者は0日目からスイートの利用者になる。

## 3. 最初の1本：受付と需要収集がセットのアプリ

**誰のため**

- 主催者自身（最初の一人）：いちばん面倒なのは受付と参加費の集金。その受付を楽にする。
- 参加者：非エンジニアのビジネス層（個人）。ペルソナの仮説は「AI活用を任された・進めたい、非エンジニアの年長のビジネス層（管理職・経営層かもしれない）」。きっかけは、相談に来た非エンジニアの年長のビジネス層の人の悩み（非エンジニアがAIエージェントをうまく活用できていない）。その人の用事は「自分で自動化を作れるようになりたい」。組織単位のAI活用にも悩んでいた。

**流れ**

| 場面 | すること |
|---|---|
| 入口 | QR → LINEログイン → 参加費（支払い方法の記録）→ 自己紹介カード（名札＋いま困っていること）→ オープンチャット案内 |
| 最中 | 名札のQRで名刺交換・「私も！」・席替え |
| あと | 困りごとの行方を追う（投稿→検討中→開発中→完成）・本気度の階段・次回の交流会で何をアプリ化するか発表 |
| 完成 | 手を挙げた人にLINEで約束を果たす連絡 |

**自然にユーザーが生まれる理由**

- 登録は名札づくり・受付という参加者全員がする儀式の中にある。需要は自己紹介の「いま困っていること」欄から生まれる。
- 今すぐ登録する理由がある：会場の人のカードが見られる・自分の困りごとの行方を追える（追うにはアカウントが要る）。
- 主催者が毎回使うので、自分で磨き続けられる。
- 次回の発表が、次の交流会に来る理由になる（交流会と交流会をつなぐ連続ドラマ）。
- Googleフォームのアンケートでも需要は集まるが、登録＝ユーザーにならない。だからアプリにする。

## 4. 次の交流会までの範囲（MoSCoW）

| 区分 | 範囲 |
|---|---|
| Must | QR→LINEログイン登録・受付チェックイン・申し込みの媒体と知ったきっかけの記録・支払い方法（PayPay／現金）と方法ごとの合計・自己紹介カード（名札＋いま困っていること）・本気度②③・主催者の一覧画面 |
| Should | オープンチャット案内・私も！・困りごとの行方の状態表示 |
| Could | 名札QRの名刺交換・マッチング席替え |
| Won't | アプリ内のオンライン決済・次回の発表（口頭）・完成時の連絡（公式LINEから手で）・創業メンバー特典（登録日だけ残す）・組織版 |

## 5. 守る方針

- 交流会では気軽さを最優先にする。お金の約束（先払い・予約課金）は持ち込まない。
- まずは無料。目的は自分の受付業務を楽にすること。
- 作るものは本気度の階段で決める。多数決ではなく、一人の深い困りごとから作る。
- 困りごとへの答えはアプリに限らない（勉強会・テンプレート・相談）。AI活用勉強会で何度も出る同じ質問がアプリ化の候補になる（勉強会がアプリのふるい）。
- 公式LINEは一方的な告知に使わず、手を挙げた人への約束を果たす連絡に絞る。
- テスターと早期登録者には、有料化したときに創業メンバー特典（無料期間・ずっと割引・勉強会の優先案内）を返す。今は登録日だけ残す。
- 運用費（GCPなどプロダクトを動かす費用）はサービスの無料枠でゼロに近づける。GCPとTerraformを使う。AIの利用料（開発の自律化）は別枠で考える。
- 言語は TypeScript。

## 6. 既存サービスとの違い

匿名のアイデアではなく、会って名札を交わした人の困りごとを集める。登録は交流会の受付そのもので起きる。

## 7. 未決の論点（ブリーフで決めること）

- **フェーズ3で誰が払うか**：個人のサブスク・組織の契約・主催者向けの決済手数料など。
- **スイートの軸**：候補は「非エンジニアがAIを仕事に使うためのスイート」と「交流会を開く人のためのスイート」。2層構造（玄関＝交流会を開く人の道具、中身＝参加者の困りごとから生まれるアプリ）の可能性もある。
- **組織版の需要**：社員が「この作業が面倒」を投稿し、AI化の候補を見える化する社内版。反応はまだ聞けていない。
- **申し込みの媒体と名簿の取り込み**：いまどの媒体（connpass・Peatix・SNSなど）を使っているかで取り込み方が変わる。
- **ペルソナ仮説の確認**：次の交流会で確かめる。
- **要確認の事項**：公式LINEの無料枠の通数・DBなどの無料枠。

## 8. 主なリスクと対策

| 失敗の未来 | 対策 |
|---|---|
| アプリが使われず続かない | 主催者自身が毎回の受付で使う。登録を受付・名札づくりに埋め込む。次回の発表で交流会どうしをつなぐ |
| 困りごとがバラバラでアプリにできない | 一人の深い困りごとから作り、あとから「私も」を集める。スイートの軸をペルソナにする。答えの形をアプリに限らない |
| 開発費用（運用費・AIエージェントの値上がり）で続かない | 運用費は無料枠とGCPで抑え、AIの利用料は別枠で見る。LINEは手を挙げた人への個別の連絡に絞る。アプリ内のオンライン決済は持たない |
| 有料会員につなげられない | 0日目から共通アカウントにする。登録日を残し、有料化のとき創業メンバー特典で返す。買い手はブリーフで決める |
| アプリが増えるほど保守に追われ、新作が止まる | 未決。自律化で減るのは作る時間だけで、運用・問い合わせ・交流会の当日の時間は残る |
| 交流会の顔ぶれが固定し、需要が枯れる | 次回の発表・投票で交流会に来る理由をつくる |
