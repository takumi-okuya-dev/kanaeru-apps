# 開発の流れの決まり（ブランチ・PR・レビュー・CI・マージ）

**対象**：このリポジトリで作業するすべての人とAI（Claude Code・Codex）。入口は[CLAUDE.md](../../CLAUDE.md)。

ステージングと本番を壊さずに、小さく出し続けるための決まり。

## 1. ブランチ

`main`（本番）／`develop`（ステージング）／`feature/*`（追加実装）の3段構成（[Constitution](../../.specify/memory/constitution.md)「開発ワークフロー」）。

| ブランチ | 何の場所か | マージすると |
|---|---|---|
| `main` | 本番 | ステージングに同じ中身を出し、承認のあと本番に出る（5章） |
| `develop` | ステージング（**既定のブランチ**） | ステージングに出る |
| `feature/*`・`fix/*`・`docs/*` | 開発（手元） | — |
| `hotfix/*` | 本番の重大なバグの急ぎの直し（`main` から切る） | — |

- ふだんのPRは`feature/*`→`develop`に向ける。ブランチは`develop`の最新から切る（`git switch -c <ブランチ> origin/develop`）。名前の付け方は[仕様と名前の決まり](./specs.md)。
- リリースは`develop`→`main`のPR（タイトルは「リリース：…」）。
- 本番の重大なバグの急ぎの直しは、`main`から`hotfix/*`を切り、`main`へ PR を出す（5章の①）。マージしたあと、`main`を`develop`に取り込み直す（`git log --oneline main ^develop`が空になること）。
- `main`・`develop`への直接のpushは禁止（PR必須。GitHubのブランチの保護で止める）。
- マージ済みのブランチは、手元とGitHubの両方から消す。

> 本番を出す前（デプロイ先がまだない間）は、`develop`だけで進めてよい。本番を立ち上げるときに`main`を切る。

## 2. PRとレビュー

- **PRは小さく**。1つのリリースに混ざる変更が少ないほど、壊れたときに原因を探しやすく、戻しやすい。DBの変更のあるPRは、とくに小さく切って先に入れる（[並行開発の決まり](./parallel-development.md) 4）。
- PRの説明の「チェック」の欄（[.github/pull_request_template.md](../../.github/pull_request_template.md)）を埋める。どう確かめたか（流したテストと結果）を書く。
- **レビューは「セルフレビュー → 別のAIのレビュー」の順**（別のAIが使えないときは、セルフレビューだけでよい）。
  1. PRは**下書き（draft）**で出す（`gh pr create --draft`）。
  2. セルフレビュー（Claude Codeの`/code-review`など）をして、指摘を直してpushする。
  3. **「Ready for review」**にする（`gh pr ready <番号>`）。自動でレビューするAI（Codexなど）は、ここから動かす。
- 見つけたバグが今のPRの目的と別なら、別のPRで直す。
- **セキュリティの確かめは、決まった時に流す**。AIの確かめは、変更の分は`/security-review`、まとまった点検は`security-audit`スキルを使う。手で確かめる一覧はまだない（作ったら`docs/security/`に置き、[文書の一覧](../README.md)に足す）。
  - リリースのPRの前に、AIのセキュリティの確かめを流し、結果をPRの説明に貼る。
  - 月に1回、AIの確かめと、手で確かめる一覧を流す。未対応があれば、直すPRかバックログに入れる。
  - ファイルの受け取り・外からの知らせ（Webhook）・決済・中でAIを呼ぶ・パスワードのログイン・MCPを入れる仕様は、`/speckit-plan`のときに確かめを流し、対応表を直す作業をtasksに入れる。

## 3. CI

- **CIは、PRにラベル「run-ci」を付けたときだけ流れる形にする**（付け直すと、もう一度流れる）。GitHubのCIは量に限りがあるので、節約する。
- **`run-ci`を付けるのは、次のPRだけ**。
  - DBの変更のあるPRなど、慎重に入れるもの。
  - 手元で確かめられないもの（`.github/workflows/`・デプロイの流れ）。
  - リリースのPR（`develop`→`main`）。必ず流す。
  - ユーザーが頼んだとき。
- **ほかのコードのPR**は、手元で全部の確かめ（型チェック・lint・全テスト、E2Eは関わるもの）を流して結果をPRに書き、セルフレビューのあとマージする。
- 文書（`docs/`・`specs/`・`*.md`）・`.specify/`・スキルの本文だけのPRは、CIを流さない。
- リリースのPR（`develop`→`main`）は、ラベルがなくてもCIが流れる形にする。
- 週に1回、`develop`の秘密の値（過去のコミットを含む）と依存の脆弱性だけを確かめる形にする。落ちたら、直すPRを出す。
- CIが流れないとき（GitHubの支払い・使える量の上限など、コードと関係のない理由）は、ラベルを付け直さず、手元の確かめの結果と理由をPRに書き、ユーザーに伝える。

## 4. マージ

- **マージしてよいかは、ユーザーが決める**（最終の承認はユーザー）。AIは、確かめずにPRまで進めてよいが、コミット・push・PRのマージは、ユーザーに頼まれたときだけ行う。
- マージは merge commit（`gh pr merge --merge`）。積み重ねたPR（あるPRの上に作ったPR）は、下から順にマージし、上のPRの向き先を`develop`に直してからマージする。
- マージの前に`develop`を取り込み、ぶつかりがないことを確かめる（[並行開発の決まり](./parallel-development.md) 5）。

## 5. デプロイ

- デプロイは、マージを合図に自動で行う（`.github/workflows/deploy.yml`。2026-11-22 から。core-018・core-019）。
  - `develop` のマージ：ステージング（`kanaeru-stg`）に出す。
  - `main` のマージ：先にステージングに同じ中身を出し、**ユーザーがステージングで確かめて承認したら**（GitHub の環境 `production` の承認者）本番（`kanaeru`）に出す。出さないときは Reject する（放っておくと、同じブランチの次のデプロイが始まらない）。
  - 順番は **DBの変更 → 新しい版**（画面と API は1つのコンテナ）。1つでも失敗したらそこで止める。
  - デプロイは DB が動いている昼に行う（DB は夜間〈0時〜8時〉に止まる。デプロイの流れは、日本時間の8時15分〜23時に始まったときだけ進む）。夜に緊急で出すときだけ、下の①の手順で DB を一時的に起こす。
  - ステージングと本番は同じ DB のサーバーを使うので、ステージングで本物の知らせを送らない・本番の Threads のアカウントをつながない（[infra/README.md](../../infra/README.md) 11章）。
- **本番に出す3つのモード**（どれも本番に出るのは `main` の中身だけ。やり方・手で打つ手順・うまくいかないときは[本番に出す手順](../release-guide.md)）：

  | モード | いつ使うか | 流れ |
  |---|---|---|
  | ① 緊急 | 本番に重大なバグがあるとき | `main` から `hotfix/*` を切る → 手元で確かめる → `main` へ PR（ラベル `run-ci`）→ マージ → ステージングで確かめて承認 → 本番。夜（0時10分〜7時45分）は、Actions の `deploy` を `main` で手で流し、`wake_db` を入にする（DB を一時的に起こし、`keep_awake_minutes` の分〈15〜90。既定60〉のあと止め直す。その間に確かめ・承認・本番のデプロイを済ませる）。直したあと `main` を `develop` に取り込み直す |
  | ② 週ごと | 軽い直し・バグの直し（ふだん） | 直しは `develop` にたまり、マージのたびにステージングに出る。**毎週水曜の昼**に、`develop`→`main` のリリースの PR（タイトルは「リリース：…」・ラベル `run-ci`）をマージ → ステージングで確かめて承認 → 本番。急ぐものは①にする |
  | ③ 新しいアプリ | 新しいアプリを出すとき | コードは②の週ごとのリリースで本番にも入る。本番のアプリの台帳（設定 → アプリの台帳）では公開しない（行がなければ既定で「運営者だけ」）。ステージングで1週間ほどユーザーが試す。問題がなければ、本番の台帳で公開に切り替える（デプロイは要らない）。Terraform のアプリのスイッチ（`threads_enabled` など）も環境ごとに入・切する |
- **出すものが変わらない変更だけなら動かさない**。文書・仕様・`.specify/`・AIのスキルだけを変えたマージでは、デプロイを飛ばす。
- マージしたら、デプロイが成功したかを確かめる。

## 6. この文書の更新

- 決まりを変えたら、同じPRでこの文書を直す。AIのメモリーだけに書かない（ほかのセッションから読めないため）。
