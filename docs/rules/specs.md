# 仕様と名前の決まり（仕様のフォルダ・番号・ブランチ・コミット）

**対象**：spec-kitで機能を作るすべての人とAI。入口は[CLAUDE.md](../../CLAUDE.md)。スキルを使う順番は[AIスキルの使い方](../ai-skills.md)。

## 1. 仕様の役目

- 仕様（`specs/<領域>/NNN-…/`の`spec.md`・`plan.md`・`tasks.md`と、必要なら`research.md`・`data-model.md`・`contracts/`・`quickstart.md`）は、**その変更で何をなぜ作るか**の依頼書。
- `develop`に入ったあとは、そのときの記録として残し、**書き換えない**。直すのは`spec.md`の`Status`（入った日と、残りの確かめ）と、`tasks.md`の印だけ。あとで変えたくなったら、新しい仕様を作る。
- **今のシステムがどうなっているか**は、コードと「今の形」の文書（[docs/README.md](../README.md) 2章）が正本。コードを変えたPRで、同じPRのうちに直す。
- 仕様の中で決まりを作らない。セッションをまたいで守る決まりができたら、この`docs/rules/`に書く。

## 2. フォルダと番号

機能を領域（アプリ・モジュール）ごとに並行して作れるよう、仕様のフォルダと番号は領域ごとに分ける。

- 新しい仕様は`specs/<領域>/NNN-<短い名前>/`に置く。
- どの領域にも属さない共通のもの（土台・CI・開発の決まりなど）は`core`。共通と領域の両方を変えるときは、主に変える方に置く。迷ったら`core`。
- 番号はフォルダごとに`001`から振る。ブランチを切る前に、`develop`と作業中のブランチの`specs/<領域>/`の最大の番号を確かめ、その次を使う。
- `specs/`の直下には新しい仕様を作らない。
- `/speckit-specify`では、出し先（`SPECIFY_FEATURE_DIRECTORY=specs/<領域>/NNN-<短い名前>`）を毎回はっきり指定する。spec-kitの自動の番号は`specs/`の直下しか見ないため。スキルの本文（`.claude/skills/speckit-specify/SKILL.md`）にも、この決まりを書いてある。

領域の一覧（領域を足したら、ここに1行足す）：

| 領域のID | 何か |
|---|---|
| `core` | 共通（どの領域にも属さないもの） |
| `account` | アカウント・セッション・LINE ログイン・今の利用者（構成の決めごと AD-2・AD-4・AD-12） |
| `event` | 交流会・要約・QR・受付係と招待・アンケートの開閉・権限（AD-5・AD-14） |
| `reception` | チェックイン・合計・内訳・参加者の書き出し（AD-6・AD-7） |
| `survey` | アンケートの回答・困りごとの一覧と書き出し（AD-13） |
| `booking` | 受付アプリの予約：交流会ごとの予約の設定・名簿（申込み）・自前の申込み・定員とキャンセル待ち・案内の同意・LINE 公式アカウントの設定と紐づけ・知らせ（AD-23・AD-24） |
| `suite` | スイートの共通：アプリの台帳（公開の状態）・見えるか（`isAppVisible`・`requireApp`）・すべてのアプリと設定の画面（AD-15・AD-16） |
| `threads` | Threads の運用（運用アカウント・戦略・プロンプト・投稿の案・承認・Threads への接続と自動投稿・反応の分析・宣伝とリサーチ・操作の記録。めぐるから移したアプリ。AD-15・AD-19・AD-20） |
| `match` | 試合表アプリ：試合表（名簿・組み合わせ・進み具合）・組織に入れる・前に入れたレベル・QR の受付・見るだけのページ（AD-25〜AD-30） |
| `person` | 人物メモ：人のメモ・会った場・人と会った場の組・検索・書き出し（自分だけが見られる。AD-31） |

## 3. ブランチとコミットの名前

- ブランチは`feature/<領域>-NNN-<短い名前>`（1つの仕様を何回かのPRに分けるときは`feature/<領域>-NNN-pr2-…`のように足す）。仕様のない直しは`fix/<領域>-…`、本番の重大なバグの急ぎの直し（`main` から切る）は`hotfix/<領域>-…`、文書だけは`docs/…`。
- コミットの頭は`feat(<領域>-NNN)`・`fix(<領域>)`・`docs(<領域>)`・`test(…)`・`refactor(…)`のように、種類と領域の名前（と番号）で呼ぶ（例：`feat(core-001)`）。
- コミットの本文とPRは日本語で書く。

## 4. この文書の更新

- 決まりを変えたら、同じPRでこの文書を直す。
