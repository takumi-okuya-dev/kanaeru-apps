# 文書の決まり（何をどこに書くか・何を作らないか）

**対象**：文書を書く・直すすべての人とAI。入口は[CLAUDE.md](../../CLAUDE.md)。文書の一覧は[docs/README.md](../README.md)。

アジャイル（機能ごとに小さく作って出す）と仕様駆動（spec-kit）で進めるので、文書は**必要最小限**にする。作ってよいかの目安は、次の3つのどれかに当たるか。

1. **認識合わせ**：ユーザー・ほかのセッション・外の人と、同じことを前提にできる。
2. **途中から入った人のため**：新しいセッションや人が、コードを全部読まずに全体をつかめる。
3. **開発を速くする**：毎回同じことを調べ直さずに済む。

どれにも当たらないもの、コードを読めば分かるもの、直し続けるのが重いものは作らない。

## 1. 文書の種類と置き場所

| 種類 | 何を書くか | 置き場所 | いつ直すか |
|---|---|---|---|
| ⓪ 構想 | プロダクトの構想・ブリーフ・PRD・調べもの | `_bmad-output/` | 構想を練り直したとき。実装が始まったら、原則はConstitutionへ、範囲はPRDを正本にする |
| ① 守る原則 | 変えない約束 | [Constitution](../../.specify/memory/constitution.md) | 原則を変えるときだけ（版を上げる） |
| ② AIが守る決まり | 作業のしかた | [CLAUDE.md](../../CLAUDE.md)・`docs/rules/` | 決まりを変えたら同じPRで |
| ③ 機能ごとの仕様 | その変更で何をなぜ作るか（ユーザーストーリー・受け入れの条件・計画・作業の一覧・APIと画面の取り決め・確かめの手順） | `specs/<領域>/NNN-…/` | **入ったら書き換えない**（[仕様と名前の決まり](./specs.md) 1） |
| ④ 今の形 | 今のシステムがどうなっているか（構成図・モジュールの境界・領域ごとの表と入口・画面の約束） | `docs/`（[docs/README.md](../README.md) 2章） | コードを変えたら同じPRで |
| UI デザインの既定 | 見た目（DESIGN.md）と振る舞い（EXPERIENCE.md）の既定。SmartHR Design System を土台にしたもの | [docs/design/](../design/README.md) | テンプレートの既定を変えるとき（プロダクトの見た目は `_bmad-output/` の DESIGN.md・EXPERIENCE.md に書く） |
| 学び（study） | 初めて使う技術の解説（このプロジェクトでの使い方に絞る） | `docs/study/` | 使い方が変わったとき・間違いに気づいたとき |
| 技術選定の候補 | 層ごとの技術の候補と、選ぶ目安（テンプレートの既定） | [docs/tech-selection.md](../tech-selection.md) | 候補を比べ直したとき |
| ⑤ 使う人・動かす人向け | 使い方・立ち上げ方・出し方・費用・報告 | README・`docs/`（[docs/README.md](../README.md) 3・4章） | 手順や中身が変わったら |
| 記録 | 決めたことの経緯・バックログ | [決めたことの記録](../decisions.md)・[バックログ](../backlog.md) | 決めたとき・アイデアが出たとき |

- **決まりは②だけに置く**。ほかの文書に「〜しなければならない」を書かない。要るときは②へのリンクにする。
- **④には経緯を書かない**。「いつ決めたか」「前はこうだった」は[決めたことの記録](../decisions.md)へ。④は「今はこう」だけを書く。細部がどの仕様にあるかを示す番号の参照（例：「（core-003）」）は書いてよい。
- **学びの文書は考え方の説明**で、今のシステムの正本（④）でも、決まりの正本（②）でもない。今の形や決まりを書きたくなったら、④や②に書いて、学びの文書からはリンクする。
- **ユーザーが初めて使う技術を入れるときは、学びの文書を足す**（ユーザーの学びと、ノウハウを残すため）。仕様や計画で新しい技術が出たら、その技術の学びの文書を、機能のPRとは別の小さな文書のPRで足す。公式の文書で確かめ、確かめきれないことは（要確認）と書く。
- **同じことを2つの文書に書かない**。書くなら片方を正本にして、もう片方はリンクと1行の要約だけにする（[docs/README.md](../README.md)の「正本」の列）。

## 2. 作らない文書

次は作らない（必要が見えたら、ここを直してから作る）。

| 作らないもの | 代わりに使うもの |
|---|---|
| 詳細設計書・技術仕様書 | コードとテスト、機能ごとの`plan.md`・`data-model.md`・`contracts/`。コードとずれやすく、直すのが重いため |
| スプリント計画書 | 機能ごとの`tasks.md`。1人とAIで機能単位に回しているため |
| 振り返りの記録 | 進め方を変えたら`docs/rules/`と[決めたことの記録](../decisions.md)に書く |
| ER図・API仕様書（全体） | 領域の地図`docs/apps/<領域>.md`とDBの定義、各仕様の`contracts/` |
| テスト仕様書 | 自動のテストと、各仕様の`quickstart.md`（手で確かめる手順） |
| 画面仕様書（全体） | UIの全体設計（作ったら④に足す）と、各仕様の`contracts/` |

## 3. 書き方

- 冒頭に、作った日・直した日（と何を直したか）を書く。古いまま残っていても、いつの内容か分かるように。
- 図はMermaidで書く（GitHubでもそのまま表示される）。ただし、置き場所（クラウド）の構成図は、各社の公式のアイコン・ロゴを使った SVG（`docs/images/`）にしてよい（箱の入れ子と線の位置を決めて描くため）。出典を図の中に書く。ほかの会社のロゴは、その会社の配る公式のものを、その会社のブランドの決まりどおりに（形や色を変えずに）使う。構成を変えたら、同じ PR で図も直す。
- 外の人にも見せる前提で書く。アカウントのID・秘密の値・本物の利用者のデータは書かない。
- 文書を足す・消す・役目を変えたときは、同じPRで[docs/README.md](../README.md)も直す。

## 4. この文書の更新

- 決まりを変えたら、同じPRでこの文書を直す。
