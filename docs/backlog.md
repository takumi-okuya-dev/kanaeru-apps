## A. スイートとして並行開発できる構成への見直し（2026-11-19）

受付アプリ（最初の版）を作り終えたら、`/bmad-architecture` の更新で[構成の決めごと](../_bmad-output/architecture-kanaeru/architecture-kanaeru.md)を見直す（主催者が決めた）。受付アプリの4つの領域（account・event・reception・survey）を作ったときに、並行して作るとぶつかる所が見えたため。

見直すこと：

1. **DB の変更の番号**：Drizzle の通し番号（`0003`…）と1つの `_journal.json` は、2つのアプリが同時に DB の変更を作るとぶつかる。番号を時刻の形にする設定（drizzle-kit の `prefix`）にするか、DB の変更の通し方を決める。
2. **「アプリ」という単位**：いまは「領域」だけ。受付アプリ＝event・reception・survey のように、どの領域がどのアプリのものか、画面の道の頭（例：`/apps/<アプリ>/…`）、スイートの中でアプリを切り替えるナビを決める（構成の決めごとの Deferred「スイートの画面の切り替え」）。
3. **共通の部品・手伝いは共通の PR で先に入れる**：受付の PR で共通の部品（選択肢のチップ）を足し、CSV とダウンロードの処理が reception と survey で二重になった。決まり（[並行開発の決まり](./rules/parallel-development.md)）の守り方を見直し、二重のものを `kernel`・`apps/web/src/lib`・`packages/ui` にまとめる。
4. **共通の文書を領域の PR で直さない**：各領域の PR が `docs/architecture.md` を直した。領域のことは `docs/apps/<領域>.md` だけに書く形を徹底する。
5. **使える権利（契約）の領域**：サブスクで売るときに「誰がどのアプリを使えるか」を判定する共通の領域。誰が払うかは、2026-11-19 に主催者が「**使いたい人が払う**。組織か個人かは区別しない」と決めた（ブリーフの未決を解いた。ブリーフは見直しのときに直す）。個人でも組織でも同じように契約できる形を、見直しのときに考える。
6. **アプリごとの公開の ON/OFF**：本番で、アプリごとに「止める／主催者だけ（試し）／公開」を切り替えられるようにする（主催者の要望）。切り替えのたびにデプロイしなくてよいよう、設定ファイルではなく管理の画面から変えられる形を第一候補にする。
7. **売り方の切り替え（スイート or 個別課金）**：スイートとは別に集客専用アプリを作る予定なので、アプリごとに「スイートに含める／個別に課金／両方」を切り替えられるようにする（主催者の要望）。6 と合わせて「アプリの台帳」（アプリごとの公開の状態と売り方）を持ち、「使えるか」は「公開されている」かつ「スイートの契約でそのアプリが含まれる、またはそのアプリの個別の契約がある」で1か所で判定する（5 の使える権利の領域）。集客専用アプリを kanaeru-apps の中の「アプリ」にするか、別のリポジトリにするかは未決。
8. **AIエージェントネイティブ**（2026-11-19 に主催者が決めた、スイート全体のコンセプト）：kanaeru のアプリは、次の2つを最初から前提に作る。
   - **3つの段階**（2026-11-19 に主催者が具体化）：
     1. **コピーして貼る**：アプリがプロンプトを組み立て、利用者がふだん使う AI のチャット（ChatGPT・Claude など）に貼る。回答をアプリに貼り戻して登録する。kanaeru に AI の費用はかからず、API キーもアカウントも要らない。外の AI に送るかは利用者が決める。
     2. **自分の API キー**：利用者が自分の API キーを登録すると、アプリが自動で AI に聞いて登録する。費用は利用者が持つ。
     3. **MCP の接続**：利用者の AI エージェントが、kanaeru の画面の操作・情報の取得・登録をする（下の「AI から使われる」）。
   - 3つの段階で押さえること：**1つの AI の作業（プロンプトの型・回答の形・回答の確かめ）を1か所で定義し、貼り付け・自動・MCP のツールのどれからも同じものを使う**（アプリごと・段階ごとにばらけないように）。貼り戻しの回答の形が崩れたときの見せ方と直し方。利用者の API キーは暗号化して持ち、ログに出さず、いつでも消せる。AI の会社ごとの違いは1か所で吸収する。kanaeru の AI の利用料はかからない（原則 V。`business-viability.md` のお金の計算の前提が変わる）。
   - **AI から使われる**：利用者がふだん使う AI エージェント（Claude・ChatGPT など）が、kanaeru のアプリの機能を直接使える。各アプリが AI 向けの窓口（MCP のサーバー。いまの OpenAPI の文書を土台にできる）を持つ。例：「次の交流会の参加者をまとめて」と AI に頼むと、kanaeru から読んで答える。汎用の AI に置きかえられる危うさ（`_bmad-output/research-app-ideas/business-viability.md`）を、逆に入口に変える狙い。
   - **AI が代わりに動く**：アプリの中の AI エージェントが、利用者の代わりに作業を進める（画面を操作するより「頼む」が主役）。例：集まった困りごとを AI が整理し、勉強会のテーマの案まで作る（B2 の「困りごとの整理」）。
   - **MCP の認証と LINE ログイン**（2026-11-19 に調べた）：LINE ログインは無料で、MCP の接続に LINE の料金はかからない。ただし MCP の接続する側（Claude・ChatGPT など）は、つなぐ先の認証の窓口に、接続する側を自動で登録できる仕組み（CIMD が推奨。DCR は任意で、あとの版で非推奨）を求める。LINE ログインは事前に登録したチャネルで使う形で、これに対応する情報は見つからなかった（要確認）。そこで、kanaeru が自分の認証の窓口（OAuth 2.1・CIMD・PKCE）を持ち、本人の確認だけを LINE ログイン（Web 用のチャネル。AD-2 のとおり同じプロバイダー）に任せる形にする。いまの設計への影響：Web 用の LINE ログインのチャネルを足す・トークン（範囲と期限つき）でのログインを足す（AD-12 を広げる）・アカウントと「ログインの手段」を別の表に分ける（LINE 以外の手段をあとから足せるように）・認証の窓口を自分で作るか外部のサービス（費用がかかる）を使うか。出典：[MCP の認証の決まり](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization)・[クライアントの登録](https://blog.modelcontextprotocol.io/posts/client_registration/)。
   - 見直しで決めること：AI からの窓口の認証（LINE のログインと、MCP の OAuth のつなぎ方）・AI に許す操作の範囲と確かめ（読むだけ／書く前に利用者が確かめる）・操作の記録・回数の制限。アプリの中の AI のモデルと費用（お金の計算に入れる）。**Constitution の原則 II との両立**：困りごとなど個人の情報を外の AI のサービスに送るときの同意と、送る量を最小にすること（原則の改定が要るかも見る）。
