# テンプレートの既定の振る舞い

SmartHR Design System の考え方を読み、このテンプレートの言葉で書き直したもの（写していない。出典は [README.md](./README.md) 3・4）。プロダクトの EXPERIENCE.md は、ここを引き継いで、プロダクトの画面と流れを足す。

## 1. 原則

1. **使う人の時間を取らない**。作り手の都合で手間を増やさない。いちばん多い操作を、いちばん少ない手数にする。
2. **出して終わりにしない**。使われ方を見て直し続ける。直しやすいように、型（部品・パターン・ことば）をそろえる。
3. **前後の事情まで見る**。目の前の画面だけで決めず、使う人の仕事の流れ・決まり（法や規約）・ほかの画面とのつながりを見て決める。
4. **ことばから作る**。画面を描く前に、扱うもの（概念）の名前と関係を決める。同じものは、どの画面でも同じことばで呼ぶ。

## 2. 言葉づかい（Voice and Tone）

- **短く、ふつうのことばで**。「〜することができます」は「〜できます」、「〜を行う」は「〜する」。
- **敬語を重ねない**。「ご確認いただけますようお願いいたします」ではなく「確認してください」。
- 助詞（を・に・が）を省かない。名詞を並べただけの文にしない。
- カタカナ語の前に、ふつうの日本語を考える。社内の呼び名・作り手の用語を画面に出さない。
- **同じものを、別のことばで呼ばない**（ことばの一覧は、プロダクトの EXPERIENCE.md に置く）。
- 操作のことば：新しく作るのは「追加」、写して作るのは「複製」、順を変えるのは「並べ替え」。「キャンセル」（始めた操作をやめる）・「取り消し」（済んだことを元に戻す）・「中断」（途中で止める）は意味で使い分ける。
- ボタンは、押すと何が起きるかを動詞で書く（「保存」「送信」「削除」）。「OK」「はい」だけにしない。
- **エラーの文は「何が起きたか・なぜか・どうすればよいか」を書く**。入りきらないときは「なぜか → どうすればよいか → 何が起きたか」の順に残す。使う人を責めることばにしない。
- 文の自動の確かめに、textlint と `textlint-rule-preset-smarthr`（MIT）を使ってよい。

## 3. 部品の型（Component Patterns）

| 場面 | 型 |
|---|---|
| 入力の誤り | 欄を離れたとき（と送ったとき）に、**その欄のそば**に出す。送ったときは、最初の誤りの欄にフォーカスを移す |
| 送った結果 | **押したボタンの近く**に出す。画面が切り替わるとき・近くに出せないときだけ、画面の上の知らせの帯を使う。すぐ消える小さな知らせ（トースト）を中心にしない |
| ダイアログ | ふだんの操作は画面の中で（重ねない）。**影響が大きい操作だけ**（消す・送る・元に戻せない）ダイアログか確かめの手順にする |
| 消す | 何が消えるか・元に戻せるかを書いて確かめる。ボタンは「削除」（危ないの色） |
| 一覧と表 | 並べ替えと絞りこみは表の上。まとめて操作するときは、選んだ数と操作を表の上に出す |
| 長い入力 | まとまりごとに見出しで分ける。長すぎるときだけ、手順（ウィザード）に分ける |
| 時間がかかる処理 | 押したらすぐ「受け付けた」を見せ、終わったら結果をその場所か知らせの帯で伝える |

## 4. 状態の型（State Patterns）

| 状態 | 見せ方 |
|---|---|
| 読みこみ中 | まとまりの場所に読みこみの印。画面全体を止めない |
| 空（まだ何もない） | なぜ空か・最初に何をすればよいかと、その操作を1つ |
| 値がない（表・項目の一覧） | 空欄にする。空欄だと意味がずれるときだけ「-」を `text-disabled` の色で |
| 失敗 | 2 のエラーの文と、やり直す操作（「もう一度」）。入れた値は消さない |
| 使えない操作 | 使えない理由が分かるようにする（隠すより、理由と一緒に使えない形で見せる） |

## 5. 操作（Interaction Primitives）

- すべての操作を、キーボードだけでできるようにする。フォーカスの順は見た目の順と同じ。フォーカスを閉じこめない（ダイアログの中だけは回し、閉じたら開いた所へ戻す）。
- フォーカスの輪は四辺とも見えるようにする（DESIGN.md の `shadow.focus`）。
- 押せる物は、指で押せる大きさ（目安 24px 以上、主の操作は 40px）。
- 動きは短く（0.3s 以内）、`prefers-reduced-motion` のときは動かさない。

## 6. アクセシビリティの下限（Accessibility Floor）

- **WCAG 2.2 AA を下限**にする（JIS X 8341-3 に合わせる）。
- 文字のコントラストは 4.5:1 以上（大きな文字は 3:1 以上）。入力欄のふち・アイコンなどの見分けに要るものは 3:1 以上。
- 色だけで伝えない（ことばかアイコンと一緒に）。
- 画像には代わりの文を、入力欄には見える名前（ラベル）を付ける。見出しの段を飛ばさない。
- 拡大 200%・幅 320px でも、横のスクロールなしで使える。
- 自動の確かめ（axe など）を通しのテストに入れ、手での確かめは SmartHR のアクセシビリティのガイドラインの一覧を参考にする。

## 7. 画面の幅（Responsive & Platform）

- パソコンを基準に作り、751px 以下を狭い画面として1列にする。
- 狭い画面では、主の操作を指の届く所（画面の下）に置いてよい。表は表の中だけで横に送るか、行をカードの形にする。
- 画面の向きを決め打ちしない。

## 8. 参考と、まねしないこと（Inspiration & Anti-patterns）

- 参考：SmartHR Design System（原則・ことば・パターン）。
- まねしない：SmartHR のブランドの色・ロゴ・イラスト・SmartHR と見間違える見た目。
- しない：トーストだけで結果を伝える・確かめのダイアログを何にでも出す・色だけの状態・作り手の用語の画面。
