# Research: 割引・紹介割（reception-002）

2026-11-19 作成。開発者が不在のため、AI が仮に決めたもの（【仮決め】）を含む。仮決めは、開発者が見直して変えてよい。開発者が決めたことは [spec.md](./spec.md) の Input。

## R1. 割引は event が持ち、消さずに「使うのをやめる」だけ【仮決め】

- **Decision**：表 `event_discount`（`id`・`event_id`・`name`・`amount`・`asks_referrer`・`archived_at`・`created_at`・`updated_at`）を event の領域に置く（AD-3）。`event_id` は `RESTRICT`。行は消さず、外すと `archived_at` を入れて新しいチェックインで選べなくする。チェックインは名前と額を写すので、外しても過去の記録は変わらない。
- **Rationale**：割引は交流会の設定（参加費の隣）なので event のもの。event は reception に依存できない（AD-3 の矢印）ので、割引が使われたかを event は知れない。だから「使われていなければ消す」は作れない。消さなければ、チェックインからの外部キーは `RESTRICT` のままで、履歴の行が宙に浮かない。
- **Alternatives**：消して `SET NULL`：写しは残るが、内訳で同じ割引をまとめる鍵が消える。reception に割引を持たせる：交流会の入力（A2）が2つの領域に割れる。

## R2. 割引は A2 のフォームの中で、交流会と一緒に保存する【仮決め】

- **Decision**：交流会の入力（`EventInput`）に `discounts`（任意の並び）を足す。作るときも直すときも、A2 の「割引」の節で行を足し・直し・外し、「作る」「保存」で交流会と同じ取引で保存する。並びの行に `id` があれば直す、なければ足す、使っている割引で並びにないものは使うのをやめる。`discounts` を送らなければ割引に触らない（前の版の画面・ほかの呼び手が割引を消さない）。
- **Rationale**：開発者の「交流会ごとに主催者が登録する」。参加費の隣で決めるものなので、同じ画面・同じボタンがわかりやすい。割引だけの窓口を足すより、窓口と画面の状態が少ない。

## R3. 割引の欄の決まり【仮決め】

- **Decision**：名前は前後の空白を除いて1〜30文字、額は1〜1,000,000円の整数（0円の割引は意味がない）、「紹介者の名前を聞く」は真偽（既定は聞かない）。1つの交流会に10まで。同じ交流会の並びで名前を重ねない（約束の zod で確かめ、2つ目の名前の欄のそばに誤り）。DB には `amount > 0` の CHECK だけ（名前の一意は、主催者1人が並び全部を送る形なので約束で足りる。DB の部分の一意の索引にすると、名前の入れ替えが1つの取引でぶつかる）。
- **Rationale**：チップに「紹介割（−1,000円）」と出すので、名前は短く。

## R4. チェックインに足す列と外部キー

- **Decision**：`checkin` に `discount_id`（uuid）・`discount_name`（text）・`discount_amount`（integer）・`referrer_name`（text）を、どれも空を許して足す。`(event_id, discount_id)` → `event_discount(event_id, id)` の複合の外部キー（`ON DELETE RESTRICT`）。そのため `event_discount` に `UNIQUE (event_id, id)`（`event_discount_event_id_id_unique`）を置く。CHECK：割引の3列はそろって空かそろって入っている・割引がなければ紹介者も空・`discount_amount >= 0`（`checkin_discount_check`・`checkin_discount_amount_check`）。
- **Rationale**：複合の外部キーで、別の交流会の割引を DB が指させない。足すのは表と空を許す列なので、前の版のアプリでも壊れない（coding.md 3。前の版の `INSERT` は4列とも空で、CHECK を満たす）。

## R5. 金額の決まり（AD-6 を広げる。開発者と合意）

- **Decision**：`decideAmount(paymentMethod, fee, discountAmount)` ＝ 無料なら0、ほかは `max(fee − (discountAmount ?? 0), 0)`。作るときは、その時の参加費と選んだ割引の今の額。直すとき：
  - 割引が変わった：新しい割引の今の名前と額を写し、その時の参加費で決め直す。
  - 割引は同じで支払い方法が変わった：**写した割引の額**と、その時の参加費で決め直す【仮決め】。
  - どちらも同じ：金額・写しを変えない。
- **Rationale**：「写した割引の額」を使うのは、あとで割引を直しても過去のチェックインに持ち込まないため（AD-6 の「写して持つ」と同じ考え）。参加費は AD-6 のとおりその時のもの。

## R6. 選べる割引【仮決め】

- **Decision**：新しいチェックイン（自分・手）と、直すときに割引を変えるときは、その交流会の使っている割引だけ。違えば 400 `DISCOUNT_UNAVAILABLE`（`fields` に `discountId`。画面は割引の設問のそばに出す）。割引を変えない直しは、使うのをやめた割引のままでも保存できる。直す枠のチップには、使っている割引に加えて、今の割引（写した名前と額）を出す。
- **Rationale**：受付の途中で主催者が割引を外しても、受付係の保存が止まらない。

## R7. 紹介者の名前（第三者の個人の情報）【仮決め】

- **Decision**：
  - 任意・前後の空白を除いて50文字まで・空なら記録しない。割引を選んだときだけ記録する（割引なしなら送っても空）。
  - 欄を出すのは、選んだ割引が「紹介者の名前を聞く」のとき（主催者の直す枠は、今の名前があれば印がなくても出す〈消せるように〉）。
  - **読めるのは主催者だけ**：一覧・手でのチェックイン・直すの答えの `referrerName` は、主催者のときだけ値、受付係には null。参加者の自分のチェックインには入れない。内訳と CSV は主催者だけの窓口。
  - **受付係が直すとき**：欄は空で出し、「入れると前の名前を置きかえます。空のままなら変えません」と添える。空なら `referrerName` を送らない。API は、送られなかったとき、割引が同じなら前の名前を残し、割引が変われば空にする。null か空の文字を送ると消す（主催者の枠が空にしたとき）。
  - ログに出さない（土台が本文をログに出さない。名前と同じ扱い）。
  - 紹介者の本人から消してほしいと頼まれたら、主催者が直す枠で空にする（自由な文字なので、アカウントの削除では探せない）。
- **Rationale**：Constitution II（最小限・主催者だけ）。受付係は当日の受付だけを手伝う人で、紹介の関係を知る要がない。受付係の空の保存で、主催者が読む名前が消えないようにする。

## R8. 内訳に足すもの【仮決め】

- **Decision**：`CheckinBreakdown` に `discounts`（使っている割引と、使われた割引ごとに `{ discountId, name, active, count, discountTotal }`。作った順。最後に割引なし `{ discountId: null, name: null, … }`）と `referrers`（紹介者ごとの `{ name, count }`。`normalizeCheckinName` でそろえて数え、多い順）。名前はその割引の今の名前（使うのをやめたものは `active: false`）。`discountTotal` は「割引の額の合計」＝ 無料でないチェックインの写した割引の額の和。
- **Rationale**：主催者が「紹介割を何人が使い、いくら割り引いたか」「だれがよく紹介してくれたか」を知るため。
- **Note**：割引の額が参加費より大きいとき（金額0円）は、実際に引いた額（その時の参加費）より大きく数える。参加費を写していないので正確には出せない。まれなので、言葉を「割引の額の合計」にしてそのまま数える。

## R9. CSV に足す列

- **Decision**：「金額」のあとに「割引」（名前の写し）・「割引の額」・「紹介者」。割引なしは空。式の差しこみの守りは今のまま（紹介者も利用者が入れた値）。

## R10. 画面

- **Decision**：
  - P1：支払い方法のあとに「割引」のチップ（「割引なし」が最初・既定。割引ごとに「紹介割（−1,000円）」）。割引の登録がなければ出さない。選んだ割引が聞くときだけ、チップの下に「紹介してくれた人の名前」（任意）。割引を変えると紹介者の欄は空にする。何をどう使うかの1文に「紹介してくれた人の名前」を足す。
  - A3：手でのチェックイン・直す枠も同じ欄（割引は event の `EventView.discounts` から）。一覧の支払い方法に割引の名前を添える（「PayPay・紹介割」）。主催者には直す枠に紹介者の名前。
  - A2：参加費の下に「割引」の節（行ごとに名前・額・「紹介者の名前を聞く」・「外す」、下に「割引を足す」）。「割引を直しても外しても、すでにあるチェックインの割引と金額は変わりません」を添える。
  - 合計のタブ：今の合計のカードはそのまま。主催者の内訳に「割引の内訳」（人数・割引の額の合計）と「紹介者」（人数）の表。
- **Rationale**：EXPERIENCE.md の「1つの画面で頼むことは1つ」「文字を打つのは名前を直すときだけ」を守り、紹介者の欄は聞く割引を選んだときだけ出す。

## R11. 要約に割引を足す（AD-5）

- **Decision**：`EventSummary` と `EventView` に `discounts`（使っている割引の `id・name・amount・asksReferrer`）を足す。AD-5 の「要約の中身」に割引を足す。
- **Rationale**：参加者の画面がチップを出すのに要る。割引の名前と額は参加者に見せてよい情報（会場の受付の掲示と同じ）。

## R12. プライバシーポリシーの下書き（別のブランチ。ここでは直さない）

- `origin/docs/legal-drafts` の `_bmad-output/legal/privacy-policy-draft.md` の「集める情報」に、次の2つを足す必要がある：
  - **紹介してくれた人の名前**（参加者が任意で入れる第三者の名前。主催者だけが読み、紹介割の確かめと御礼に使う）
  - **選んだ割引**（割引の名前と額。金額の記録に使う）
- そのブランチのセッションか開発者が直す。

## R13. 機能の印では止めない

- **Decision**：`DOMAIN_FEATURES` の印を足さない。割引を登録しなければ何も出ない。
- **Rationale**：止めたいときは、交流会の割引を外せばよい（設定の1行と同じ速さ）。
