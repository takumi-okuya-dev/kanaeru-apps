## User Scenarios & Testing *(mandatory)*

### User Story 1 - 参加者が受付QRからチェックインする (Priority: P1)

参加者は受付QRを読み、チェックインの画面（P1）で、交流会の要約（名前・日時・会場・参加費）を見る。名前の欄には前回のチェックインの名前（なければ LINE の表示名）が入っている。申し込みの媒体・知ったきっかけ・支払い方法をチップで選び、「チェックインする」を押す。画面は「チェックインしました」と交流会の名前のカードに変わり、紙の名札の案内が出る。

**Why this priority**: 受付そのもの（UJ-1・PRD 6.1 の1番目）。

**Independent Test**: ログインした人でチェックインの画面を開き、名前の初期値・選ばずに押したときの誤り・押したあとの済んだカードを確かめる。読み直すと「チェックイン済み」になり、記録が増えないことを確かめる。

**Acceptance Scenarios**:

1. **Given** 初めての参加者, **When** チェックインの画面を開く, **Then** 名前に LINE の表示名が入り、知ったきっかけは選ばれていない
2. **Given** 前にチェックインした参加者, **When** 別の交流会のチェックインの画面を開く, **Then** 名前に前回の名前、知ったきっかけに前回の答えが入り、申し込みの媒体と支払い方法は選ばれていない（A4）
3. **Given** 支払い方法を選んでいない, **When** 「チェックインする」, **Then** その設問のそばに「支払い方法を選んでください。」が出て、最初の誤りへ動く
4. **Given** 全部選んだ, **When** 「チェックインする」, **Then** 「チェックインしました」と交流会の名前、「受付で紙の名札に名前を書いて、お入りください」が出て、カードの見出しにフォーカスが移る
5. **Given** チェックイン済み, **When** 受付QRを読み直す, **Then** 入力の欄を出さずに「チェックイン済み」のカードが出て、記録は増えない（FR-5）
6. **Given** オープンチャットの URL がある, **When** 済んだ状態, **Then** 「コミュニティのオープンチャットに参加する」（下線つきのリンク）が出る（FR-17）
7. **Given** アンケートが開いている, **When** 済んだ状態, **Then** 主のボタン「アンケートに答える」（アンケートの画面へ）が出て、LINE グループの招待リンクがあれば「交流会のLINEグループに参加する」も出る（FR-9・FR-22）。閉じていれば、どちらも出ない
8. **Given** 交流会がない, **When** 開く, **Then** 「この交流会は見つかりません。受付の人に声をかけてください」

### User Story 2 - 主催者・受付係が一覧を見て、手でチェックインする (Priority: P1)

主催者と受付係は、一覧画面（A3）の参加者のタブで、名前・チェックインの時刻・申し込みの媒体・知ったきっかけ・支払い方法を見る。新しいチェックインは5秒以内に出る。「手でチェックイン」を押すとタブの中に欄が開き、名前と3つのチップを入れて「チェックインする」。行には「手でのチェックイン」と入れた人の名前が付く。

**Why this priority**: LINE を使わない人・電波の弱い人の受付（UJ-3・PRD 5章）。

**Independent Test**: 受付係で手でチェックインすると一覧と合計に入り、手の印と入れた人が付くこと、別の端末のチェックインが読み直しで出ることを確かめる。

**Acceptance Scenarios**:

1. **Given** 受付係, **When** 一覧画面を開く, **Then** その交流会のチェックインが新しい順に出る
2. **Given** 受付係, **When** 手でチェックインする, **Then** 一覧の行に「手でのチェックイン」と入れた人の名前が付き、合計に入る
3. **Given** 手でのチェックインと LINE のチェックインの名前が同じ（空白・全角半角の違いを除く）, **When** 一覧を見る, **Then** 両方の行に「同じ名前があります」が出る
4. **Given** 別の端末で新しいチェックイン, **When** 5秒待つ, **Then** 開き直さずに一覧に出る
5. **Given** 主催者でも受付係でもない人, **When** 一覧の窓口を呼ぶ, **Then** 403

### User Story 3 - 支払い方法を直し、取り消し、合計を見て清算する (Priority: P1)

主催者と受付係は、行を押して開く枠で、名前と3つのチップを直して「保存」し、または「取り消す」（「このチェックインを取り消します。アンケートの回答があれば一緒に消えます」を確かめる）。合計のタブには、PayPay・現金・無料（招待など）の人数と金額と全体の合計が出る。

**Why this priority**: 清算の手計算をなくす（UJ-4・SM-4）。

**Independent Test**: 支払い方法を PayPay から現金に直すと合計がすぐ変わり、無料にすると金額が0円になること、名前だけ直しても金額が変わらないこと、取り消すと一覧と合計から外れることを確かめる。

**Acceptance Scenarios**:

1. **Given** 参加費 1,000円・PayPay のチェックイン, **When** 支払い方法を現金に直す, **Then** PayPay が1人・1,000円減り、現金が1人・1,000円増える
2. **Given** 参加費を直したあとの交流会, **When** 既にあるチェックインの名前だけを直す, **Then** 金額は前のまま（AD-6）
3. **Given** 参加費を直したあとの交流会, **When** 支払い方法を直す, **Then** 金額は今の参加費（無料なら0円）
4. **Given** チェックイン, **When** 取り消す, **Then** 行が消え（DELETE）、一覧と合計から外れる
5. **Given** 同じ名前の印がある手でのチェックイン, **When** 枠を開く, **Then** 「LINEのほうを残し、手でのチェックインを取り消してまとめます」の1文が出る（AD-7）

### User Story 4 - 主催者が内訳を見て、参加者を CSV で書き出し、頼まれたら消す (Priority: P2)

主催者は、合計のタブの下で申し込みの媒体と知ったきっかけの人数の内訳を見る。書き出しと削除の画面（A5）で、参加者の一覧を CSV（UTF-8 の BOM つき）で書き出す。参加者に頼まれたら、その人を選んで消す（アカウントのある人はアカウントごと、手でのチェックインはそのチェックインを）。受付係には内訳・書き出し・削除を出さない。

**Why this priority**: PRD 6.1 の3番目（FR-13・FR-15・FR-16）。

**Independent Test**: 主催者で内訳の合計がチェックインの数と同じこと、CSV が BOM で始まり日本語の見出しを持つこと、受付係では 403 になることを確かめる。

**Acceptance Scenarios**:

1. **Given** 主催者, **When** 合計のタブを開く, **Then** 支払い方法の合計の下に、申し込みの媒体と知ったきっかけの選択肢ごとの人数が出て、それぞれの合計がチェックインの数と同じ
2. **Given** 受付係, **When** 合計のタブを開く, **Then** 内訳は出ない（窓口は 403）
3. **Given** 主催者, **When** 「参加者をCSVで書き出す」, **Then** BOM つきの CSV（名前・チェックインの時刻・申し込みの媒体・知ったきっかけ・支払い方法・金額・入れ方・入れた人）が落ちる
4. **Given** 主催者, **When** アカウントのある参加者を消す, **Then** 何が消えるか（アカウント・チェックイン・回答・ほかの交流会の分も）と元に戻せないことを確かめてから消え、一覧・合計・書き出しに出ない
5. **Given** 受付係, **When** 書き出しと削除の画面を開く, **Then** 「この画面は主催者だけが使えます」

### User Story 5 - survey が、チェックインと名前を reception から引く (Priority: P1)

survey は、回答を受けるときにその人のチェックインを（`findCheckin`）、困りごとの一覧の名前を（`listCheckins`・`getCheckin`）、reception の入口から引く。回答の行は `checkinTable` を外部キーで参照し、チェックインを取り消すと回答も消える（AD-7）。

**Why this priority**: 並行して作る survey-001 がすぐ使う。

**Independent Test**: 結合のテストで `findCheckin`・`getCheckin`・`listCheckins` が決めた形を返すことを確かめる。

### Edge Cases

- 同じ人が同時に2回チェックインを送っても、行は1つ（交流会と account の組の一意の制約。account がある行だけ）。2回目は「チェックイン済み」で返す。
- 手でのチェックインは何件でも作れる（account がない）。
- 直す・取り消す相手が、ほかの端末で取り消されていた：404（「このチェックインは見つかりません。…」）。一覧を読み直す。
- 別の交流会のチェックインの ID で直す・取り消す：404。
- 参加者本人のアカウントを消す：その人のチェックインも消える（`ON DELETE CASCADE`）。受付係のアカウントを消す：その人が手で入れたチェックインは残り、入れた人が空になる（`ON DELETE SET NULL`）。交流会は消せない（`RESTRICT`）。
- 5秒おきの読み直しが失敗：前の一覧と合計を出したまま「最新にできませんでした」。夜間の停止（503 `DB_UNAVAILABLE`）なら読み直しを止める。
- 参加費0円の交流会：PayPay・現金でも金額は0円。
- CSV の名前が `=`・`+`・`-`・`@` で始まる：Excel が式として読まないよう、先頭に `'` を付ける。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: reception の領域が `checkin`（交流会・account〈LINE のとき〉・入れた人〈手のとき〉・名前・申し込みの媒体・知ったきっかけ・支払い方法・金額〈円の整数・0以上〉・チェックインの時刻）の表を持つ。交流会は `RESTRICT`、account は `ON DELETE CASCADE`、入れた人は `ON DELETE SET NULL`。交流会と account の組は、account がある行で一意（AD-3・AD-7）。選択肢の列は `text` と CHECK。
- **FR-002**: ログインした人は、ある交流会に自分でチェックインできる（`POST /api/v1/events/{eventId}/checkins/me`）。すでにあれば記録を増やさず、すでにあるものを返す。
- **FR-003**: ログインした人は、その交流会の自分のチェックイン（なければ空）と、名前と知ったきっかけの初期値を読める（`GET /api/v1/events/{eventId}/checkins/me`）。名前の初期値は前回のチェックインの名前、なければ account の表示名。知ったきっかけは前回の答え、なければ空（AD-6・A4）。
- **FR-004**: 金額はチェックインを作るときと、支払い方法を直すときだけ決める：無料なら0円、ほかは event の `getEventSummary` のその時の参加費（AD-6）。ほかを直しても金額は変えない。
- **FR-005**: 主催者とその交流会の受付係は、一覧（`GET …/checkins`。同じ名前の印・手の印・入れた人の名前つき）を読み、手でチェックインし（`POST …/checkins`）、直し（`PUT …/checkins/{checkinId}`）、取り消せる（`DELETE …/checkins/{checkinId}`。行を消す）。権限は event の `requireEventRole` で要求のたびに確かめる（AD-5）。
- **FR-006**: 同じ名前の比べ方（前後の空白を除き、NFKC でそろえ、間の空白を消す）は reception の約束に1つ置き、API が一覧の行に印を付ける。
- **FR-007**: 主催者と受付係は、支払い方法ごとの人数と金額と全体の合計を読める（`GET …/checkins/totals`。金額は `checkin` の金額の和）。
- **FR-008**: 主催者だけが、申し込みの媒体と知ったきっかけの人数の内訳（`GET …/checkins/breakdown`）と、参加者の CSV（`GET …/checkins/export`。UTF-8 の BOM つき）を読める。受付係は 403。
- **FR-009**: 選択肢（申し込みの媒体：connpass・Peatix・直接・その他／知ったきっかけ：知人の紹介・SNS・connpass などの告知・その他／支払い方法：PayPay・現金・無料（招待など））は、英語の短い code と画面の言葉と並び順を reception の約束に置く。
- **FR-010**: reception の入口（`index.ts`）が survey に `findCheckin(db, eventId, accountId)`・`getCheckin(db, checkinId)`・`listCheckins(db, eventId)`・`checkinTable`（外部キーのためだけ）を出す。テストの手伝い `test/helpers/reception.ts` を置く。
- **FR-011**: 画面 P1（参加者の道。`SessionGate`）：要約 → 名前（初期値あり）→ 3つのチップ → 何をどう使うかの1文 → 「チェックインする」（1つの主のボタン）。済んだら、チェックインのカード・紙の名札の案内・開いていれば「アンケートに答える」（survey の参加者の道へ）・開いていて招待リンクがあれば LINE グループ・URL があればオープンチャット。友だち追加は出さない（FR-6）。
- **FR-012**: 画面 A3（`ADMIN_ROUTE_PATTERNS.eventReception`。主催者・受付係）：上に `EventAdminNav`。タブ「参加者」「合計」。5秒おきに読み直し、手でのチェックイン・直す・取り消しのあとはその場で読み直す。主催者には合計の下に内訳と、A5 への入口。
- **FR-013**: 画面 A5（`ADMIN_ROUTE_PATTERNS.eventData`。主催者だけ）：参加者の CSV の書き出し、参加者のデータを消す（アカウントのある人は account の `DELETE /api/v1/accounts/{accountId}`、手でのチェックインは取り消し。確かめの枠で何が消えるかを書く）。
- **FR-014**: チップは押せる高さ 44px 以上、選んだものは 2px の墨のふちとチェックの印（色だけにしない）。ラジオのまとまりとして読み上げ、矢印で移る。
- **FR-015**: 入力の形・エラーの code と日本語の文言は、約束の reception のフォルダに置く。

### Key Entities

- **チェックイン**：参加者がその交流会に来た記録。そのときの名前と金額を写して持つ。LINE のときは account、手のときは入れた人を持つ。
- **合計**：支払い方法ごとの人数と金額の和。
- **内訳**：申し込みの媒体・知ったきっかけの選択肢ごとの人数。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 全部の確かめ（`pnpm check`）が通る。
- **SC-002**: 参加者が試験用のログインでチェックインの画面を開き、選ぶだけで「チェックインしました」まで進むことが、E2E で両方の幅（1440px・375px）のアクセシビリティの違反0件で通る。
- **SC-003**: 受付係が手でチェックインし、支払い方法を直すと合計が変わることが、E2E で通る。
- **SC-004**: 金額の決まり・二重の防止・同じ名前の印・権限（受付係は内訳・CSV・削除が 403）・CASCADE と SET NULL が、本物の PostgreSQL の結合のテストで通る。

## Assumptions

- アンケートの画面（P2）と困りごとの画面・CSV・回答を代わりに入れる操作は survey-001 が作る。reception は「アンケートに答える」のリンク（`participantPaths.survey`）と、差しこみの場所を置く。
- 何をどう使うかの文とプライバシーポリシーの URL は、公開前に主催者が用意する（EXPERIENCE Open Questions 2）。この版は1文の仮の文を出し、リンクは置かない【仮決め R12】。
- 会場全体の電波が悪いときは紙の名簿で受け、あとで手でのチェックインとして入れる（A17）。この版に一括の取り込みはない。
- 機能の印では止めない（受付は交流会の要。止めたいときは受付QRを出さなければよい）。
