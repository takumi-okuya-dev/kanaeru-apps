# Research: 定期の仕事を1つの窓口にまとめる（core-017）

## R1. まとめ方：組み立ての共通の窓口と、領域の `scheduledJob`

- **今**：Threads（`/api/v1/threads/jobs/tick`・5分ごと・8〜23時台）と booking（`/api/v1/booking/jobs/tick`・10分ごと・9〜23時台）が、それぞれ Cloud Scheduler の仕事を持つ。DB の停止・起動と合わせて4つで、無料の3つを1つ超える（月0.10ドル）。
- **選んだ形**：組み立てに `POST /api/v1/jobs/tick` を1つ置き、領域は `index.ts` から `scheduledJob` を出す。組み立ては業務を知らず、領域の名前も書かない（`withdrawal`・`publicReadPaths` と同じ）。
- **選ばなかった形**：
  - Threads の窓口から booking の仕事を呼ぶ：領域が領域を呼ぶことになる（AD-3）。
  - Cloud Workflows で2つの窓口を順に呼ぶ：部品が増え、Terraform と権限が増える。
  - 呼ぶ間隔を延ばして仕事の数はそのまま：Scheduler の数は減らない。

## R2. 当たるかの判定：日本時間・5分の区切り

- Cloud Scheduler は `*/5 8-23 * * *`（日本時間）で呼ぶ。数秒遅れて届くことがあるので、届いた時刻の分を5分の区切りに切り下げ（10時10分03秒 → 10時10分）、`分 % everyMinutes === 0` と時間帯で決める。
- 間隔は5〜60の5の倍数だけ（窓口を呼ぶ間隔より細かい間隔は作れないため）。60を超える間隔（1日1回など）は、要るときに足す。
- 時刻は窓口に渡す `now`（既定は今の時刻）から作る。テストは時刻を差しかえる。

## R3. 動かし方：同時に動かし、失敗を分ける

- Cloud Run の1回の要求の上限は60秒（`infra/cloud_run.tf`）。今は領域ごとに60秒あるので、順に動かすと合わせて60秒を超えうる。当たる領域の仕事を `Promise.allSettled` で同時に動かす。DB の接続は1台5本で、領域の仕事はそれぞれ順に問い合わせるので足りる。
- 1つが投げても、ほかは最後まで動かす。答えは `200` で、その領域は `failed`。ログには領域の名前と誤りの名前だけを出す（本文・トークンを出さない）。
- 答えは領域ごとの `status`（`ran`・`skipped`〈時間外〉・`off`〈アプリが切〉・`failed`）と時間（ms）だけ。領域の仕事の数の結果はログに出す。

## R4. 領域の窓口と Cloud Scheduler の仕事の移し方

- この PR は共通だけ（仕組み・窓口・共通の Cloud Scheduler の仕事）。領域のフォルダには触らない（[並行開発の決まり](../../../docs/rules/parallel-development.md)）。
- 領域ごとに、`scheduledJob` を出し、その領域の Cloud Scheduler の仕事（`infra/threads.tf`・`infra/booking.tf`）を消す PR を出す。本番はまだ作っていないので、移す間に仕事が2回動く・動かない時間は出ない。
- 領域の `/jobs/tick` の窓口は、テストの手伝いと手元の確かめに使っているので、消すかはその領域が決める。
