## User Scenarios & Testing *(mandatory)*

### User Story 1 - 主催者が本番の置き場所を1回の手順で作れる (Priority: P1)

主催者（開発者）は、手で作るもの（プロジェクト・請求・state の置き場所）を最小にして、残りの本番の資源（コンテナの置き場所・DB・秘密・身分と権限・夜間の停止・予算・サービス）を、コードから同じ形で作り直せる。

**Why this priority**: 置き場所がないと、11/25 の交流会で受付を動かせない。手で作った資源が残ると、作り直せず費用も分からなくなる（AD-9）。

**Independent Test**: 空のプロジェクトで、手順書（infra/README.md）のとおりに進めると、資源が揃い、仮の画面が公開の URL で開く。手元では、資源の定義が書式と整合の確かめを通る。

**Acceptance Scenarios**:

1. **Given** プロジェクトと state の置き場所だけがある, **When** 手順書のとおりに作る, **Then** DB・サービス・夜間の停止・予算がすべて揃い、もう一度流しても差が出ない。
2. **Given** 作り終えた, **When** 定義の中を読む, **Then** DB のパスワードなどの秘密の値は、コード・リポジトリ・Terraform の state のどこにもない。
3. **Given** 作り終えた, **When** DB を消す操作を誤って流す, **Then** 3段の守りで止まる。

---

### User Story 2 - main のマージで、DB の変更 → 新しい版の順に自動で出る (Priority: P1)

主催者が `develop`→`main` のリリースの PR をマージすると、コンテナが作られ、同じコンテナで DB の変更が当たり、成功したときだけ新しい版が公開される。文書だけの変更では何も動かない。

**Why this priority**: 手元から本番の DB を直接直さない・古い表で新しいコードを動かさない（AD-11）。

**Independent Test**: リポジトリの変数を入れた状態で、main から手で流すと、DB の変更の job が成功してから新しい版が動き、動いているかの窓口が 200 を返す。

**Acceptance Scenarios**:

1. **Given** アプリのコードを変えたマージ, **When** main に入る, **Then** コンテナを作る → DB の変更 → 新しい版の順に進み、最後に動いているかを確かめる。
2. **Given** DB の変更が失敗する, **When** デプロイが進む, **Then** 新しい版は出ず、前の版が動き続ける。
3. **Given** 文書・仕様・infra/ だけを変えたマージ, **When** main に入る, **Then** デプロイは動かない。
4. **Given** 日本時間の0時〜8時, **When** デプロイが始まる, **Then** すぐに分かりやすい理由で止まる（手で流すときだけ、確かめを飛ばせる）。
5. **Given** main 以外のブランチ・ほかのリポジトリ, **When** GCP に入ろうとする, **Then** 入れない。

---

### User Story 3 - 費用を守る（夜間の停止と予算の知らせ） (Priority: P2)

DB は毎日0時に止まり8時に動く。交流会が0時を越える日は、主催者がその日の停止だけを止められ、コードを当て直しても元に戻らない。月の費用が予算の50%・100%に届くとメールが来る。

**Why this priority**: 運用費の目標は月2,000円以内（Constitution V）。費用の大半は DB。

**Independent Test**: Scheduler の仕事を手で動かすと DB が止まる・動く。予算が作られ、宛先が請求先アカウントの管理者になっている。

**Acceptance Scenarios**:

1. **Given** 0時, **When** 停止の仕事が動く, **Then** DB が止まり、次の作り直しの手順で動き出さない。
2. **Given** 主催者が停止の仕事を一時停止した, **When** 作り直しの手順を流す, **Then** 一時停止のまま残る。
3. **Given** 新規のクレジットで請求が0円に見える月, **When** 本当の費用が1,000円を超える, **Then** 50%の知らせが来る。

### Edge Cases

- 夜間に main へマージした：時間帯の確かめで止まる。8時を過ぎてから手で流し直す。
- 最初の作成では本物のイメージがまだない：仮のイメージで立ち上げ、最初のデプロイで置きかえる。作り直しの手順はイメージを戻さない。
- DB のパスワードを替える：版の数を1つ上げて作り直すと、DB と秘密の両方に同じ新しい値が入る。動いている台は次の版で新しい値を読む。
- 公開の URL が2つある（決まった形とそうでない形）：画面の源は1つに決め、LINE のエンドポイントもそれに合わせる。
- 予算の通貨が請求先アカウントと違う：作成が失敗する。変数で合わせる。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 1つのコンテナが、画面の組み立てたファイルと API を同じ源で返せる形で作られること（画面のファイルの場所は設定で渡す）。
- **FR-002**: 同じコンテナを、DB の変更を当てる仕事としても動かせること。何度流しても同じ結果になること。
- **FR-003**: コンテナは管理者ではない利用者で動き、開発の道具を含まないこと。LIFF ID は組み立てのときに埋めること。
- **FR-004**: 手で作るのはプロジェクト・請求のひもづけ・state の置き場所（版を残す）だけで、ほかの本番の資源はすべて Terraform で作ること（AD-9）。
- **FR-005**: DB は ENTERPRISE・db-f1-micro・PostgreSQL 18・東京で、承認済みネットワークのない公開IP、毎日12時（日本時間）のバックアップを7つ残し、消す操作を止めること（AD-8・AD-9）。
- **FR-006**: DB のパスワードはコード・リポジトリ・state に残さず、Secret Manager から実行時に渡すこと。
- **FR-007**: サービスは最大2台・最小0台で、DB へは組み込みの接続（Unix ソケット）だけでつなぎ、本番の設定（`APP_ENV=production`・`TRUSTED_PROXY_HOPS=1`・`RATE_LIMIT_MAX=600`・LINE の値・オープンチャットの URL）を持つこと。イメージの差は Terraform が戻さないこと。
- **FR-008**: 夜間の停止（0時）と起動（8時。日本時間）を自動で行い、DB の動く・止まるの状態と仕事の一時停止を Terraform が戻さないこと（AD-10）。
- **FR-009**: 請求の予算を月2,000円にし、50%・100%でメールで知らせること。
- **FR-010**: GitHub Actions は鍵を置かずに GCP に入り、入れるのはこのリポジトリの main のブランチだけであること。身分の権限は要るものだけにすること。
- **FR-011**: main への push（出すものが変わるファイルだけ）と手での実行で、コンテナを作る → DB の変更 → 新しい版の順に出し、途中で失敗したら止めること。デプロイは同時に1つだけで、流れているものを取り消さないこと（AD-11）。
- **FR-012**: 日本時間の0時〜8時はデプロイを早く止め、理由を出すこと。手での実行に限り、この確かめを飛ばせること。
- **FR-013**: デプロイの設定は GitHub の Secrets を使わず、リポジトリの変数だけで渡すこと。外の部品は SHA で固定すること。
- **FR-014**: 初めての手順（プロジェクト・請求・state・LINE の値・作成・リポジトリの変数）を日本語の手順書に書くこと。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 手順書に沿えば、プロジェクトを作ったあと本番の URL が開くまで、手で打つ命令が（道具を入れるのを除いて）15個以内で済む。
- **SC-002**: 資源の定義は書式と整合の確かめ（fmt・validate）を通り、2回目の作成で差が0件になる。
- **SC-003**: アプリを変えたマージから本番に出るまで、人の操作は0回で、15分以内に終わる。
- **SC-004**: 文書だけのマージでデプロイが動く回数は0回。
- **SC-005**: リポジトリと state を全部読んでも、DB のパスワードは0回出てくる。
- **SC-006**: 月の費用が予算の50%に届いた日のうちに、主催者にメールが届く。

## Assumptions

- 環境は本番の1つだけ（ステージングは交流会のあと。AD-11）。
- 画面のファイルを返す処理・画面の CSP・`LINE_CHANNEL_IDS` などの設定の確かめは、別の共通の PR（core-001 の続き）で入る。この仕様は環境の値と場所を決めて渡すだけ（[research.md](./research.md) の「つなぎ目」）。
- Terraform は主催者の手元から流す（GitHub Actions からは流さない）。
- LINE のチャネル・LIFF ID・オープンチャットは主催者が用意する。
- 請求先アカウントの通貨は円（違えば変数で合わせる）。

## Clarifications

### Session 2026-11-19

開発者は寝ているため、エージェントが仮決めした（[research.md](./research.md) に理由）。

- Q: GitHub Actions の入り方は、構成の決めごとどおり Direct WIF（サービスアカウントなし）にできるか？ → A: できない。Cloud Run が WIF の直の権限に対応していないため、WIF でデプロイ用のサービスアカウントになりすます（鍵は作らない）。構成の決めごと AD-9 の「Direct WIF」は直しが要る（R-2）。
- Q: DB のパスワードを Terraform の中で作るか、手で入れるか？ → A: Terraform の中で「その場だけの値」として作り、書くだけの欄で DB と Secret Manager に渡す（state に残らない）。秘密には `DATABASE_URL` 丸ごとを入れる（R-3）。
- Q: 本番のコンテナで DB の変更をどう当てるか？ → A: 開発の道具を入れず、drizzle-orm の migrator を呼ぶ小さな手順（`apps/api/scripts/migrate.ts`）を同じコンテナで動かす（R-5）。
- Q: 夜間に main へマージしたら？ → A: 時間帯の確かめで早く止め、8時を過ぎてから手で流し直す。交流会で停止を止めた夜だけ、手での実行で確かめを飛ばせる（R-9）。
- Q: どのファイルの変更でデプロイするか？ → A: 出すものが変わるファイルを並べる形（apps・packages・依存の一覧・Dockerfile・deploy.yml。`*.md` は除く）。infra/ は手元で apply するので含めない（R-9）。
