# Feature Specification: 共通の道具をまとめる（CSV・日本時間の日時・ダウンロード）と DB の変更の確かめ（core-004）

**Feature Branch**: `feature/core-004-shared-tools`

**Created**: 2026-11-19

**Status**: Draft

**Input**: 開発者の指示（2026-11-19）。構成の決めごと AD-17・AD-18 と [バックログ](../../../docs/backlog.md) A の「作る順番 1」。受付アプリを作ったときに、CSV の作り方（BOM・改行・式として読まれない守り・`"` の囲み）・日本時間の日時の書き方・CSV を返すときのヘッダー・画面のダウンロードが、reception と survey で同じ形で二重になった。守りの処理が2か所にあると、直し忘れで穴が残る。AD-18（共通にしてよいのは業務を知らず状態を持たない技術の道具だけ）に沿って1か所にまとめる。あわせて、AD-17 のとおり、DB の変更の作り忘れと順番の狂いを全部の確かめで止める。参加者と困りごとの CSV の中身・ファイルの名前・画面の動きは1バイトも変えない。

## User Scenarios & Testing *(mandatory)*

このプロダクトの「利用者」は、ここでは開発者（主催者本人と、並行して作る AI のセッション）。主催者の画面と CSV の見え方は変わらない。

### User Story 1 - 2つ目のアプリが CSV を書き出すとき、守りつきの道具をそのまま使える (Priority: P1)

開発者は、新しいアプリで一覧を CSV に書き出す。見出しと行を渡すだけで、Excel で文字化けせず、利用者が入れた値が式として動かない CSV ができる。守りの処理を写したり、自分で書いたりしない。

**Why this priority**: 守りの処理（式として読まれない守り）が写しごとに食い違うのが、いちばん危ない（AD-18）。

**Independent Test**: 共通の道具だけを使い、`=1+1`・`@SUM(A1)`・`"`・改行・`,` を含む値で CSV を作り、BOM・改行・守り・囲みを確かめる。

**Acceptance Scenarios**:

1. **Given** 見出しと行, **When** CSV を作る, **Then** 先頭に BOM、行の区切りと最後の行の終わりは CRLF
2. **Given** `=`・`+`・`-`・`@`・タブ・CR で始まる値, **When** 欄にする, **Then** 先頭に `'` が付く
3. **Given** `"`・`,`・CR・LF を含む値, **When** 欄にする, **Then** `"` で囲み、中の `"` は `""` にする
4. **Given** 共通の道具, **When** その中身を読む, **Then** 業務の言葉（参加者・困りごと・交流会など）と、ほかの領域への参照がない

---

### User Story 2 - 主催者が書き出す CSV は今までと1バイトも変わらない (Priority: P1)

主催者は、A5（書き出しと削除）で参加者の CSV を、困りごとの画面で困りごとの CSV を書き出す。中身・並び・ファイルの名前（`participants-YYYY-MM-DD.csv`・`concerns-YYYY-MM-DD.csv`）・保存のされ方は、今と同じ。

**Why this priority**: 内側の整理で、交流会（2026-11-25）の動きを変えない。

**Independent Test**: 今ある reception・survey の CSV のテスト（API と E2E）を、期待の値を直さずに流して通す。

**Acceptance Scenarios**:

1. **Given** 割引・紹介者・手でのチェックインを含む参加者, **When** 参加者の CSV を書き出す, **Then** 今のテストの期待どおり（見出し・欄・日本時間の日時・守り）
2. **Given** 回答と主催者の代わりの入力, **When** 困りごとの CSV を書き出す, **Then** 今のテストの期待どおり
3. **Given** 主催者, **When** 画面のボタンで書き出す, **Then** 今と同じファイルの名前で保存される。エラーのときの出し方も同じ

---

### User Story 3 - DB の変更の作り忘れと順番の狂いを、全部の確かめで止める (Priority: P2)

開発者が表の定義を直して DB の変更を作り忘れたとき、または並行の作業で DB の変更の順番が狂ったとき、PR の前の全部の確かめが落ちて、何が悪いかを日本語で出す。

**Why this priority**: 2つのアプリを並行して作ると、DB の変更が当たらない・順番が入れ替わる事故が起きうる（AD-17。いまの DB の道具は、順番が古いものを黙って飛ばす）。

**Independent Test**: 表の定義だけを直した状態、DB の変更の記録の時刻を逆にした状態、壊れた記録の状態で、それぞれ確かめが落ちることを確かめる。

**Acceptance Scenarios**:

1. **Given** 表の定義を直し、DB の変更を作っていない, **When** 全部の確かめを流す, **Then** 落ちて、「DB の変更を作り忘れています（`pnpm db:generate`）」の旨と差分のファイルを出す
2. **Given** DB の変更の記録で、後の変更の時刻が前より古い, **When** 確かめる, **Then** 落ちて、どの変更かを出す
3. **Given** 記録が壊れている・同じ親を指す記録が2つある, **When** 確かめる, **Then** 落ちる
4. **Given** 何も変えていない, **When** 確かめる, **Then** 通り、作業の木に差分を残さない

### Edge Cases

- 空の値・`null` の欄は空の欄にする（今と同じ）。
- 値の途中の `=` は守りの対象にしない（先頭だけ。今と同じ）。
- 見出しも同じ欄の作り方を通す（今の見出しは守りの対象の文字で始まらないので、中身は変わらない）。
- ファイルの名前の日付は、書き出したときの日本時間の日付（サーバーの時刻帯に頼らない。今と同じ）。
- 画面で、ヘッダーにファイルの名前がないときは、呼んだ側が決めた既定の名前（`participants.csv`・`concerns.csv`）にする（今と同じ）。
- DB の変更の確かめは、DB に接続しない（手元の DB が止まっていても流せる）。作業の木を汚したまま落ちない（確かめのために作ったファイルは消す）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: CSV の作り方（BOM・CRLF・最後の行の CRLF・式として読まれない守り・`"` の囲み）を、業務を知らない共通の道具の1か所に置く。reception と survey は、それを使って見出しと行だけを渡す。
- **FR-002**: 共通の道具は、業務の言葉とほかの領域への参照を持たず、状態を持たない。将来に領域を別のサービスに切り出しても、そのまま取り込める包みにする（AD-18）。
- **FR-003**: 日本時間の日時（`YYYY-MM-DD HH:mm`）の書き方を、日本時間の関数の約束の場所（contracts の core）の1か所に置き、reception と survey の写しを消す。
- **FR-004**: CSV を返すときのヘッダー（種類・文字コード・添付・`<名前>-<日本時間の日付>.csv` のファイル名）を、API の共通（kernel）の1か所に置き、reception と survey はそれを使う。
- **FR-005**: 画面で CSV を受け取る処理（ヘッダーからファイル名を読む・既定の名前・エラーの扱い）と保存する処理を、画面の共通（lib）の1か所に置き、reception と survey はそれを使う。
- **FR-006**: 参加者と困りごとの CSV の中身・ファイルの名前・画面の動きとエラーの出し方は変えない。今あるテストの期待の値を直さずに通す。
- **FR-007**: 全部の確かめ（`pnpm check`）に、DB の変更の確かめを足す：(a) 表の定義から DB の変更を作り直して差分が出ないこと、(b) 記録の時刻が順に増えること、(c) DB の道具の整合の確かめ（壊れた記録・同じ親の記録）。落ちたら、日本語で理由と直し方を出す。
- **FR-008**: DB の変更の確かめは DB に接続せずに流せ、通ったときも落ちたときも作業の木に余計な差分を残さない。
- **FR-009**: 共通の道具には、それぞれ単体のテストを付ける（守り・囲み・BOM・改行・ファイル名・既定の名前）。
- **FR-010**: 共通の道具と DB の変更の確かめを、文書（並行開発の決まり・コードの書き方の決まり・今の形の説明）に1行ずつ足し、新しいアプリが見つけられるようにする。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 式として読まれない守りの処理が、リポジトリの中で1か所だけになる（今は2か所）。
- **SC-002**: 日本時間の日時の書き方・CSV のヘッダー・画面のダウンロードの処理が、それぞれ1か所だけになる。
- **SC-003**: 参加者と困りごとの CSV のテスト（API・E2E）が、期待の値を1つも直さずに通る。
- **SC-004**: 表の定義だけを直した状態・記録の時刻が逆の状態・壊れた記録の状態の3つで、全部の確かめが落ちる。何も変えていない状態では通る。
- **SC-005**: 全部の確かめ（秘密の値・書式・型・lint・単体・E2E）が通る。

## Assumptions

- 共通の道具の包みの名前は `@workspace/csv`（今の `@workspace/contracts`・`@workspace/ui` に合わせる）。画面だけの道具は `apps/web/src/lib`（画面は1つのまま。AD-18）。
- DB の変更の確かめは、今の DB の道具（Drizzle 0.45・drizzle-kit 0.31）の上で作る。Drizzle 1.0 に移ったら直す（AD-17）。
- この PR は共通の PR で、DB の表を変えない。交流会の画面と API の窓口の形（OpenAPI）は変えない。
- CI は節約の決まりどおり、手元で全部の確かめを流して PR に結果を書く。
