# Research: 本番に出す3つのモード（core-019）

## R1. 本番の前の確かめ：1回の流れの中で、ステージング → 承認 → 本番

- `main` のマージで、同じコミットをまずステージングに出し（`deploy-environment.yml` を `environment: staging` で呼ぶ）、成功したら `environment: production` で呼ぶ。GitHub の環境 `production` に承認者（Required reviewers）を置くと、その仕事は承認するまで始まらない（GitHub の Environments。公開のリポジトリで使える）。
- `hotfix/*` をそのままステージングに出す形（案A）は、WIF とデプロイの身分にブランチを足すことになり、ステージングが develop と違う中身になる時間も長い。案B は本番に出るのがいつも `main` の中身だけで、手順が1本。
- ステージングは `main` のマージのたびに `main` の中身になる。次の `develop` のマージ（`main` を `develop` に取り込み直したときを含む）で develop の中身に戻る。
- ステージングのデプロイの身分を `main` からも使えるよう、WIF のなりすましを `refs/heads/develop` と `refs/heads/main` の2つにした。本番の身分は `main` からだけのまま。
- 2つの流れ（`main` と `develop`）が同じ環境に同時に出ないよう、`deploy-environment.yml` の仕事は環境ごとに1つずつ（`concurrency: deploy-environment-<環境>`）。

## R2. 夜の緊急デプロイ：DB を一時的に起こして、必ず止め直す

- `wake_db` を入にして手で流すと、`wake-db` の仕事が `gcloud sql instances patch --activation-policy=ALWAYS` で起こし、`RUNNABLE` になるまで待つ（最大10分）。
- `stop-db` の仕事は `wake-db` だけを待ち、DB が動き出してから `keep_awake_minutes`（15〜90。既定60）たったら（`wake-db` が出す `stop_at`）、成功・失敗・承認しなかったにかかわらず `--activation-policy=NEVER` で止め直す。本番の仕事（承認待ち）を待たないのは、承認されないと最長30日待ち続け、そのあいだ DB が起きたままになるため。
- 取り消したとき：仕事の `if: always()` だけでは、中の手順は既定の `success()` で飛ばされる。待つ手順は `!cancelled()`、身分を取る・止め直す手順は `always()` にして、取り消したらすぐ止め直す（強い取り消し〈Force cancel〉では動かないので、手順書に手で止める方法を書く）。
- 承認が遅れたとき：本番の仕事は承認のあとに始まるので、流れの始まりの時間の確かめだけでは足りない。`deploy-environment.yml` の中で、コンテナを作る前（昼は23時15分まで・夜は `stop_at` まで20分より長く）と DB の変更の直前（23時40分まで・15分より長く。DB の変更の job の起動・新しい版・動いているかの確かめ〈4分まで〉に足りるように）に確かめ、足りなければ何もせずに止まる。DB の変更の途中で DB が止まらないようにするため。
- 前から動いていたとき（交流会で夜間の停止を止めた日）は起こさず、止め直しもしない（`was_stopped`）。止め直すのは7時45分より前だけ（8時の Cloud Scheduler の起動と、止める処理が重ならないように）。
- 起こす・止める処理は `--async` で頼み、状態を見て待つ（gcloud の待ちの上限で落ちても処理は続くため）。止め直しは、ほかの処理が動いていると断られるので、30秒おきに10回まで試す。`wake_db` のときは `skip_hour_check` を入にしても残りの確かめは飛ばさない。
- 残り：DB の権限はプロジェクトの単位で付けている。台の名前の条件（IAM Conditions）で絞るのは、本物の環境で確かめられるときにバックログ C6 と一緒に行う。
- 使えるのは0時10分〜7時45分だけ。0時〜0時10分は0時の停止（Cloud Scheduler。失敗したら1分おきに直し直す）が効き終わる前で、7時45分〜8時は8時の起動と重なるため。
- 権限：自前の役割 `kanaeruSqlActivation`（`cloudsql.instances.get`・`update`）は、止める・動かすのほかに、台の設定（ネットワーク・バックアップ・消す守り）も直せる。develop から使えるステージングのデプロイの身分に付けると、develop に入ったコードが昼に DB を止めたり設定を変えたりできてしまう。そこで、`main` からだけなりすませる専用の身分 `kanaeru-db-waker` に持たせ、デプロイの身分には付けない。`wake_db` も `main` だけにした。
- 残り（バックログ）：本番のデプロイの身分のなりすましは `main` のブランチで絞っていて、GitHub の環境 `production`（承認）では絞っていない。`main` に入った別の workflow なら承認なしで本番の身分を使える（core-018 から同じ）。WIF の属性に環境を足して絞るのは、本物の環境で確かめられるときに別の PR で行う。

## R3. 新しいアプリ：出す（デプロイ）と公開を分ける

- コードは週ごとのリリースで本番にも入れ、本番のアプリの台帳（AD-16）では「切」にしておく。ステージングで1週間試し、問題がなければ本番の台帳を公開に切り替える。デプロイは要らない。DB の変更は前の版のアプリでも壊れない形だけにする決まり（`docs/rules/coding.md` 3）があるので、先に入れても困らない。
