## User Scenarios & Testing *(mandatory)*

### User Story 1 - 店舗ごとのチームで運用アカウントを分ける (Priority: P1)

持ち主が運用アカウントを「店舗A」のチームに入れる。店舗A のリーダーが、店舗A の編集者を担当にする。店舗B の人には店舗A の運用アカウントが見えない。

**Acceptance Scenarios**:

1. **Given** 持ち主が入っていないチーム, **When** そこへ入れる, **Then** 404
2. **Given** 店舗A のリーダー, **When** 店舗A の編集者を担当にする, **Then** 付く。店舗B の運用アカウントでは 403
3. **Given** 店舗B だけの編集者, **When** 店舗A の運用アカウントを開く, **Then** 404
4. **Given** 組織の管理者, **When** どのチームの運用アカウントでも担当を付ける, **Then** 付く

### User Story 2 - リーダーが自分のチームの運用状況を見る (Priority: P2)

リーダーは、自分のチームの運用アカウントと人の数と日付だけを見る。ほかのチームは出ない。

### User Story 3 - チームから外れる・チームが消える (Priority: P2)

持ち主がチームから外れると、その運用アカウントはチームから外れ、担当も消える。担当の人がチームから外れると、その人の担当が消える。

## Requirements *(mandatory)*

- **FR-1**: 判定は access.ts の1か所（threads-013 の FR-1 のまま）。チームの人かどうかは要求のたびに suite から引く。
- **FR-2**: `threads_organization_account` に `team_id`（NOT NULL）。`team(id, organization_id)` と `team_member(team_id, owner_account_id)` を指す外部キーを CASCADE。`threads_assignment` に `team_id`（NOT NULL）。`team_member(team_id, account_id)` と `threads_organization_account(threads_account_id, team_id)` を指す外部キーを CASCADE。
- **FR-3**: 入力 `ThreadsPlacementInput` を `{ teamId }`（null で外す）にする。`ThreadsAccountTeam` は入っているチーム（組織の名前とチームの名前）と、入れられるチームの一覧を返す。
- **FR-4**: NG ワードの確かめと人による承認は、どの関わりでも省かない（threads-013 の FR-2 のまま）。
- **FR-5**: 運用状況は数と日付だけ（threads-013 の FR-3 のまま）。

## 範囲の外

1つの運用アカウントを複数のチームに入れる・チームをまたぐ担当・リーダーがチームの人を出し入れする。
