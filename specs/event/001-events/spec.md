## User Scenarios & Testing *(mandatory)*

### User Story 1 - 主催者が交流会を作り、直す (Priority: P1)

主催者は、交流会の一覧（A1）から「交流会を追加」を押し、名前・日時・会場・参加費・GoogleフォームのURL（任意）・LINEグループの招待リンク（任意）を入れて作る。あとで同じ欄を直せる。

**Why this priority**: 受付・アンケート・合計のすべてが交流会を前提にする（PRD 6.1 の1番目）。

**Independent Test**: 主催者のセッションで交流会を作ると一覧に名前・日時・会場・参加費が出ること、0円も入れられること、直すと変わること、主催者でなければ作れないことを確かめる。

**Acceptance Scenarios**:

1. **Given** 主催者, **When** 名前・日時・会場・参加費を入れて作る, **Then** 一覧に名前・日時（日本時間）・会場・参加費が出る
2. **Given** 主催者, **When** 参加費を0円にする, **Then** 作れる
3. **Given** 主催者, **When** 名前を空・参加費を負や小数・URL を https でない形にする, **Then** 欄のそばに日本語の理由が出て、作られない
4. **Given** 主催者, **When** 交流会を直す画面を開く, **Then** 今の値が入っていて、「参加費を直しても、すでにあるチェックインの金額は変わりません」と出る
5. **Given** 主催者でない人, **When** 作る・直す窓口を呼ぶ, **Then** 403

---

### User Story 2 - 主催者が受付QR・アンケートQRを出して印刷する (Priority: P1)

主催者は、準備の画面（A4）で、その交流会の受付QRとアンケートQRを並べて見る。QR にはミニアプリの URL（参加者の道）が入っている。それぞれ、1枚に1つの QR を大きく載せた印刷の画面を開いて印刷できる。

**Why this priority**: 受付QRは受付そのものの入口（FR-2・PRD 6.1 の1番目）。

**Independent Test**: 準備の画面に「受付QR」「アンケートQR」の見出しと交流会の名前つきの QR が出て、QR の中身が `participantPaths` の道（本番はミニアプリの URL）であること、別の交流会では別の道になることを確かめる。

**Acceptance Scenarios**:

1. **Given** 主催者, **When** 準備の画面を開く, **Then** 受付QRとアンケートQRが、どちらかをことばで書いて並ぶ
2. **Given** 受付QR, **When** 読む, **Then** その交流会のチェックインの画面の道が開く（アンケートQRはアンケートの画面）
3. **Given** 主催者, **When** 印刷の画面を開く, **Then** その QR だけが大きく出て、「印刷する」で印刷できる

---

### User Story 3 - 主催者がアンケートを開け閉めする (Priority: P1)

主催者は準備の画面で「アンケートを開く」「アンケートを閉じる」を押す。今の状態をことばで出す。開いているかは要約に載り、survey と参加者の画面が読む。

**Why this priority**: アンケートの時間の切り替え（FR-9・PRD 6.1 の2番目）。

**Independent Test**: 主催者が開くと要約の「開いているか」が true になり、閉じると false になること、主催者でなければ 403 であることを確かめる。

**Acceptance Scenarios**:

1. **Given** 閉じている交流会, **When** 主催者が「アンケートを開く」, **Then** 「アンケートは開いています」と出て、要約が開いているになる
2. **Given** 開いている交流会, **When** 主催者が「アンケートを閉じる」, **Then** 「アンケートは閉じています」と出る
3. **Given** 受付係・参加者, **When** 開閉の窓口を呼ぶ, **Then** 403

---

### User Story 4 - 主催者が受付係を招き、受付係がリンクから入る (Priority: P2)

主催者は準備の画面で、交流会ごとに1本の招待のリンクを作り、写して受付係に送る。受付係はリンク（P3）を開き、交流会の名前を確かめて「受ける」を押すと、その交流会の受付係になる。リンクは何人でも使え、交流会の日（日本時間）が終わると使えない。作り直すと前のリンクは使えない。主催者は受付係の一覧を見て、外せる。外された人は、次に開いたときから使えない。

**Why this priority**: 受付係がいない回は主催者の端末で回せる（PRD 6.1 の3番目）。

**Independent Test**: 主催者がリンクを作り、別の人がログインして受けると受付係になり、交流会の一覧にその交流会が出ること、期限を過ぎた・作り直した前のリンクでは受けられないこと、外すと権限がなくなることを確かめる。

**Acceptance Scenarios**:

1. **Given** 主催者, **When** 「招待のリンクを作る」, **Then** リンクと「{日付} の終わりまで使えます」が出て、写せる
2. **Given** 招待のリンク, **When** ログインした人が開いて「受ける」, **Then** その交流会の受付係になり、交流会の一覧に出る
3. **Given** 交流会の日（日本時間）が終わった, **When** リンクで受ける, **Then** 「この招待のリンクは使えません。主催者に新しいリンクをもらってください」
4. **Given** 主催者がリンクを作り直した, **When** 前のリンクで受ける, **Then** 同じく使えない
5. **Given** すでに受付係・主催者, **When** リンクで受ける, **Then** そのまま進む（記録は増えない）
6. **Given** 主催者が受付係を外した, **When** その人が交流会の窓口を呼ぶ, **Then** 403
7. **Given** 主催者が受付係を外した, **When** その人が外される前のリンクで受け直す, **Then** 使えない（外すと招待のリンクも作り直される【仮決め R3】）

---

### User Story 5 - ほかの領域が、権限と要約を1つの仕組みで使う (Priority: P1)

reception・survey は、交流会ごとの権限（主催者・受付係・どちらでもない）を event の1つの関数と middleware で要求のたびに確かめる。参加者の画面と survey は、ログインしていれば誰でも読める要約（名前・日時・会場・参加費・アンケートが開いているか・GoogleフォームのURL・LINEグループの招待リンク・オープンチャットの URL）を読む。

**Why this priority**: 並行して作る reception・survey がすぐ使う（AD-5・AD-13）。

**Independent Test**: テストの中で `requireEventRole` を付けた道を足し、主催者・受付係・どちらでもない人・ない交流会・形の違う ID で 200・200・403・404・404 になること、外したあとは 403 になること、要約がログインした誰にでも返ることを確かめる。

**Acceptance Scenarios**:

1. **Given** 主催者, **When** どの交流会でも, **Then** 役目は主催者
2. **Given** その交流会の受付係, **When** 役目を引く, **Then** 受付係（ほかの交流会では、どちらでもない）
3. **Given** ログインした誰か, **When** 要約を読む, **Then** 決めた欄だけが返る（受付係の一覧・招待の印は含まない）
4. **Given** 未ログイン, **When** 要約を読む, **Then** 401

---

### User Story 6 - 主催者と受付係が、自分の交流会を一覧から選ぶ (Priority: P2)

交流会の一覧（A1）に、主催者はすべての交流会、受付係は自分が受付係の交流会だけを出す。受付係には「交流会を追加」「準備」「直す」を出さず、準備の画面を開いても使えない。

**Why this priority**: 受付係が LINE のミニアプリを開き直したとき、一覧から戻れる（EXPERIENCE Open Questions）。

**Independent Test**: 受付係で一覧を開くと自分の交流会だけが出て、準備への入口がなく、準備の画面の道を開くと使えない状態が出ることを確かめる（E2E）。

**Acceptance Scenarios**:

1. **Given** 主催者, **When** 一覧を開く, **Then** すべての交流会が日時の新しい順に出る
2. **Given** 受付係, **When** 一覧を開く, **Then** 自分の交流会だけが出て、「交流会を追加」「準備」「直す」が出ない
3. **Given** 受付係・参加者, **When** 準備・作成・編集の画面を開く, **Then** 「この画面は主催者だけが使えます」が見出しで出る
4. **Given** どちらでもない人, **When** 一覧を開く, **Then** 「交流会はまだありません」（主催者でなければ「交流会を追加」は出ない）

### Edge Cases

- 交流会の ID の形が違う・ない交流会：404（受付係・主催者の窓口も、要約も）。
- 招待のリンクの印の形が違う・知らない：404 `STAFF_INVITE_INVALID`（同じ文）。期限切れは 410 `STAFF_INVITE_EXPIRED`。
- 交流会の日時をあとで直すと、招待の期限も、受けるときの今の日時で決まる（AD-5）。
- 受付係のアカウントが消されると、受付係の割り当ても消える（`ON DELETE CASCADE`。AD-7）。交流会は消さない（この版は消す機能がない。参照は `RESTRICT`）。
- 同じ人が同時に2回受けても、受付係は1つ（交流会と account の組の一意の制約）。
- 同時に2回作り直しても、招待のリンクは交流会ごとに1本（交流会の一意の制約）。
- 夜間の停止中：土台の 503 `DB_UNAVAILABLE`（event は読みかえない）。
- 印刷とリンクの写しは PC で主に使う。写せない端末では、リンクの文字を選んで写せる。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: event の領域が `event`（名前・始まりの日時・会場・参加費〈円の整数・0以上〉・GoogleフォームのURL〈任意〉・LINEグループの招待リンク〈任意〉・アンケートが開いているか〈既定は閉じている〉）・`event_staff`（交流会と account の組・一意。account は `ON DELETE CASCADE`、交流会は `RESTRICT`）・`staff_invite`（交流会ごとに1つ・招待の印〈一意〉・作った時刻。交流会は `RESTRICT`）の表を持つ（AD-3・AD-7）。
- **FR-002**: 主催者だけが、交流会を作る・直す（`POST /api/v1/events`・`PUT /api/v1/events/{eventId}`）。消す窓口はない。
- **FR-003**: `GET /api/v1/events` は、主催者にはすべて、受付係には自分の交流会だけ、どちらでもない人には空の一覧を、日時の新しい順に返す。各行に自分の役目を付ける。
- **FR-004**: `GET /api/v1/events/{eventId}` は、主催者と、その交流会の受付係だけが読める（自分の役目つき）。
- **FR-005**: `GET /api/v1/events/{eventId}/summary` は、ログインしていれば誰でも読め、名前・日時・会場・参加費・アンケートが開いているか・GoogleフォームのURL・LINEグループの招待リンク・コミュニティのオープンチャットの URL（設定。なければ空）だけを返す（AD-5・FR-17・FR-22）。
- **FR-006**: 主催者だけが、アンケートを開く・閉じる（`PUT /api/v1/events/{eventId}/survey`）。
- **FR-007**: 主催者だけが、招待のリンクを作る・作り直す（`POST /api/v1/events/{eventId}/staff-invite`）・今のリンクを読む（`GET` 同じ道）。作り直すと前の印は使えない。期限（交流会の日時の日本時間の日付の終わり）を一緒に返す。
- **FR-008**: ログインした人は、招待の中身（交流会の名前・日時・期限・自分の役目）を読み（`GET /api/v1/staff-invites/{inviteToken}`）、受ける（`POST /api/v1/staff-invites/{inviteToken}/accept`）。受けると受付係になる。期限は受けるときに、交流会の今の日時から決める。すでに主催者・受付係なら、期限にかかわらず何もせずに通す。
- **FR-009**: 主催者だけが、受付係の一覧（表示名・加えた時刻）を読み（`GET /api/v1/events/{eventId}/staff`）、外せる（`DELETE /api/v1/events/{eventId}/staff/{accountId}`）。外すと、招待のリンクがあれば作り直し、前の印は使えない（外された人が前のリンクで受け直せない）。
- **FR-010**: event の入口（`index.ts`）が、ほかの領域に `getEventRole(db, config, eventId, account)`（`"organizer" | "staff" | null`）・`requireEventRole(deps, roles)`（`{eventId}` の道の middleware）・`currentEventRole(c)`・`getEventSummary(db, config, eventId)`・`eventTable`（外部キーのためだけ）を出す。役目は要求のたびに引き、セッションに写さない。
- **FR-011**: 交流会の権限の誤りは 403（code `FORBIDDEN`・event の文）、ない交流会は 404（code `NOT_FOUND`・event の文）。
- **FR-012**: 画面：交流会の一覧（A1）・作成と編集（A2）・準備（A4。QR の表示と印刷・招待のリンクと作り直し・受付係の一覧と外す・アンケートの開閉）・受付係の招待（P3）。どれもログインが要る（`SessionGate`）。
- **FR-013**: QR と招待のリンクは、約束の土台の `participantPaths` と `miniAppPermalink` で作る（AD-14）。QR は濃い点と白い地、まわりに4モジュールの余白、画面では一辺 240px 以上。
- **FR-014**: 管理の画面の道（A1〜A5 と困りごとの画面・QR の印刷）は、event の約束の1か所に定数で置く。event の画面の入口は、交流会の管理の画面どうしの行き来（参加者・合計／困りごと〈主催者だけ〉／準備〈主催者だけ〉）を出す `EventAdminNav` を出す。
- **FR-015**: 入力の形・エラーの code と日本語の文言は、約束の event のフォルダに置く。

### Key Entities

- **交流会**：主催者が作る1回ごとの催し。名前・始まりの日時・会場・参加費・GoogleフォームのURL・LINEグループの招待リンク・アンケートが開いているか。
- **受付係**：交流会と account の組。その交流会の中だけで効く。
- **招待のリンク**：交流会ごとに1つの印。何人でも使え、交流会の日の終わりまで。作り直すと替わる。
- **要約**：参加者に見せてよい交流会の欄だけ。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 全部の確かめ（`pnpm check`）が通る。
- **SC-002**: 主催者が交流会を作り、準備の画面で受付QRを出し、アンケートを開くまでが、E2E で両方の幅のアクセシビリティの違反0件で通る。
- **SC-003**: 受付係が招待のリンクから受け、一覧でその交流会を見て、準備の画面が使えないことが、E2E で通る。
- **SC-004**: 外した受付係の次の要求が 403 になり、外される前のリンクで受け直せない（結合のテスト・通しのテスト）。

## Assumptions

- 一覧画面（A3）・書き出しと削除（A5）・困りごとの画面は reception・survey の仕様で作る。event は道の形とナビの差しこみ口だけを置く。
- 交流会を消す機能は作らない（AD-7）。
- アンケートを閉じたあとの扱い（主催者の代わりの入力は受ける）は survey が決める（AD-13）。event は印を持つだけ。
- QR の中身が本物のミニアプリで開くかは、置き場所に出してから確かめる（構成 Open Questions 1）。
