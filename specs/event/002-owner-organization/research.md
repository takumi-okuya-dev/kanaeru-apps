# Research: 交流会の持ち主と組織（event-002）

2026-11-20 作成。答える人がいないため、PRD 受付アプリの予約と構成の決めごと（AD-5・AD-19・AD-22・AD-23）から AI が決めた（【仮決め】）。

## R1. 今ある交流会の持ち主の埋め方【仮決め】

**決めたこと**：event の領域の中の「持ち主のない交流会を、運営者のものにする」（`claimLegacyEvents`。`UPDATE event SET owner_account_id = 運営者 WHERE owner_account_id IS NULL`）を、次のときに流す。

- 運営者（account の `isOrganizer`）が交流会の一覧（`GET /api/v1/events`）を開いたとき
- 運営者が、持ち主のない交流会の道（`requireEventRole` を通る道）を開いたとき（event-002 の2つ目の PR から）

`NOT NULL` は、本番で持ち主のない交流会が0件と確かめてから、別の小さな DB の変更で付け、同じ PR でこの処理を消す（[コードの書き方](../../../docs/rules/coding.md) 3 の「既存の行が通らないかもしれない制約は2回に分ける」）。

**理由**：

- 運営者は設定 `ORGANIZER_LINE_USER_ID`（LINE のユーザー ID）で決まる。DB の変更の SQL は設定を読めず、本番の DB の変更の仕事（Cloud Run jobs の `scripts/migrate.ts`）に渡す値は `DATABASE_URL` だけ。SQL で運営者の account を引けない。
- 起動のときに1回流す仕組み（組み立ての `DomainModule` に起動の手順を足す）は共通のファイル（`app.ts`・`server.ts`）を直すことになり、領域の PR に混ぜられない（[並行開発の決まり](../../../docs/rules/parallel-development.md) 3-3）。手で流す手順（スクリプト）は、本番で人が流し忘れる。
- 前の版のアプリで交流会を作れたのは運営者だけ（`requireOrganizer`）なので、**持ち主のない交流会はすべて運営者のもの**と言える。デプロイの途中や前の版に戻したときに前の版が作った交流会（持ち主なし）も、同じ処理で運営者のものになる。
- 運営者は交流会の一覧から受付アプリを使うので、デプロイのあとの最初の利用で埋まる。埋まるまでの間も、受付係・参加者の画面（要約・チェックイン・アンケート）は持ち主を使わないので止まらない。
- `isOrganizer` を交流会の権限に使わない（AD-5）。この処理は「運営者の account がどれか」を知るためだけに使い、権限の判定（`resolveEventAccess`）はいつも持ち主と組織だけを見る。埋めたあとは、運営者もほかの人の交流会を管理できない（FR-B7）。

**ほかの案**：

- DB の変更の SQL で、いちばん古い account や、チェックインの「入れた人」から運営者を推す：当たる保証がない。
- 起動のときに流す：上のとおり共通の変更が要る。夜間の DB の停止中に立ち上がると失敗し、次に立ち上がるまで埋まらない。
- 持ち主のない交流会を、判定の中でずっと「運営者のもの」とみなす（埋めない）：`isOrganizer` が権限の判定に残り続け、`NOT NULL` にできない。

## R2. 持ち主の外部キーと、チェックインのある交流会【仮決め】

**決めたこと**：`event.owner_account_id` は account を指す `ON DELETE RESTRICT`。退会では event の段（R3）が、組織に入れた交流会を引き継ぎ、組織に入れていない交流会を子の行（受付係・招待のリンク・割引・組織に入れる）ごと消す。消す交流会にチェックインがあると、reception の `checkin.event_id`（`RESTRICT`）で DB が止め、account の退会の窓口が 409 `ACCOUNT_OWNS_SHARED_RECORDS` を返す（今の仕組み。`isForeignKeyViolation`）。持ち主自身のチェックインも数える。

**理由**：

- event は reception の表を読めない（依存は reception → event の一方向。AD-3・AD-23）。チェックインがあるかを event が見て決めることはできないので、DB の外部キーに止めさせる。
- `CASCADE` にすると、受付係・割引・招待のリンクの `event_id`（`RESTRICT`）で止まり、チェックインがなくても退会できなくなる。子の外部キーを `CASCADE` に変えるのは AD-7（交流会を指す外部キーは `RESTRICT`）を変えることになる。event の段が自分の表を自分で消せば、AD-7 を変えずに済む。
- 持ち主自身のチェックインを除くには、reception の段が先に本人のチェックインを消す必要があるが、手順は suite → event → reception の順なので、event が消すときにはまだ残っている。持ち主が自分の交流会にチェックインするのは試しのときくらいなので、409 のままにする（先に組織に入れれば退会できる）。

## R3. 退会の引き継ぎと消すは、account を消すトランザクションの中で【仮決め】

**決めたこと**：event の退会の段は `prepare` で何もせず、`finalize`（account を消すトランザクションの中・suite の `finalize` のあと）で、(1) 組織に入れた交流会の持ち主を、組織の今の管理者に替える（`event.owner_account_id` と `event_organization.owner_account_id`）、(2) 組織に入れていない交流会を消す。

**理由**：

- 409 のとき、組織の交流会の引き継ぎだけが済んでいる、という半端を残さない（チェックインのある個人の交流会で止まったら、すべて元に戻る）。
- suite の `finalize` は同じトランザクションの中で、退会する人が管理者の組織を引き継ぎ終えている。そのあとに流すので、今の管理者は退会する人でない。管理者がいない組織（誰もいなくて消えた組織）の交流会は、外部キーで組織から外れ、(2) で個人の交流会として扱われる。
- threads は外のサービスの後始末が多く、運用アカウントごとに `prepare` で行う。交流会は表の行を直すだけなので、1つのトランザクションに入る。

**引き継ぎで変えないもの**：受付係（新しい持ち主が受付係だった行も残す。主催者が勝つので害がない）・招待のリンク・割引・アンケートの開閉。

## R4. 部員の役目の出し方【仮決め】

**決めたこと**：約束（`@workspace/contracts/event`）に `EVENT_ACCESS_ROLES`（`organizer`・`staff`・`member`）と `EventAccessRole` を足す。`requireEventRole` はこの並びから選び、`currentEventRole` と `getEventRole` はこの型を返す。交流会の答えの `myRole`（`EventRole`）は `organizer`・`staff` のまま。

**理由**：この版では部員は管理の画面を使えない（PRD 4.1・AD-5）。答えの `myRole` に部員を入れると、画面のすべての役目の分け方に部員を足すことになる。予約（booking）は `requireEventRole(deps, ["organizer", "member"])` などで部員を使える。

## R5. 組織に入れる窓口【仮決め】

- `GET /api/v1/events/{eventId}/organization`（主催者）：持ち主（名前）・今の組織・自分が持ち主か・選べる組織（持ち主が入っている組織。持ち主でなければ空）。
- `PUT /api/v1/events/{eventId}/organization`（`{ organizationId: uuid | null }`）：主催者でなければ 403 `FORBIDDEN`（`requireEventRole`）、持ち主でなければ 403 `EVENT_OWNER_ONLY`、入っていない組織は 404 `EVENT_ORGANIZATION_NOT_FOUND`（threads の `THREADS_TEAM_NOT_FOUND` と同じく 404）。今と同じなら何もしない。入れ替えは同じトランザクションで外して入れる（交流会の行に `FOR UPDATE`）。
- 組織に入れる・外すと、主催者の範囲が変わるので、画面は交流会と一覧の問い合わせを読み直す。

## R6. 「持ち主と組織」の置き場所【仮決め】

準備の画面（A4。交流会の設定と受付係を置く画面）の最初に節を置く。PRD UJ-6 とモックアップの説明（持ち主の名前・組織の選択か「入れない（個人）」・説明の文）に合わせる。説明の文：「組織に入れると、その組織の管理者と編集者も、この交流会を管理できます。メンバーは部員になります。持ち主はあなたのまま変わりません。」。持ち主でない主催者には、選択の代わりに今の組織と「組織に入れる・外すのは、持ち主だけです。」を出す。

## R7. 一覧の絞りこみ【仮決め】

窓口に絞りこみの値を足さず、一覧の答えの行ごとの `organization` で、画面がチップ（`ChoiceChips`。「すべて」・組織の名前・「個人」）で絞る。チップは、一覧に組織の交流会が1つ以上あるときだけ出す。主催者1人の交流会は月に数回なので、すべてを返しても重くない。

## R8. 作るときの契約【仮決め】

作るときに `hasEntitlement` を呼ばない。売り始める前はいつも通すので、呼んでも振る舞いは同じ。threads も運用アカウントを作るときに呼んでいない。売り始めるとき（AD-16・AD-22）に、作る窓口（持ち主＝作る人・組織＝null）に足す。

## R9. 一覧の引き方

主催者の交流会は「持ち主が自分」か「組織に入れていて、その組織で自分が管理者か編集者」。組織の役割は suite の `listMemberships`（入っている組織と役割）で引き、管理者・編集者の組織の ID で `event_organization` を絞る（suite の表と結ばない。AD-3）。受付係の交流会は `event_staff` と結ぶ。1回の SQL で取り、行ごとの役目は「主催者の条件に当たれば主催者、ほかは受付係」。持ち主の名前は account の `findDisplayNames`（まとめて）、組織の名前は suite の `findOrganization`（組織ごと）で引く。

## R10. セキュリティの確かめ（[開発の流れの決まり](../../../docs/rules/development-flow.md) 2）

ファイルの受け取り・外からの知らせ（Webhook）・決済・中で AI を呼ぶ・パスワードのログイン・MCP のどれも足さないので、`/speckit-plan` のときの確かめは当たらない。権限の範囲が変わるので、結合のテストで「ほかの人の交流会の主催者の窓口は 403（event・reception・survey）」と「部員は 403」を確かめる。
