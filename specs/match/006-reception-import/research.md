# Research: 受付の交流会から名簿を入れる・前に入れたレベル（match-006）

## R1. 選べる交流会の一覧は、画面が event の窓口から読む【仮決め】

- AD-25「選べる交流会は、event の判定で主催者のものだけ」。event の `index.ts` は、ある交流会の役目（`getEventRole`）は出すが、主催者の交流会の一覧は出さない（`listAccessibleEvents` は event の中だけ）。
- 選んだ形：画面が event の窓口 `GET /api/v1/events`（主催者と受付係の交流会。行ごとに `myRole`）を読み、`myRole === "organizer"` の行だけを出す。入れる窓口（match）は `getEventRole` でもう一度確かめるので、画面の絞りは見せ方だけ。画面がほかの領域の窓口を呼ぶ形は、reception → account・threads → suite にもある。
- 選ばなかった形：event の `index.ts` に「主催者の交流会の一覧」を足す（event の領域のフォルダを直すことになり、この PR の範囲が広がる）。見本の M0 は一覧に人数（チェックイン N人・申込み M人）を出すが、そのためには交流会ごとに読む窓口が要るので、人数は交流会を選んだあとに出す。
- 受付アプリが見えない人（AD-16）には、event の窓口が 404 を返し、match の窓口も 404 にする（`isAppVisible`）。

## R2. 申込みの名簿は booking の `index.ts` の `listApplicantRoster`

- AD-23 の 2026-11-22 の直しのとおり、確定した申込みの名前と account だけを出す（メールアドレス・媒体・案内の同意・メモは出さない）。
- 出す行：その交流会の、まとめていない（`merged_into_id` が空）、状態が確定の行。キャンセル待ち・打診中・取り消しは出さない。並びは申し込んだ日時の古い順。
- 使い方が受付だけの交流会は、名簿が隠れているので空（booking の名簿の窓口が 409 を返すのと同じ考え）。
- 権限は呼ぶ側（match）が event の判定で確かめる（booking の中では確かめない。reception の `listEventAttendees` と同じ）。
- booking の領域のフォルダを触るのは、この関数（`repository.ts`）と `index.ts` の出す行と、そのテストだけ。

## R3. 名簿の人に account を持たせ、中身を送ったときにレベルを覚える【仮決め】

- 「account のある人のレベルを運営が入れたら覚える」には、名簿の人と account を結ぶ必要がある。中身（`match_table.content.players[]`）に任意の `accountId` を足した。
- 覚える時：担当の端末が中身を送る `PUT` の中（同じトランザクション）で、前の中身と比べ、account とレベルのある人で、レベルが前と違うか前にいなかった人だけを書く。名簿と設定の画面でレベルを選んだときも、受付の交流会から入れたとき（覚えたレベルがそのまま入る）も、同じ道で覚える。電波がない間の変更も、送ったときに覚える。
- レベルを外した（空にした）人は、覚えたものを消さない。
- 名簿に残った account が消えた（退会した）人は、外部キーの違反になる。まとめて書いて違反したら、1人ずつ区切り（savepoint）で書き直し、違反した人だけを飛ばす。中身の保存は止めない。
- 中身の account は、見るだけのページ（呼び名だけを出す）・電波なしで渡す QR（呼び名だけ）には出ない。運営（持ち主と組織の管理者・編集者）の画面と担当の端末の IndexedDB にはある。account の ID は氏名ではないが、退会した人の ID が試合表に残る（90日で消える）。
- 選ばなかった形：入れる枠の中でだけ覚える（あとで名簿でレベルを直しても覚え直せない）。account の代わりに意味のない札を返す（札と account の対応を別に持つことになり、重い）。

## R4. 覚えている持ち主は、試合表を入れた組織か持ち主

- `match_level_memory` は相手（持ち主の account か組織）ごとに1行（match-001）。試合表を組織に入れていれば組織、入れていなければ試合表の持ち主（今の利用者ではない。組織の編集者が直しても、個人の試合表は持ち主のもの）。
- 組織に入れた試合表で覚えたレベルは、その組織の試合表で使え、個人の試合表には付かない（逆も同じ）。

## R5. 既定で入れる人：チェックインした人がいればそちら【仮決め】

見本の M0 は申込みの名簿に印が付いているが、当日はチェックインした人の方が来た人に合う。チェックインした人が1人もいなければ申込みの名簿（前もって）。運営はどちらも選べる。

## R6. 名前と呼び名

- 名前（チェックインと申込みの名前。LINE の表示名のことがある）は、呼び名を作るためだけに窓口が返し、画面の「氏名（入れたもの）」の列に、画面を開いている間だけ出す（貼り付けと同じ）。試合表には持たない。
- 呼び名は貼り付け・CSV と同じ `assignNicknames`（姓・同じ姓は名の字・空白がなければ頭の2字で「姓と名の間に空白がありません」の印）。LINE の表示名は空白がないことが多いので、印が付きやすい。
- 後ろに足すときは、名簿にもういる account の人は入れない（2回押しても同じ人が2行にならない）。account のない人は見分けられないので入れる（同じ呼び名には「同じ名前」の印が付く）。
- 試合表の `event_id`（名簿を入れた交流会）は、この PR では書かない。読む所がまだなく、中身を送る `PUT` とは別の書き方が要るため（残り）。

## R7. FR-M26（ログインの前に試す）は作らない

初めての運営が、ログインの前に貼り付け → 組む → 印刷を試し、保存と共有のときにログインを求める形。今の画面は、試合表をサーバーで作ってから名簿と設定・試合表・印刷を開く（`TableFrame`・`table-editor.ts`・担当の端末の ID）。ログインなしで動かすには、端末だけで持つ試合表の道と、ログインしたあとにその中身で試合表を作る流れ（IndexedDB の置き場所・送りの扱いを含む）が要り、この PR に入れると大きくなる。次の PR で作る（残り）。
