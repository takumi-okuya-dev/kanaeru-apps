# Research: 名簿を入れた受付の交流会を出す・ホーム画面のアイコン（match-007）

## R1. DB は変えない：`event_id` はそのまま、名前と日時の写しは中身に持つ【仮決め】

- `match_table.event_id`（0021）は `event.id` を指す外部キーで `ON DELETE SET NULL`、索引 `match_table_event_id_idx` つき。AD-25「交流会の ID を持つ（任意。交流会が消えたら null）」のとおりで、列を変える必要はない。
- 交流会が消えると列は空になるので、列だけでは「どこから入れたか」を出せない。名前と日時の写しが要る。列を足す（DB の変更・先に小さな DB の PR）代わりに、試合表の中身（JSON）に任意の `receptionEvent`（交流会の ID・入れたときの名前〈200文字まで。交流会の名前の上限 100 文字より大きくとる〉・始まりの日時）を足した。
- 中身に置くと、写しは担当の端末の送りの列（match-005）にそのまま乗る（電波がない間に入れ直しても、送ったときにつながる）。入れ直しも、ほかの直しと同じ版の番号で食い違いを止められる。
- 注意：中身の形は strict なので、写しの入った中身を前の版の API が読むと形が合わず 500 になる（前の版に戻したとき）。match-003 の `archive`・match-006 の `accountId` と同じ扱い。試合表アプリはまだ出していない（台帳で運営者だけ）ので、今は受け入れる。出したあとに中身の欄を足すときは、前の版が知らない欄を読み捨てる形を先に出すことを考える（残り）。
- 選ばなかった形：列を足す（`event_name`・`event_starts_at`）。DB の PR を先に分けることになり、写しは交流会の持ち主の情報なのに試合表の列が増える。中身の写しなら、送りの列と版の番号の仕組みをそのまま使える。

## R2. つなぐのはサーバー：送ったときに、入れてよい交流会のときだけ【仮決め】

- 写しは担当の端末が書くので、どの交流会の ID でも書けてしまう。`event_id` は、中身を直す `PUT` の中（同じトランザクション）で、写しの交流会が今つないでいる交流会と違うときだけ、match-006 の入れる窓口と同じ判定（`reception-link.ts` の `canImportEvent`：受付アプリが見え・今の利用者が交流会の主催者で・交流会と試合表の持ち主が同じ）を通ったときにつなぐ。入れる窓口（`routes-reception.ts`）も同じ関数に寄せた（判定を1か所にする）。
- 入れてよくないとき（入れたあとに主催者でなくなった・交流会を組織から外した・交流会が消えた・作った写し）は、`event_id` を空にする。送りは止めない（止めると担当の端末の送りの列が止まり、試合表そのものを直せなくなる。写しは中身に残り、画面は「交流会は見られません」と出す）。
- 確かめてから書くまでに交流会が消えると、外部キーで止まる。区切り（savepoint）の中で書き、止まったら空にする（`level-memory.ts` と同じ形）。
- 写しが同じ交流会のまま、あとで交流会を組織から外したなどで判定が変わっても、つながりは外さない（「名簿をどこから入れたか」は変わらないため）。開けるかは、読むたびに見る人ごとに決める（R3）。
- 選ばなかった形：入れる窓口（`GET …/reception-events/{eventId}`）でつなぐ（読む窓口が書くことになり、入れずに閉じても書かれる）。つなぐだけの窓口を別に足す（担当の端末の送りの列の外で書くことになり、電波がない間に入れたときにつながらない）。

## R3. 出す場所と見え方【仮決め】

- 出すのは運営の画面だけ：試合表の一覧（各行に「受付：{名前}（{日付}）から入れた」の文だけ。行は試合表へのリンクなので、受付アプリへのリンクは入れない）と、名簿と設定・試合表の題の下（`ReceptionEventNote.tsx`）。試合表はもともと持ち主と入れた組織の管理者・編集者しか読めない（AD-25）ので、出す相手もそれだけ。
- 受付アプリへのリンク：答えの `canOpen` が true（つないだ交流会が写しと同じ・今の利用者がその交流会の主催者か受付係〈一覧画面 `/admin/events/{eventId}` を開ける役目〉・受付アプリが見える）のときだけ。受付アプリの道は LIFF を始める道なので、画面の中の行き来にせず、ページを読み直すふつうのリンクにする（core-013）。
- `canOpen` が false：写しの名前と日付に「（交流会は見られません）」を添える（消えた・役目がない・受付アプリが見えないを分けない。ほかの人の交流会のことを漏らさない）。
- 送っていない入れ直しの間（中身の写しの交流会と、サーバーが答えた交流会が違う）は、名前と日付だけを出す（リンクも「見られません」も出さない）。
- 見るだけのページ（AD-26）・電波なしで渡す QR（AD-28）は、中身から呼び名・組み合わせ・進み具合だけを選んで作る形なので、写しは入らない（結合と単体のテストで確かめる）。
- 文の形は、入れる枠の交流会の選択肢と同じ「名前（日付）」。名前に日付が入っていても重ねて出す（どの日の交流会かを確かに分かるように）。

## R4. 入れ直し・貼り付けで置きかえたとき【仮決め】

- 受付の交流会から入れたら（置きかえても後ろに足しても）、その交流会の写しに置きかえる（いちばん新しく入れた交流会を出す）。
- フォームの貼り付け・CSV で名簿を置きかえたら、写しを外す（名簿はもう交流会から来ていない）。送ると `event_id` も空になる。
- 貼り付けで後ろに足しただけ・1人足す・QR の受付で入った人を足したときは、写しを残す（名簿の多くは交流会から来たまま）。

## R5. アイコンの絵【仮決め】

- 試合表そのものを絵にした：墨（`#3B3833`）の地に白い表を置き、名前の枠（横長の角丸）が4つずつ並んだ4行のうち、2行目（いまの試合）を墨にする。ほかの行の枠は `text-disabled`（`#C1BDB7`）。2つ目と3つ目の枠の間を広くして、2人ずつの組（ダブルス）を表す。シャトル・ラケット・ネットなど競技の形は入れない（テニス・卓球などにも使えるように）。
- 色は tokens.css の値だけ（primary・surface・text-disabled）。墨は DESIGN.md で「主のボタン・選んだ状態」だけの色だが、アイコンはアプリの外（ホーム画面）に出るものなので、プロダクトの色として地に使った。
- 文字は入れない（「試合表」の字は 180 画素では読めないため）。名前はホーム画面のラベル（manifest の `short_name`・`apple-mobile-web-app-title`）で出す。
- maskable は同じ絵を 0.86 倍にして、安全な円（直径 80%）の中に収めた。地の墨は端まで塗る（端末が丸・角丸・しずく形に切り抜いても、表は欠けない）。iPhone の apple-touch-icon は角の透けない四角（iOS が角を丸める）。
- PNG は `pnpm exec tsx e2e/scripts/render-match-icons.ts` で SVG から作る（E2E と同じ Playwright の Chromium・等倍・ちょうどの大きさ）。同じ SVG と同じ Chromium で2回作り、同じバイトになることを確かめた。SVG を直したときだけ手で流す（組み立て・テストでは流さない）。

## R6. manifest と見出しのリンク：public の `match/` に置き、運営の画面を開いている間だけ付ける【仮決め】

- 外枠の `index.html` はどのアプリの道でも同じなので、そこに manifest を書くと受付アプリなどにも効いてしまう。API が道ごとに `index.html` を書きかえる形は、共通（`platform/web`）を直すことになる。
- 選んだ形：manifest とアイコンを `apps/web/public/match/`（Vite がそのまま `dist/match/` に写す）に置き、見出しのリンク（manifest・`apple-touch-icon`・`apple-mobile-web-app-title`）は試合表の運営の画面の枠 `MatchGate` を開いている間だけ付け、離れたら外す（`use-home-screen.ts`。見るだけのページの `noindex` と同じ形）。道は `home-screen.ts` の1か所に置き、組み立ての設定もここを読む。
- 見るだけ・受付のページ（参加者が開くその日だけのページ）には付けない。manifest の始まりは運営の一覧 `/match/` なので、参加者がホーム画面に置くと運営の画面が開いてしまうため。
- `start_url`・`scope`・`id` は `/match/`（末尾の `/` つき）。Service Worker の範囲 `/match/` の中なので、ホーム画面から開くと電波がなくても開ける（match-005 R3 の「`/match` は範囲の外」を、ホーム画面からの入口では避けられる）。画面の道具は `/match/` でも一覧を出す（E2E で確かめた）。
- 色：`theme_color` は外枠の上の帯と同じ surface（白）、`background_color` は地の background（`#F8F7F6`）。値の食い違いは `home-screen.test.tsx` が tokens.css と比べて止める。
- CSP：画面の CSP は `default-src 'self'` で `manifest-src` は書いていないので、自分の源の manifest は読める。アイコンは `img-src 'self'`。CSP を直す必要はない（E2E で CSP の違反がないことを確かめる）。API は `.webmanifest` を `application/manifest+json`（Hono の型の一覧）、`/match/…` の静かなファイルを `Cache-Control: no-cache` で返す。

## R7. Service Worker に持たせる：組み立ての plugin に `publicFiles` を足す【仮決め・共通の変更】

- core-015 の plugin（`apps/web/scoped-service-worker.ts`）は、組み立ての束（JS・CSS と、そこから読む画像）だけを持つ。public のファイルは束に入らないので持たれない。
- `publicFiles`（public からの道の並び）を足し、名指ししたファイルを持つ道に足し、中身も版の印に入れる（アイコンを描き直すと新しい版になる）。名指ししたファイルがなければ組み立てを止める。`vite.config.ts` は試合表の Service Worker に `MATCH_HOME_SCREEN_FILES` を渡すだけ。
- 共通の変更なので本来は先に小さな共通の PR に分ける（並行開発の決まり 3-3）が、plugin を使うのは試合表だけで、足すのは任意の欄1つ（ほかの書き出し方は変わらない）なので、この PR に入れて PR の説明に書く。主催者が分けるべきと判断したら、`scoped-service-worker.ts`・`.test.ts` を先に出す。
- 選ばなかった形：Service Worker の本文（`sw.js`。試合表の領域）に道を直に書く（アイコンを描き直しても版の印が変わらず、古いアイコンを持ち続ける）。アイコンを画面のコードから読んで束に入れる（manifest は決まった道のアイコンを指すので、印つきの名前にできない）。

## R8. 実機の確かめ（残り）

- iPhone（iOS の Safari）の「ホーム画面に追加」は、追加したときの画面の見出しのリンク（`apple-touch-icon`・`apple-mobile-web-app-title`）と manifest を読む。どの道（一覧・試合表の中）で追加しても `/match/` から開くか、standalone で開くか、電波なしで開くか（Service Worker）、アイコンの角の丸めと見え方は、**実機で確かめる必要がある**（シミュレーターと E2E の Chromium では確かめられない）。iOS の版によって manifest の `start_url` を使うかが違う。
- Android の Chrome は、manifest の maskable のアイコン・`start_url`・インストールの案内を実機で確かめる。
- 見出しのリンクは画面が付けるので、ページを開いてすぐ（JS が動く前）にホーム画面に追加すると、リンクがまだないことがある。実機で困るなら、API が `/match/…` の外枠にだけリンクを書く形（共通の `platform/web`）を考える。
