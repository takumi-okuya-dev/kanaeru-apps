# Research: 試合表の表とアプリの登録（match-001）

2026-11-22 作成。答える人がいないため、PRD 試合表アプリと構成の決めごと（AD-3・AD-15・AD-16・AD-17・AD-19・AD-22・AD-25・AD-26・AD-28・AD-30）から AI が決めた（【仮決め】）。表の作りは受付アプリの交流会（`event_organization`）と予約（`booking_line_channel` の持ち主の CHECK）にそろえた。

## R1. 中身を1つの JSON にまとめ、DB は object だけを確かめる【仮決め】

**決めたこと**：名簿（呼び名・レベル・当日の印）・組み合わせ・進み具合・設定（試合の形・レベルの分け方・1試合の長さ・試合の時間）は `match_table.content`（jsonb）にまとめる。DB の CHECK は `jsonb_typeof(content) = 'object'` だけにし、形（人数や試合の数の上限・呼び名の長さ・レベルの code）は約束の zod で確かめてから書く（match-002）。

**理由**：

- AD-28 が「1つのまとまり（JSON）として `match_table` に持ち、`version` を付ける」と決めている。担当の端末が組み直した表をまるごと送る形なので、行に分けると、送るたびに消して足す処理が要る。
- 形を DB の CHECK に書くと、組み方や設定を足すたびに DB の変更が要る（DB の変更は小さく先に入れる決まりがあり、重い）。サーバーは中身を計算し直さず、形を確かめて持つだけ（AD-28）なので、zod の1か所で足りる。

## R2. 同じ変更の二重は、最後に受けた変更の ID と比べる【仮決め】

**決めたこと**：`match_table.last_change_id`（uuid）に、最後に受けた変更の ID を持つ。同じ ID がもう一度来たら、前と同じ答え（今の試合表）を返す（match-002）。

**理由**：担当の端末は1台で、送っていない変更は古い順に1つずつ送り、答えを待ってから次を送る（AD-28）。二重になるのは「受けたのに答えが届かなかった送り」を送り直すときだけで、それは最後に受けた変更。変更の ID の一覧の表を作るより小さい。担当が替わると前の担当の送りは `MATCH_NOT_EDITOR` で止まる。

## R3. 退会の手順は match-002 に入れる（この PR の外部キーで、退会は止まらない）【仮決め】

**決めたこと**：`match_table.owner_account_id` は CASCADE にする。組織に入れた試合表をその組織の管理者に引き継ぐ退会の手順（AD-22 の (2)・AD-25）は、試合表の窓口と同じ match-002 で足す。

**理由**：

- 引き継ぎは suite の `index.ts`（`findOrganizationAdmin`・`adminAfterWithdrawal`）を読む業務の処理なので、表だけの PR に入れると PR が大きくなる。
- この PR の段では、試合表を作る・組織に入れる窓口がないので、引き継ぐ試合表は生まれない。外部キーは CASCADE なので、account を消す処理が試合表の行で止まることもない（受付アプリの交流会のような RESTRICT の止まり方はない）。
- ほかの人自身の本人の記録（AD-19 の `409 ACCOUNT_OWNS_SHARED_RECORDS`）は、試合表にはぶら下がらない（受付の行は名前とレベルだけで account を持たない。覚えたレベルは本人の account の CASCADE）。

## R4. レベルの code【仮決め】

`advanced`（上級）・`intermediate`（中級）・`beginner`（初級）・`novice`（入門）。並びはフォームの「1上級」〜「4入門」の数字の順で、並びの番号を「段」にして、レベルの差（分けないときに1試合の差を2段以内にする。PRD FR-M6）を比べる。言葉は PRD 3章のとおり。

## R5. 札の期限を列に持つ【仮決め】

見るだけの札（AD-26）と受付の札（AD-30）は、どちらも SHA-256 と期限（`*_token_expires_at`）を持つ。期限は札を作るときに「その日の終わり（日本時間）」で決める。試合の日から毎回計算すると、試合の日を直したときに出した札の期限が黙って変わり、印刷した QR が思わぬ日に使える・使えなくなる。受付を締めた時刻（`join_closed_at`）は、札を作り直さずに受付だけを止めるため。

## R6. `/match` の仮の画面【仮決め】

アプリの登録のテスト（`router.test.tsx` の「アプリを開いたときの道は、道の木にある」）が `/match` の道を求めるので、準備中の案内だけを出す仮の画面を置く。台帳に行がない間は運営者だけに見え（AD-16）、match-002 で一覧と作るに置きかえる。試合表の道は LIFF を始めない（core-013）ので、この画面は `SessionGate` を使わない。

## R7. 消し方のまとめ

| 外部キー | 消し方 | 理由 |
|---|---|---|
| `match_table.owner_account_id` | CASCADE | 持ち主のデータ（AD-19）。組織の試合表は退会の段が先に引き継ぐ（R3） |
| `match_table.event_id` | SET NULL | 交流会には頼らない（AD-25） |
| `match_table_organization` の複合の外部キー | CASCADE | 持ち主が組織を抜けたら個人のものに戻す（AD-22・`event_organization` と同じ） |
| `match_level_memory` の3つ | CASCADE | 相手か本人がいなくなれば覚える意味がない |
| `match_join.match_table_id` | CASCADE | 試合表と一緒に消える（AD-30） |
