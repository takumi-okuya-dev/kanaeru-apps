# Research: 予約の名簿（booking-001）

2026-11-20 作成。答える人がいないため、PRD 受付アプリの予約と構成の決めごと（AD-3・AD-5・AD-7・AD-15・AD-19・AD-23）から AI が決めた（【仮決め】）。めぐる（`meguru-app`）の `specs/collect/`（名簿・まとめて貼る・名簿なしの受付）と `specs/people/001-people-memo`（CSV の取り込み・列の対応・同じ人の候補）を読んで参考にした（コードは写していない）。

## R1. 使い方の持ち方【仮決め】

**決めたこと**：`booking_setting`（`event_id` が主キー・`mode`）。行がなければ「受付だけ」。この版の `mode` は `reception`（受付だけ）・`roster`（名簿を使う）の2つ（CHECK）。主催者が切り替えると行を作るか直す（`reception` に戻しても行は消さない）。名簿の行は使い方と別に持ち、「受付だけ」の間は隠す：名簿の窓口は 409 `BOOKING_ROSTER_OFF`・ナビに「名簿」を出さない・受付係の「名簿に当てる」も出さない。「名簿を使う」に戻すと前の名簿が出る（FR-B13）。

**「自前で申込みを受ける」を足すとき**：その仕様で CHECK に `self_page` を足す（今の行は `reception`・`roster` だけなので、どの行も通る。[コードの書き方](../../../docs/rules/coding.md) 3 の「既存の行が通らないかもしれない制約」に当たらず、1回でよい）。定員・見せる範囲・受け付けるかの列は、空を許すか既定値つきで足す。画面の選択のカードは、その仕様で3つ目を出す。

**理由**：

- AD-23「使い方が受付だけの交流会では、booking は何も持たない（設定の行がなければ受付だけ）」に合わせ、今ある交流会は何もしなくても受付だけ（PRD 7章）。
- 受付だけに戻すとき行を消すと、あとで足す定員などの設定まで消える。`reception` の行を残す形なら、戻しても設定が残る。
- 今使わない値（`self_page`）を CHECK に先に入れると、窓口の入力で弾く作りが要り、取り違えの余地ができる。足すときの変更は小さい。

## R2. 入口と状態の値【仮決め】

- 入口 `entry_kind`：`manual`（手で足す）・`import`（取り込み。貼るも CSV も）・`walk_in`（飛び入り）。PRD の入口は「自前のページ・手で足す・取り込み」で、飛び入りは手で足すの1つだが、受付係の画面（S1）が「飛び入り」の数と印を出すので、別の値にした。自前のページ（`self_page`）は、その仕様で CHECK に足す。
- 状態 `status`：`confirmed`（確定）・`cancelled`（取り消し）。キャンセル待ち（`waitlisted`）・打診中（`offered`）は定員の仕様で CHECK に足す（R1 と同じく1回でよい）。
- 「来なかった」は状態に持たず、読むときに決める（R8）。

## R3. 媒体の選択肢【仮決め】

受付の「申し込みの媒体」（`connpass`・`peatix`・`direct`〈直接〉・`other`〈その他〉）を `@workspace/contracts/reception` から読んでそのまま使う（AD-23「同じ列挙を contracts から読む」）。モックアップの「こくちーず」「Google フォーム」は今の選択肢にないので「その他」を選ぶ。選択肢を足すのは受付の `checkin` の CHECK と画面を変えることになり、この仕様の目的と別なので、主催者に確かめてから別の変更で行う（足すなら booking の CHECK も同じ値に広げる）。

## R4. 取り込みの「すでにある」（同じものを2回取り込んでも増えない）【仮決め】

**決めたこと**：取り込み（貼る・CSV）の行ごとに、名前を前後の空白を消して、そろえた名前（`normalizeCheckinName`）を作る。名簿のうち **同じ交流会・入口が取り込み・同じ媒体** の行（取り消しも数える）を、そろえた名前ごとに数える。送られた行を上から見て、同じ名前の「すでにある」の数が残っていればそれを1つ使って「すでにある」、なければ「入る」。名前が空なら「名前が空」。見積もり（preview）と取り込みは同じ関数で決め、取り込みは交流会の設定の行を `FOR UPDATE` で押さえたトランザクションの中で決め直す（同時に2回押しても増えない）。

**理由**：

- 掲載サイトや Google フォームの CSV は、見出しや列が増えたり並びが変わったりする。行の全体を鍵にすると、同じ人が別の行として入る。名前と媒体なら、列が変わっても同じ人が同じ鍵になる。
- 同じ名前の別人が同じ CSV に2人いても、数で比べるので2人とも入る（1回目）・2回目は2人とも「すでにある」。
- 取り消した人も数えるのは、取り込み直しで取り消した人が戻ってくると困るため（取り消しは主催者の意思）。
- 手で足した行・別の媒体の行に同じ名前があっても「入る」にする（勝手にまとめない。FR-B24）。見積もりの行と名簿に「同じ名前があります」を出し、主催者がまとめられる（R7）。
- 名前の列が別の人に入れ替わる（例：掲載サイトで名前を直した）と別の行になる。そのときも同じ名前の印は付かないが、主催者が古い行を取り消せる。

**ほかの案**：CSV の行の全体のハッシュを鍵にする（列が変わると増える）・取り込みごとに前の取り込みを消して入れ直す（手で直した状態や当てが消える）。

## R5. CSV の読み方と、ファイルの受け取りの確かめ（[開発の流れの決まり](../../../docs/rules/development-flow.md) 2）

**決めたこと**：ファイルは画面（ブラウザ）の中で読み、サーバーに送らない・残さない。画面が送るのは、行の番号と、選んだ列の名前の文字だけ（JSON。1回に500行まで〈API の本文の上限 100KB に収まる数〉・名前は50文字まで〈チェックインの名前と同じ〉）。

- 読み方：`File.arrayBuffer()` → UTF-8（`fatal`）で読めなければ Shift_JIS（Excel で保存した掲載サイトの CSV のため）。BOM を外す。CSV の切り方は RFC 4180（`"` の囲み・`""`・囲みの中の改行・CRLF/LF）を booking の画面の中の小さな関数で行う（新しい依存を足さない）。
- 見出しは1行目。見出しが空の列は「（n列目）」と呼ぶ。行が500を超えたら、取り込まずに誤りを出す。ファイルの大きさは 5MB まで（画面で止める）。
- 名前の文字はチェックインの名前と同じ形（1〜50文字・前後の空白を消す）で、API が確かめる（`zod`）。名前の中身は HTML に差しこまない（React の文字として出す）。

**ファイルの受け取りの確かめの結論**：サーバーはファイルを受け取らないので、ファイルの形・大きさ・中身の害（マクロ・パスの細工）・保存の場所の確かめは当たらない。残る守りは、(1) 送る名前の数と長さの上限（API の約束）、(2) 書き出す CSV で式として読まれない形（`@workspace/csv`）、(3) 名前をログに出さない、(4) 画面で読むファイルの大きさの上限。どれも作業の一覧に入れた（tasks の T008〈約束の上限〉・T018〈書き出し〉・T023〈画面の上限〉と、それぞれの結合・単体・E2E のテスト）。`docs/security/` の対応表は、サーバーが受け取る形がないので直さない。

## R6. 列の対応を覚える【仮決め】

**決めたこと**：`booking_import_mapping`（`owner_account_id`・`header_key`・`name_column`・`application_source`）。持ち主は**交流会の持ち主**（PRD「持ち主ごとに覚える」。組織の編集者が取り込んでも、交流会の持ち主の対応として覚える）。`header_key` は見出しの並びを JSON の文字にしたもの（`JSON.stringify(headers)`）で、`(owner_account_id, header_key)` で一意。取り込むときに `mapping`（見出しと選んだ列）を一緒に送ると、上書きで覚える。画面は `GET …/import-mappings` で持ち主の対応をまとめて読み、同じ見出しの並びのものを選んでおく。見出しは50列まで・1つ100文字まで。

**理由**：見出し（フォームの設問の名前・掲載サイトの列の名前）は参加者の個人の情報ではないので、そのまま持ってよい。ハッシュにすると画面で同じかを比べにくい。

## R7. 同じ名前の印と、まとめる【仮決め】

- 印：その交流会の名簿のうち、取り消しでない行で、そろえた名前が同じ行が2つ以上あれば、その全部に `sameName: true`（受付の同じ名前の印と同じそろえ方）。
- まとめる（主催者だけ）：`POST …/entries/merge`（`{ keepEntryId, removeEntryId }`）。2つは同じ交流会で、そろえた名前が同じこと（違えば 400 `BOOKING_MERGE_NAME_MISMATCH`）。消す行の当てたチェックイン・アカウント・メモを、残す行になければ移す。消す行は**物理的に消さず**、状態を取り消しにして `merged_into_id` に残す行を入れる（名簿・人数・来なかった・当て・候補から隠す。取り込みの「すでにある」の数にだけは入れる。消すと、同じ CSV を取り込み直したときに人が戻り、SC-002 が破れるため）。まとめた先の行が消えると（本人のアカウントを消したとき）`merged_into_id` は空に戻り、取り消しの行として名簿に出る。状態は「どちらかが確定なら確定」。1つのトランザクションで行う。

## R8. チェックインとの当て（読むときに決める）【仮決め】

booking が reception の `listEventAttendees`（チェックインの ID・名前・アカウント・時刻・入れ方）を読み、名簿と合わせて決める（保存しない。AD-23）。

```text
1. 名簿の行の checkin_id がそのチェックイン → 当たった（手）。行の入口が飛び入りなら「飛び入り」
2. 行のアカウント = チェックインのアカウント（どちらも空でない）で、1で当たっていない行とチェックイン → 当たった（自動）
3. 残りのチェックインごとに、当たっていない確定の行で、そろえた名前が同じで、「ちがう人」にしていない行がちょうど1つ → 候補
4. ほか → 名簿にいない（名簿から選ぶ・飛び入りにする）
```

- 取り消しの行は当てない（候補にも名簿から選ぶにも出さない）。来た人が取り消しの行の人なら、主催者が戻してから当てるか、飛び入りにする。
- 「当てる」「名簿から選ぶ」は `checkin_id` に持つ（`booking_entry_checkin_id_unique`。同じチェックインを2つの行に当てられない）。行がもう当たっている（手か自動）・取り消し・チェックインがその交流会にない・チェックインがもう当たっている、は 409 か 404。
- 「ちがう人」は `booking_dismissal`（チェックインと行の組）に持つ。受付係の画面を複数の端末で開いても同じに見える。
- 来なかった：交流会の始まりの日の終わり（`endOfJstDate(startsAt)`）を過ぎ、確定で当たっていない行。
- 名簿の行の「来た」：当たったチェックインがある（手・自動・飛び入り）。

## R9. 受付の `index.ts` に足すもの（FR-B103 と飛び入り）

- `listEventAttendees(db, eventId)`：その交流会のチェックインした人 `{ checkinId, name, accountId, method, checkedInAt }`（古い順）。ほかのアプリ（試合表など）にも出す。名前は AD-6 の写し。
- `hasCheckedIn(db, eventId, accountId)`：その人がその交流会にチェックインしたか。
- `createManualCheckin(db, config, { eventId, enteredBy, input })`：手でのチェックインを作る（参加費・割引・金額の決め方は今の手でのチェックインの窓口と同じ。窓口もこの関数を使う形に直す）。booking は飛び入りと「名簿から選んで手でチェックイン」で、自分のトランザクションの `tx` を渡して呼び、同じトランザクションで名簿の行を書く。

受付は booking を読まない（依存は booking → reception → event）。

## R10. 権限【仮決め】

| 操作 | 主催者 | 受付係 |
|---|---|---|
| 使い方を読む | ○ | ○（ナビと画面のため） |
| 使い方を変える | ○ | — |
| 名簿を見る・1人足す | ○ | ○ |
| 貼る・CSV・列の対応・取り消しと戻す・まとめる・書き出す | ○ | — |
| 名簿に当てる（候補を当てる・ちがう人・名簿から選ぶ・当てを外す・飛び入り・名簿から選んで手でチェックイン） | ○ | ○ |

判定は event の `requireEventRole`（主催者・受付係）。部員とほかの人は 403、ない交流会は 404。名簿の行・チェックインは、道の交流会のものだけを読む（違えば 404）。

## R11. 消し方と退会【仮決め】

| 外部キー | 消し方 | 理由 |
|---|---|---|
| `booking_setting.event_id`・`booking_entry.event_id`・`booking_dismissal.event_id` | `CASCADE` | 名簿は交流会の持ち主のデータ（AD-19）。event の退会の段（suite のあと・アプリの領域の順で booking より先）が組織に入れていない交流会を消すと、名簿も一緒に消える。booking は event より先に流れないので、`RESTRICT` だと名簿のある交流会の持ち主が退会できない。AD-7 の「交流会を指す外部キーは RESTRICT」は「交流会を消す機能がない」ための決まりで、交流会を消すのは event の退会の段だけ（event-002 research R2）。チェックインのある交流会は、今までどおり `checkin.event_id`（RESTRICT）で止まり 409 |
| `booking_entry.account_id` | `CASCADE` | 本人の申込み（AD-7 の本人のデータ）。この版では空 |
| `booking_entry.entered_by`・`booking_dismissal.dismissed_by` | `SET NULL` | 「誰がしたか」（AD-7） |
| `booking_entry.checkin_id` | `SET NULL` | AD-23。チェックインを取り消すと当てが外れる |
| `booking_dismissal.checkin_id` | `CASCADE` | チェックインがなくなれば組も要らない |
| `booking_dismissal.entry_id` | `CASCADE` | 行がなくなれば組も要らない |
| `booking_import_mapping.owner_account_id` | `CASCADE` | 持ち主のデータ。組織の交流会を引き継いだ新しい持ち主は、覚え直す |

booking の退会の段（`withdrawal`）は、前の手順と最後の確かめで何もしない（外部キーが消す）。確かめの中身だけ出す：退会する人が持ち主の、組織に入れていない交流会に名簿の行があれば「組織に入れていない交流会の名簿（n人分）も一緒に消えます。」。組織に入れた交流会の名簿は、交流会と一緒に新しい持ち主に移る（何もしない）。

## R12. 設定で止めるか【仮決め】

`DOMAIN_FEATURES` の印は足さない。[コードの書き方](../../../docs/rules/coding.md) 2 の「大きな機能は設定で止められるように作る」のねらいは、出したあとに困ったときコードを戻さずに止めること。名簿は交流会ごとに主催者が選んだときだけ動き、既定の「受付だけ」の交流会の振る舞い（チェックイン・一覧・合計）は変えない。困ったら主催者が「受付だけ」に戻せば止まる。印を足すと、使っている主催者の名簿が設定1つで見えなくなり、かえって困る。

## R13. 画面の置き場所と差しこみの場所

- 道（管理の画面。`@workspace/contracts/booking` の `BOOKING_ROUTE_PATTERNS`）：名簿 `/admin/events/$eventId/roster`・入れる `/admin/events/$eventId/roster/import`・名簿に当てる `/admin/events/$eventId/roster/match`。交流会の中の道なので、event のナビの項目（参加者・合計など）も出る。
- ナビ：booking の `useNavItems` が、交流会の中で、使い方が「名簿を使う」で、役目が主催者か受付係のときだけ「名簿」を出す。ナビのために問い合わせを始めず、画面が読んだ使い方（問い合わせの鍵 `["booking", "setting", eventId]`）と交流会（event の鍵）から決める。
- 使い方を読む画面：(a) 準備の画面（A4）の「使い方」の節、(b) 受付の一覧画面（A3）の上の「名簿」の節（名簿を使う交流会だけ「名簿に当てる（n）」と名簿への入口を出す。ほかは何も出さない）。どちらも event・reception の画面に、持ち主が置く差しこみの場所（event の `registerSetupSection`・reception の `registerReceptionSection`）から出す。差しこみの場所は、同じ受付アプリの event・reception の画面に、この仕様で足す（[並行開発の決まり](../../../docs/rules/parallel-development.md) 3-1。受付アプリはこの作業場所が持つ）。
- 名簿から選んで手でチェックインする欄は、受付の画面の部品（`CheckinFields` と欄の確かめ）を reception の `index.ts` から読んで使う（作り直さない）。

## R14. 内訳に来なかった人を出すか【仮決め】

PRD FR-B102 は「名簿と内訳に出す」。受付の内訳（A3 の合計のタブ）は reception の画面で、reception は booking を読めない（AD-23）。この版では名簿の画面の人数の欄（確定・取り消し・来た・来なかった・媒体ごと）に出し、受付の内訳には出さない。内訳の画面に出すなら、reception の画面に差しこみの場所を置いて booking から節を出す（使ってから決める）。

## R15. 書き出しの列

名簿の CSV（主催者だけ。`@workspace/csv`）：名前・媒体・入口・状態・申し込んだ日時（日本時間）・来た（来た・来なかった・空）・入れた人・メモ。並びは申し込んだ日時の古い順。ファイルの名前は `roster`。

## R16. 名前と日時

- 申し込んだ日時は、手で足す・取り込み・飛び入りでは、行を作った時刻（`applied_at` の既定値）。CSV の申込みの日時の列は読まない（列が媒体ごとに違い、日時の形もまちまちなため）。
- 名前は前後の空白を消して持つ。そろえた名前は持たず、比べるときに作る（受付と同じ）。

## R17. 参加者の画面

この仕様で参加者の画面は足さない。受付の参加者のチェックインの画面（P1）は変えないので、ほかの人の名前は出ない（FR-B100）。

## R18. 受付係の画面の読み直し

「名簿に当てる」は、受付の一覧と同じく5秒おきに読み直す（夜間の停止の 503 だけ止める）。受付の画面の決め方（`isNightStop`・`receptionPollInterval`）を reception の画面の `index.ts` から出して使う（作り直さない）。

## R19. 作りながら決めたこと

- **取り込みの上限は500行**：API の本文の上限（`/api/v1` は 100KB。共通の `app.ts`）に、名前が50文字の全角でも収まる数にした。上限を上げるには本文の上限を窓口ごとに変える共通の変更が要るので、使ってから決める。CSV の見出しは50列・1つ100文字まで。
- **event の `index.ts` に2つ足した**：`findEventOwnerAccountId`（列の対応を交流会の持ち主ごとに覚えるため）と `listPersonalEventIds`（退会の確かめで、消える交流会の名簿の人数を出すため。event の退会の段の中の問い合わせを関数にして共に使う）。booking は event の表を読まない（AD-3）。
- **退会の確かめの名簿の人数**は、組織に入れていない交流会のものだけを数える。組織に入れていても、組織にほかに誰もいなくて消える交流会（event の確かめでは消えるほうに出る）の名簿は数えない（まれなので、文が少し少なく出るだけにした）。
- **名簿の画面は、狭い画面ではカード**にした（表を横に動かす枠は、中に押せるものがないと axe の `scrollable-region-focusable` に当たるため。受付の一覧と同じ形）。
- **「ちがう人」に取り消しはない**：組は残り、その行を手で「名簿から選ぶ」で当てれば当たる（候補に出ないだけ）。
