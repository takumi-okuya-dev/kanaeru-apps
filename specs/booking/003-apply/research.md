# Research: 自前の申込みページ（booking-003）

2026-11-20 作成。答える人がいないため、PRD 受付アプリの予約・構成の決めごと（AD-3・AD-5・AD-7・AD-14・AD-19・AD-22〜AD-24）・モックアップ（P1〜P3・P6・P7・A1）と booking-001・002 の仮決めから AI が決めた。【仮決め】は主催者の確かめを待つ。番号は spec.md の Clarifications と同じ。

## R1 使い方・受け付けるか・見せる範囲の持ち方【仮決め】

- **Decision**：`booking_setting.mode` の CHECK に `self_page` を足す（今の行は `reception`・`roster` だけなので、どの行も通る。[コードの書き方](../../../docs/rules/coding.md) 3 の「既存の行が通らないかもしれない制約」に当たらず、1回でよい。booking-001 R1 で決めた足し方）。列 `accepting boolean not null default false`（受付を開いているか）と `visibility text not null default 'public'`（`public`・`members` の CHECK）を足す。「受付中」は `mode = 'self_page' かつ accepting かつ 今 < 始まり` を読むときに決める。始まりを過ぎたら `accepting` は書きかえず、閉じたものとして扱う（PRD FR-B47「読むときに判定でよい」）。名簿の窓口の確かめ（booking-001 の `requireRoster`）は「受付だけでない」に広げ、自前でも名簿・取り込み・当てる画面を使える。
- **Rationale**：AD-3 の `booking_setting`（使い方・定員・見せる範囲・受け付けるか）。既定を閉じるにするのは、ステージングがないまま出す守り（主催者が開くまで外の人が申し込めない）。始まりで書きかえないのは、定時の処理を足さないため（AD-10・原則 V）。
- **Alternatives**：受付を閉じる時刻の列（締め切りの時刻を選べる。使ってから決める）。始まりを過ぎたら `accepting` を false に書きかえる（定時の処理が要る）。

## R2 参加者が開く道【仮決め】

- **Decision**：AD-14 の一覧（`packages/contracts/src/core/participant-paths.ts`）に `apply: "/e/$eventId"`・`entry: "/e/$eventId/entry/$entryToken"`（どちらも AD-14 に書いてある）と `myBookings: "/my-bookings"` を足す。どれも外枠のナビを出さない（`layout: "bare"`）。「LINE を使わずに申し込む」は申込みページの中の切り替えで、道を足さない。「部の予定」は `/my-bookings?tab=schedule`。
- **Rationale**：自分の申込みは参加者の画面で、管理の外枠（`/admin/…`）に置くとナビが出る。`-` を含む頭はアプリの key（英小文字と数字だけ）とぶつからないので、予約語は足さない（booking-002 R2 と同じ）。知らせのリンクは申込みページ（LINE の人）と札のページ（メールの人）を指し、自分の申込みの道を外から開かせる必要はないが、参加者の道は1か所に置く決まり（router.test が `bare` を確かめる）なので core に置く。
- **AD-14 を直す**：2026-11-20 の注で `/my-bookings` を足す。

## R3 ログインなしで見せる中身と、任意のログイン【仮決め】

- **Decision**：`GET /api/v1/booking/events/{eventId}/page` はログインを求めない。account の `findSessionViewer` でクッキーがあれば今の利用者を引き、あれば役目（event の `getEventRole`）・自分の申込み・案内の同意・名前の初めの値を足す。中身は交流会の名前・日時・会場・参加費（event の `getEventSummary`）・主催の名前（R17）・受付の状態（`open`・`closed`・`started`）・見せる範囲・友だち追加の URL・カレンダー。割引・Google フォーム・LINE グループのリンクは返さない（要約のうち、申込みに要るものだけ）。
- **Rationale**：PRD FR-B40（ログインなしで見られる）と SM-C1（ログインを強く求めすぎない）。event の要約の窓口（`/events/{id}/summary`）はログイン必須なので使わない。

## R4 1交流会1人1つと申し込み直し【仮決め】

- **Decision**：LINE の申込みは `booking_entry_event_id_account_id_unique`（booking-001 で置いた部分の一意）で1つ。申し込むときは設定の行を `FOR UPDATE` で押さえ、その交流会の自分の行を探す。なければ作る（入口 `self_page`・媒体 `direct`〈直接〉・入れた人は本人）。取り消しなら確定に戻し、申し込んだ日時を今に、名前を入れ直したものにする。確定なら何もしない（200 で今の申込みを返し、知らせは送らない）。名前の初めの値は、その人の最後の申込みの名前（どの交流会でも）、なければ account の表示名。
- **媒体を `direct` にする理由**：受付の申し込みの媒体（booking-001 R3）に「自前のページ」がない。`direct`（直接）がいちばん近い。入口（`self_page`）で自前と分かる。
- **Rationale**：手で足した行（名前だけ・アカウントなし）と自前の行は別の行になる。同じ名前の印（booking-001 R7）で主催者が気づき、まとめられる。

## R5 案内の同意【仮決め】

- **Decision**：`booking_consent`（`id`・`account_id`〈同意した人。CASCADE〉・`organization_id`〈CASCADE〉・`owner_account_id`〈CASCADE〉・`created_at`）。相手は `organization_id` か `owner_account_id` のどちらか1つ（CHECK。AD-23 の列の名前）。`(account_id, organization_id)`・`(account_id, owner_account_id)` で部分の一意。相手は交流会を組織に入れていれば組織、なければ交流会の持ち主（booking-002 R5 と同じ決め方）。
- 申し込むときの `consent: true` で作る（あれば何もしない）。`false` でもすでにある同意は消さない（外すのは自分の申込みの画面）。ページの答えに `consented` を入れ、同意していればチェックを出さず「案内を受け取っています（自分の申込みで外せます）」と出す。
- メールで申し込む人には出さない：アカウントがなく「いつでも外せる」を作るには、メールアドレスを申込みの外に持つことになる。案内は予約の知らせでないので、Constitution II（メールアドレスは予約の知らせのためだけ）に当たるおそれがある。モックアップ P7 のチェックは出さない。
- 案内を送る機能・主催者が同意した人数を見る画面は作らない（PRD 4.8 の外・次の仕様）。
- **Rationale**：組織ごとに閉じる（AD-23）。組織が消えれば同意も消え、持ち主が退会すれば個人の同意も消える（AD-19）。

## R6 申込み完了の画面【仮決め】

- **Decision**：申込みページのまま「申し込みました」の題に切り替える（道を変えない）。状態・カレンダーに追加（R16）・友だち追加（公式アカウントの設定の `basic_id` があれば `https://line.me/R/ti/p/{basicId}`。`@` は `%40` にする）・メールアドレスの欄（任意・`/me/contact`。主催者に見えない・いつでも消せる と書く）・「自分の申込みを見る」。
- 友だち追加の案内は、もう紐づいている人には「この公式 LINE で知らせを受け取れます」と出す（booking-002 の紐づけを読む）。
- **Rationale**：モックアップ P3。LIFF の `requestFriendship` は LINE ログインのチャネルに結びつく公式アカウントだけなので、組織ごとの公式アカウントには使えない。

## R7 取り消し【仮決め】

- **Decision**：`POST /api/v1/booking/me/entries/{entryId}/cancel`（本人の行だけ。ほかの人の行・ない行は 404）と `POST /api/v1/booking/entry-tokens/{entryToken}/cancel`（メールの申込み）。始まりを過ぎたら 409 `BOOKING_CANCEL_CLOSED`。状態を `cancelled` にする（行は残る）。メールで申し込んだ人が取り消したら、連絡のメールアドレス（`contact_email`）を消す（Constitution II：本人がアドレスを消せる。札は残し、札のページで「取り消し」を見せる）。そのあともう一度メールで申し込むと、新しい行になる（主催者が名簿で取り消した行はアドレスが残るので、もう一度申し込むと同じ行が確定に戻り、前の札は使えなくなる）【仮決め】。もう取り消しなら同じ答え。知らせは送らない（6つの知らせにない）。
- **Rationale**：PRD FR-B44「取り消せるのは始まりまで」。行を残すのは、主催者が名簿で戻せ、取り込みの「すでにある」と同じく取り消しの意思を残すため（booking-001 R4）。

## R8 部員だけの回【仮決め】

- **Decision**：見せる範囲が `members` の交流会は、event の `getEventRole` が `organizer`・`member` の人だけに答える（役目は主催者 → 受付係 → 部員の順に1つだけ決まるので、`staff` のときは交流会の組織のメンバーかを suite の `findMembership` で確かめ直し、メンバーなら答える。部員で受付係も兼ねる人が開けるように）。LINE で申し込むときは、設定の行を押さえたあとの見せる範囲で決め直す。受付係（`staff`）・役目のない人・ログインしていない人には、ページ・申込み・`.ics`・メールで申し込む の窓口が 403 `BOOKING_PAGE_MEMBERS_ONLY`（交流会の名前も返さない）。役目は要求のたびに引く（AD-5）。組織に入れていない交流会では `members` を選べない（400 `BOOKING_VISIBILITY_NEEDS_ORGANIZATION`）。組織から外したあとも `members` は残るが、部員がいないので主催者だけが見られる。
- **受付係を外す理由**：PRD FR-B45「部員と主催者だけ」。受付係は当日の受付のための役目で、申込みのためではない（助っ人は組織の外の人）。部員が受付係を兼ねるときは部員として見せる。
- 部員が抜けたあと：すでにある申込みは自分の申込みに残り、取り消せる（取り消しは本人の行かだけを見る）。

## R9 部の予定【仮決め】

- **Decision**：`GET /api/v1/booking/me/schedule`：suite の `listMemberships` で自分の組織を引き、event の `listOrganizationEvents`（足す。組織の並びに入れた交流会の ID・組織・始まり。始まりの日の終わりが今より後のもの）で交流会を引き、使い方が自前のものだけを、始まりの近い順に返す。行ごとに受付の状態・見せる範囲・主催（組織の名前）・自分の申込みの状態。
- event の `index.ts` に `listOrganizationEvents(db, organizationIds, from)` を1つ足す（booking は event の表を読まない。AD-3）。
- **Rationale**：PRD 11章の4（モックアップの案）。メンバーの役割に関係なく出す（管理者・編集者は主催者だが、部の予定として見たい）。

## R10 メールで申し込む【仮決め】

- **Decision**：
  1. `POST /api/v1/booking/events/{eventId}/email-requests`（ログインなし・`{ name, email }`）：受付中で見せる範囲が誰でもの交流会だけ。確認の待ち `booking_email_request`（交流会・名前・小文字にそろえたメールアドレス・札の SHA-256・期限24時間）を作り、確認のメールを送る。札は32バイトの乱数の base64url（booking-002 R3 と同じ作り方）。
  2. メールのリンクは `WEB_URL/e/{eventId}/entry/{札}`。画面は `GET /api/v1/booking/entry-tokens/{札}` で中身（`pending`〈確認の前〉・`entry`〈申込みがある〉）を読む。期限切れは 410、知らない札は 404。
  3. 「申込みを確定する」で `POST /api/v1/booking/entry-tokens/{札}/confirm`：交流会の設定の行 → 確認の待ちの順に `FOR UPDATE` で押さえ（メールで申し込む側と同じ順にして、デッドロックを避ける）、交流会がまだ受付中か確かめ、そのアドレスの申込み（`(event_id, contact_email)` の部分の一意）があれば札を新しいものに替えて確定に戻し、なければ行（入口 `self_page`・媒体 `direct`・アカウントなし・`contact_email`・`entry_token_hash`）を作る。確認の待ちを消す。確定の知らせを送る。
  4. 確定したあと、同じ札は `entry_token_hash` で申込みを指し、見る・取り消すに使う。札の期限は確認だけ（24時間）。申込みの札は、交流会の始まりのあとも状態を見るのに使える（取り消しは始まりまで）。
- GET で確定しない理由：メールの下見やウイルスの確かめの仕組みがリンクを先に開くと、本人が押していないのに申し込まれる。
- 答えを同じにする理由：アドレスを入れて「すでに申し込んでいます」と出すと、ほかの人がそのアドレスの人が申し込んだかを知れる。すでに申込みがある人も新しいリンクで確定でき（なくしたリンクの取り直しにもなる）、行は増えない。
- 確認のメールは `notifier.sendEmail` で守り（`NOTIFY_MODE`・`NOTIFY_ALLOWLIST`）を通す。知らせの記録（`booking_notice`）は申込みがないと書けない（`booking_notice_entry_check`）ので残さず、ログに交流会の ID と結果だけを出す。
- 送り主の名前・返信先は booking-002 R8（組織の名前か持ち主の表示名＋（kanaeru）・返信先は設定のアドレス）。
- 確認の待ちの後始末：新しい待ちを作るときに、期限切れの待ちを交流会に関係なくすべて消す（定時の処理を足さない。名前とメールアドレスを持つので、どの交流会のものも期限のあとに残さない）。

## R11 確認のメールの回数の制限【仮決め】

- **Decision**：(1) `/api/v1` の書く道の IP ごとの制限（共通。既定 60秒に100回）。(2) 同じ交流会・同じアドレスの確認の待ちが10分より新しければ、メールを送らず待ちも作らない（答えは同じ 202）。10分を過ぎていれば、前の待ちを消して新しい待ち・新しい札で送る（前のリンクは使えなくなる）。(3) 交流会ごとに、直近1時間に作った期限内の確認の待ちが200件に達したら 429 `BOOKING_EMAIL_REQUEST_LIMIT`（メールは送らない。1時間たてばまた受け付ける。24時間の期限の待ちを全部数えると、200件を送りつけるだけでその会のメールの申込みを24時間止められるため）【仮決め】。(3) は (2) より先に確かめる（先に (2) を見ると、上限のときに「そのアドレスの待ちがあるか」が答えの違い〈202 と 429〉で分かるため）。
- **Rationale**：ほかの人のアドレスにメールを送りつける使い方（メールの爆撃）を縛る。DB の数で縛るので、API が複数あっても効く。メモリーの数え（`platform/rate-limit`）はアドレスごとの鍵が増え、API を2つにすると効かない。

## R12 申込みの知らせ【仮決め】

- **Decision**：確定したとき（新しく作った・取り消しから戻した・メールの申込みを確定した）に `sendNotice(deps, { entryId, kind: "confirmed", links: { entry, calendar } })` を呼ぶ。`entry` は LINE の人は `WEB_URL/e/{eventId}`、メールの人は `WEB_URL/e/{eventId}/entry/{札}`（札の平文は確定の要求の中にだけある）。`calendar` は Google カレンダーのリンク。`sendNotice` の送り先に「行の連絡のメール（`contact_email`）」を足す（LINE の紐づけ → 行の連絡のメール → 本人の連絡のメール → なし）。例外はログに出して、申込みの答えは成功のまま返す。
- **Rationale**：PRD FR-B86（確定の知らせに「カレンダーに追加」）。booking-002 の Assumptions（メールで申し込む人のアドレスは申込みの側に持つ）。

## R13 主催者の画面【仮決め】

- **Decision**：準備の画面の「使い方」の節に3つ目のカード（「自前で申込みを受ける」：申込みページ・案内の同意・知らせ。定員とキャンセル待ちは次の版）。今の使い方が自前なら、その下に「申込みページ」の節：受付の状態（受付中・閉じています・始まりを過ぎたので閉じました）と「受付を開く」／「受付を閉じる」、見せる範囲（誰でも・部員だけ。組織に入れていなければ部員だけを選べず「組織に入れると選べます」）、ページの URL（ミニアプリの URL。LIFF ID のない手元は画面の源＋道）とコピー。窓口は `PUT /api/v1/booking/events/{eventId}/self-page`（主催者だけ・`{ accepting, visibility }`。使い方が自前でなければ 409 `BOOKING_SELF_PAGE_OFF`）。使い方を自前でないものに変えたら `accepting` を false にする（あとで自前に戻したときに、知らないうちに受付が開いたままにならないように）。`GET …/setting` に `accepting`・`visibility`・`started`・`inOrganization` を足す。
- ナビの「名簿」・受付の一覧画面の「名簿」の節・名簿の画面の入口の確かめは、使い方が受付だけでなければ出す（自前でも名簿を使う）。

## R14 名簿での見え方【仮決め】

- **Decision**：入口 `self_page` の言葉は「自前」。名簿の答え（`toRosterEntry`）は列を選んで作っているので、`contact_email`・`entry_token_hash` は出ない。CSV も同じ。まとめる（booking-001 R7）ときは、消す行の `contact_email`・`entry_token_hash` を、残す行になければ移す（先に消す行から外して一意の制約に当たらないようにする）。
- 主催者が名簿でメールの申込みを取り消す・戻すのは今までどおりできる（知らせは送らない。変更の知らせは booking-004）。

## R15 FR-B100（チェックインに自動で当たる）

booking-001 の当て方の2（行のアカウント＝チェックインのアカウント）がそのまま効く。メールの申込み（アカウントなし）は、名前の候補（当て方の3）か手で当てる。

## R16 カレンダー【仮決め】

- **Decision**：Google カレンダーのリンク `https://calendar.google.com/calendar/render?action=TEMPLATE&text=<名前>&dates=<始まりUTC>/<終わりUTC>&location=<会場>&details=<主催と申込みページ>`。`.ics` は `GET /api/v1/booking/events/{eventId}/calendar`（ログインなし・ページと同じ見せる範囲の決まり・使い方が自前のときだけ）で、`text/calendar; charset=utf-8`・`Content-Disposition: attachment; filename="event.ics"`。RFC 5545 の形（CRLF・75オクテットの折り返し・`\`・`;`・`,`・改行の escape・`UID:<eventId>@kanaeru`・`DTSTAMP`）。終わりは始まりの2時間後（交流会に終わりの時刻がない）。Google の API は使わない（PRD 8.2）。
- リンクを作る関数は `packages/contracts/src/booking/calendar.ts`（zod を読まない）に置き、API（知らせ）と画面が同じものを使う。
- **Alternatives**：終わりの時刻を交流会に足す（event の変更。主催者が要ると言ったら）。

## R17 主催の名前【仮決め】

組織に入れていれば組織の名前（suite の `findOrganization`）、なければ持ち主の表示名（account の `findDisplayNames`）。booking-002 の `holderNameOf` と同じ。持ち主のない今の交流会は空（画面は「主催」の行を出さない）。

## R18 席の残り

出さない。定員は booking-004 で `booking_setting` に列を足して入れる（空を許す列。今の行は「定員なし」）。ページの答えの形に席の欄を置かず、booking-004 で足す（今の画面は欄がなければ出さない）。

## R19 自分の申込みの一覧【仮決め】

`GET /api/v1/booking/me/entries`：本人の行（`account_id`）のうち、交流会の始まりの日（日本時間）の終わりが今より後のものを、始まりの近い順に。状態（確定・取り消し）・取り消せるか（確定かつ始まりの前）・交流会の名前・日時・会場・主催・Google カレンダーのリンク。入口が自前でない行（主催者が手で足した行に本人のアカウントが付いたもの〈まとめたとき〉）も本人の申込みとして出す。

## R20 退会

LINE の申込み（`booking_entry.account_id`）・案内の同意（`booking_consent.account_id`）は本人のデータで CASCADE（AD-7・AD-19）。退会の確かめの中身に「予約の申込み（n件）と案内の同意も消えます」を足す（どちらかがあるときだけ）。メールの申込み・確認の待ちはアカウントを持たず、交流会が消えると消える（CASCADE）。持ち主の退会で `owner_account_id` の同意が消える（持ち主のデータの相手がいなくなる）。

## R21 設定で止めるか【仮決め】

`DOMAIN_FEATURES` の印は足さない（booking-001 R12・002 R19 と同じ考え方）。交流会ごとの受付は既定で閉じ、主催者が開いたときだけ外の人が申し込める。知らせは `NOTIFY_MODE`（本番の既定は `off`）で止まる。困ったら主催者が受付を閉じる・使い方を変える。

## R22 作りの置き場所

- API：`apps/api/src/modules/booking/` に `apply-repository.ts`（設定の列・申込み・同意・確認の待ちの読み書き）・`apply.ts`（申し込む・取り消す・確認の待ち・札・ページの答え）・`calendar-ics.ts`（`.ics`）・`routes-apply.ts`（参加者の窓口）・`routes.ts`（主催者の `self-page` と `setting` の欄）。
- 札の作り方と SHA-256 は `line-link.ts` のもの（booking-002）を共に使う形に `tokens.ts` へ移す（`line-link.ts` は `tokens.ts` を呼ぶ）。
- 画面：`ApplyPage.tsx`（`/e/$eventId`）・`EntryTokenPage.tsx`（`/e/$eventId/entry/$entryToken`）・`MyBookingsPage.tsx`（`/my-bookings`）・`SelfPageSection.tsx`（準備の画面の申込みページの節）・`apply-api.ts`・`links.ts`（ミニアプリの URL）。

## R23 作りながら決めたこと

- **申込みの約束（`apply.ts`）は受付の約束を読まない**：名前の上限を受付の `CHECKIN_NAME_MAX` から読むと、申込みページの画面の束に受付の zod の形（`checkin.ts`）が入り、組み立て（rolldown）が受付の約束を入口の束から別の束に分けた。別の束は入口より先に動くので、画面の zod の設定（`lib/zod-config.ts` の jitless）より先に形が作られ、zod が eval を試して CSP の違反（`script-src eval`）が出た（E2E が見つけた）。`APPLY_NAME_MAX = 50` を `apply.ts` に持ち、`apply.test.ts` が受付の値と同じかを見張る。束の分け方に頼らない直し（zod の設定を別の入口にする・組み立ての設定）は共通の変更なので、残したことに書く。
- **名前の初めの値**：前の申込みの名前（どの交流会でも、いちばん新しいもの）→ LINE の表示名（R4 のとおり）。受付のチェックインの名前は reception の表なので読まない。
- **申込みページの部員だけの回でログインしていない人**：ページは中身を返さない（403）。画面は「部員の方は LINE でログイン」を出す。
- **自分の申込みの一覧の取り消し**：本人の行なら、入口が自前でない行（主催者がまとめてアカウントが付いた行）も取り消せる（R19）。
- **メールで申し込む答え**：送り直しの間隔の中（10分以内の2回目）も 202。メールの結果（送った・止めている・許可リストにない・準備がない）は答えに出さず、ログに交流会の ID と結果だけを出す（R10）。
- **確定の知らせのリンク**：LINE の人は申込みページ（`WEB_URL/e/{eventId}`）、メールの人は札のページ。自分の申込みの道（`/my-bookings`）は知らせに入れない。
- **booking-002 の画面の単体のテスト1つ**（設定がなければ3つの欄のフォーム）が、全部のテストを一緒に流すと重さで時間切れになることがあったので、待つ時間を延ばした（中身は変えていない）。

## 計画のときのセキュリティの確かめ（[開発の流れの決まり](../../../docs/rules/development-flow.md) 2）

ログインなしの窓口・メールのリンクの札・外へ送るメールを持つので、`security-audit` スキルの観点（入力の境界・認証と認可・札とセッション・CSRF・回数の制限と送りつけ・情報の漏れ・ログ・列挙）で確かめた。

| # | 見つけたこと（起こりうること） | 対策 | 確かめ |
|---|---|---|---|
| S1 | 札の推測・総当たり | 32バイトの乱数（base64url）。DB は SHA-256 だけで比べる（一意の索引）。窓口は `/api/v1` の IP ごとの制限 | 単体（札の長さ）・結合（DB に平文がない） |
| S2 | 札が DB・ログ・記録から漏れる | DB は SHA-256 だけ。ログは道の定義の形（実際の札を出さない。組み立ての決まり）。領域のログに札・アドレス・名前を出さない。知らせの記録に本文がない | 結合（ログに札とアドレスがない） |
| S3 | 札の URL が外の源へ漏れる（Referer） | 画面の `Referrer-Policy: strict-origin-when-cross-origin`（外へは源だけ。`platform/web`）。外へのリンク（Google カレンダー・友だち追加）は `rel="noreferrer"` | 読み合わせ |
| S4 | Cloud Run の要求の記録（基盤のログ）に、札のページの URL が残る | 消せない残りの危うさ。札の力は1つの申込みを見る・取り消すだけ・確認は24時間・ログを見られるのは運営だけ（Cloud Logging の権限）。quickstart に書く | 読み合わせ |
| S5 | メールの下見の仕組みがリンクを開いて、勝手に申し込む・取り消す | GET は読むだけ。確定と取り消しは画面のボタンの POST だけ | 結合（GET で行ができない） |
| S6 | ほかの人のアドレスへ確認のメールを送りつける（メールの爆撃） | 同じ交流会・同じアドレスは10分に1通・交流会ごとの待ちは直近1時間に200件まで・IP ごとの制限・守り（`NOTIFY_MODE`）を通す。メールの中身は交流会の名前と確認のリンクだけ | 結合（10分以内の2回目は送らない・200件で 429） |
| S7 | アドレスの申込みがあるかを、答えの違いで知る（列挙） | 確認のメールの窓口の答えは、申込みがあってもなくても、10分以内の2回目でも同じ（202）。上限の確かめを10分の確かめより先にし、上限のときはどのアドレスも 429。違いはメールの中だけ | 結合 |
| S8 | 二重の申込み（同時に2回押す・2つの端末） | `(event_id, account_id)`・`(event_id, contact_email)`・`entry_token_hash` の部分の一意と、設定の行の `FOR UPDATE`。2つ目は同じ答え | 結合（2回で1行） |
| S9 | 部員だけの回の中身が外に見える（ページ・`.ics`・自分の申込み・部の予定） | ページ・申込み・`.ics`・メールで申し込む の窓口は要求のたびに役目を引き、主催者と部員のほかは 403 で中身を返さない。部の予定は自分がメンバーの組織だけ。自分の申込みは本人の行だけ | 結合（外の人・受付係・ログインなしは 403） |
| S10 | CSRF（ほかのサイトから申し込ませる・取り消させる） | 組み立ての `csrf`（フォームの形を止める）と Origin の確かめ（`/api/v1` の状態を変える道）。窓口は JSON だけを受ける。クッキーは `SameSite=Lax` | 結合（ほかの源の Origin は 403。組み立ての既存のテスト） |
| S11 | ほかの人の申込みを取り消す（IDOR） | 本人の窓口は `account_id` が今の利用者の行だけ（違えば 404）。札の窓口は札の SHA-256 で1つの行だけ | 結合 |
| S12 | 主催者・受付係が参加者のメールアドレスを読む | 名簿・CSV・当てる画面の答えは列を選んで作る（`contact_email` を読まない）。確認の待ちは窓口から読めない | 結合（名簿・CSV にアドレスがない） |
| S13 | 入れた名前・アドレスでの差しこみ（XSS・メールのヘッダー・`.ics`） | 名前は zod（1〜50文字・前後の空白）と React の文字。アドレスは zod のメールの形（改行を含まない）。`.ics` は RFC 5545 の escape（`\`・`;`・`,`・改行）と折り返し。Google のリンクは `URLSearchParams` | 単体（`.ics` の escape）・結合 |
| S14 | 受付を開く前・閉じたあと・始まりのあとに申し込ませる | 申し込む・確定する窓口は、書く前に設定の行を押さえて受付中かを決め直す | 結合 |
