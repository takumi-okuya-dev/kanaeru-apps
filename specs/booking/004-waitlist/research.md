# Research: 定員・キャンセル待ち・期限つきの繰り上げ・変更と中止の知らせ（booking-004）

2026-11-20 作成。答える人がいないため、PRD 受付アプリの予約（4.5・4.6・5.4・8.1）・構成の決めごと（AD-3・AD-5・AD-10・AD-14・AD-23・AD-24）・モックアップと booking-001〜003 の仮決めから AI が決めた。【仮決め】は主催者の確かめを待つ。番号は spec.md の Clarifications と同じ。

## R1 定員と媒体の枠の持ち方【仮決め】

- **Decision**：`booking_setting.capacity integer`（空＝定員なし。CHECK `capacity is null or capacity between 1 and 1000`）。媒体の枠は `booking_quota`（`event_id`〈CASCADE〉・`application_source`・`seats`〈1〜1000〉・`manage_url`〈任意・500文字まで・`http(s)://` で始まる〉・`(event_id, application_source)` で一意）。枠を置ける媒体は受付の申し込みの媒体のうち直接（`direct`）を除く `connpass`・`peatix`・`other`（直接は自前のページと電話などの申込みで、外の媒体ではないため）。窓口は `PUT /api/v1/booking/events/{eventId}/capacity`（主催者だけ・`{ capacity, quotas }` を丸ごと置きかえる）。枠の合計は定員まで（400 `BOOKING_QUOTA_OVER_CAPACITY`）、定員がないのに枠は置けない（同じ 400）。
- 使い方が「名簿を使う」でも入れられる。そのときは人数の目安と超えた人数だけ（PRD FR-B11）。キャンセル待ち・打診・知らせは自前のときだけ（PRD 4.5 の頭書き）。
- **Rationale**：AD-3 の `booking_setting`（定員）・`booking_quota`（媒体の枠）。上限1000は、交流会の規模（数十人）に対して十分で、打ち間違い（16000）を止めるため。
- **Alternatives**：枠を直接にも置ける（自前のページの席を決める）→ 自前の残りは「定員 − ほか」で決まるので要らない。

## R2 埋まった席・自前の残り・枠を押さえるのをやめるとき【仮決め】

- **Decision**：
  - 埋まった席 = 確定（`confirmed`）＋打診中（`offered`）。入口（自前・手・取り込み・飛び入り）を問わない（PRD FR-B61）。
  - 枠のまだ埋まっていない席 = 枠ごとに `max(席の数 − その媒体の確定＋打診中, 0)` の和。
  - 自前の残り = 定員 − 埋まった席 − 枠のまだ埋まっていない席（負なら0として見せる）。
  - **一度満員になったら、枠を押さえるのをやめる**：埋まった席が定員に届いたのを初めて見たとき（書く処理の中）に `booking_setting.quota_released_at` を入れる。入ったあとは、枠のまだ埋まっていない席を引かない。
- **枠を押さえるのをやめる理由**：UJ-4（Peatix の1人が取り消すと森さんに打診が届く）。満員のとき主催者に「Peatix を止めて」と出すので、そのあと Peatix で空いた席を Peatix のために押さえ続けると、だれも埋めない席が残る（SM-3「席が空いたまま始まった回」）。主催者が Peatix を止め忘れて二重に売れたら「n人超えています」で気づける。
- **Alternatives**：枠ごとに「止めた」の印を主催者が押す（操作が増える。使ってから決める）。定員を増やしたら押さえを戻す（増やした席は FR-B64 のとおりキャンセル待ちに回すので戻さない）。

## R3 満員の画面と止める媒体【仮決め】

- **Decision**：設定の答え（`GET …/setting`）に `seats`（定員があるとき）：`{ capacity, filled, confirmed, offered, waitlisted, selfRemaining, over, full, quotasReleased, sameDay, quotas: [{ applicationSource, seats, filled, remaining, manageUrl }], stopSources: [{ applicationSource, manageUrl }] }`。`full` は埋まった席 ≥ 定員。`stopSources` は満員のとき、枠を決めた媒体と、名簿に取り消しでない申込みがある直接でない媒体（URL は枠にあれば）。`over` は `max(埋まった席 − 定員, 0)`。
- 画面（準備の画面の定員の節・名簿の上）：満員なら「満員です。次の媒体の受付を止めてください：Peatix（管理ページを開く）」、自前の残りだけ0なら「自前のページの席は埋まりました。キャンセル待ちを受け付けています」と枠の残り、超えたら「n人超えています（勝手に取り消しません）」。
- **Rationale**：PRD FR-B62・B63・11章の5（主催者への知らせは作らず画面に出す）。Threads アプリの掲載の記録は読まない（アプリをまたがない。FR-B62）。

## R4 キャンセル待ちの並びと入り方【仮決め】

- **Decision**：
  - `booking_entry.status` の CHECK に `waitlisted`（キャンセル待ち）・`offered`（打診中）を足す（今の行は `confirmed`・`cancelled` だけなので、どの行も通る。1回でよい）。
  - 並び = `waitlisted` の行を `applied_at` の古い順・同じ時刻は ID の順。何番目かは読むときに数える（保存しない）。取り消しから申し込み直すと `applied_at` が今になる（booking-003 R4）ので、最後に並ぶ。
  - 自前の申込み（LINE・メールの確定）は、書く前に片付け（R9）と打診をしてから、自前の残りが1以上で、キャンセル待ちがいないか当日の空きなら確定、ほかはキャンセル待ち。もうキャンセル待ちの人がもう一度申し込んでも何もしない（当日の空きなら確定。R7）。
  - 主催者が手で足すとき（自前で定員がある・満員）：入力 `waitlist: true` でキャンセル待ちに入れる（画面は満員のときだけ「定員を超えて足す」〈既定〉と「キャンセル待ちに入れる」を出す。PRD FR-B20）。取り込み・飛び入りはいつも確定（超えたら超えた人数を出す。FR-B63）。
- **Rationale**：PRD 3章（キャンセル待ち＝満員のときに自前のページで申し込んだ人の並び〈申し込んだ順〉）。

## R5 打診の表と、同時に走ったとき【仮決め】

- **Decision**：`booking_offer`（`id`・`event_id`〈CASCADE〉・`entry_id`〈CASCADE〉・`status`〈`pending`・`accepted`・`declined`・`expired`・`withdrawn`〉・`deadline`・`token_hash`〈メールの人の返事の札の SHA-256。空でなければ一意〉・`offered_by`〈手で打診した主催者。自動は空。SET NULL〉・`responded_at`・`created_at`・`updated_at`）。待っている打診は申込みごとに1つ（`booking_offer_entry_id_pending_unique`：`status = 'pending'` の部分の一意）。索引 `(status, deadline)`（定期の仕事が期限切れを探す）・`event_id`。
- 打診すると、申込みを `offered` にして打診の行を `pending` で作る。参加で `accepted`・申込みは確定、辞退で `declined`・取り消し、期限切れで `expired`・取り消し、主催者が確定・取り消し・中止したら `withdrawn`。
- **同時に走ったとき**：席を数えて打診する処理（片付け）は、いつも `booking_setting` の行を `FOR UPDATE` で押さえたトランザクションの中で、押さえたあとに読み直した行から決める（申込み・返事・取り消し・主催者の操作・定期の仕事のどれも同じ関数）。2つ目は1つ目の結果を読むので、二重に打診しない・定員を超えて打診しない。部分の一意は二重目の守り。知らせは、そのトランザクションが変えた行の分だけ、確定のあとに送る（ロールバックした分は送らない）。
- **Rationale**：AD-3 の `booking_offer`（打診と返事の期限）。booking-001・003 が名簿を書くときに同じ行を押さえている（形をそろえる）。

## R6 返事の期限の決め方（日本時間）【仮決め】

- **Decision**（`deadline.ts` の `offerDeadline(now, startsAt)`。日本時間は UTC+9 の固定〈夏時間なし〉で、サーバーの時刻帯に頼らない）：
  1. `d = now + 24時間`
  2. `d` が日本時間の **0時より後・9時より前**（0:00 ちょうどと 9:00 ちょうどは含まない）なら、その日の 9:00 にする（PRD FR-B65）
  3. `d` が始まりの2時間前より後なら、始まりの2時間前にする（ちょうど2時間前はそのまま。PRD FR-B65【仮決め】）
  4. 3 の結果が日本時間の 0時より後・9時より前なら、その日の 0:00（前の夜の24時）にする【この版の仮決め】
  5. `d − now` が1時間に足りなければ打診しない（`null`。当日の空き。ちょうど1時間は打診する。PRD FR-B67）
- **4 を足した理由**：始まりが 10:00 の会で 3 の結果が 8:00 になると、DB が0時〜8時に止まる（AD-10）ので、本人は0時から8時まで答えられず、定期の仕事も9時まで動かない。期限を「8:00」と見せるのは誤り。0時（前の夜の24時）にすれば、期限は答えられる時間の中にある。PRD 5.4・AD-24 の「期限は夜に切れない形で決める」に合う。
- 0時ちょうどは「その日の24時」として夜に含めない（DB は0時に止まるので、23:59 までに答えればよい）。9時ちょうどは夜に含めない（DB は8時に動き、定期の仕事は9時から）。
- 日時の変更で打診の期限は変えない。返事は始まりの前までしか受けない（始まりが早まったときの守り）。
- **Alternatives**：4 を足さず PRD の文のまま（期限が止まっている時間に落ちる）。夜の打診を朝まで待つ（打診が遅れ、席が空いたまま始まりやすい）。

## R7 当日の空き【仮決め】

- **Decision**：片付けのとき、自前の残りが1以上でキャンセル待ちがいて、`offerDeadline` が `null`（1時間取れない）なら、打診をやめる。
  - 申込みページの `seats.sameDay = true`（「当日の空き：残り n 席（先着）」）。新しい申込みは、残りがあれば確定（キャンセル待ちを待たない）。
  - キャンセル待ちの人は、自分の申込み・札のページの「参加する」で、残りがあれば確定（なければ 409 `BOOKING_NO_SEAT`）。
  - キャンセル待ちの人に「当日の空きが出ました」（知らせの種類 `same_day` を足す。`booking_notice_kind_check` を広げる）を、交流会ごとに1回だけ送る（`booking_setting.same_day_notified_at`）。
- 1回だけにする理由：PRD SM-C2（送りすぎない）。2回目の空きは、知らせを受けた人がページで見られる。
- `same_day` は PRD FR-B80 の6つの外だが、FR-B67 が「当日の空きが出ました」を知らせると決めているので足す。

## R8 打診への返事【仮決め】

- **Decision**：
  - LINE の人：`POST /api/v1/booking/me/entries/{entryId}/respond`（`{ answer: "accept" | "decline" }`。本人の行だけ）。
  - メールの人：`POST /api/v1/booking/entry-tokens/{entryToken}/respond`（同じ入力）。札は申込みの札か、打診の知らせの返事の札（`booking_offer.token_hash`）。札のページの読む・取り消すも、返事の札で同じに使える。
  - 参加：打診中で期限の前・始まりの前なら確定（打診は `accepted`）。確定の知らせを送る。キャンセル待ちで当日の空きの残りがあれば確定（R7）。
  - 辞退：打診中なら取り消し（`declined`）にして次の人に打診する。キャンセル待ちの人の辞退は取り消しと同じ。
  - 期限の後：410 `BOOKING_OFFER_EXPIRED`（先に片付けて取り消しにし、次の人に打診する）。打診中でもキャンセル待ちでもない：409 `BOOKING_OFFER_NOT_PENDING`。
  - 取り消し（booking-003 の窓口）は、確定・キャンセル待ち・打診中のどれでも始まりまでできる。打診中の取り消しは辞退と同じに次へ回す。
- 返事の札を打診ごとに作る理由：打診は定期の仕事でも起きるので、申込みの札の平文（確定のときだけ手にある）を知らせに入れられない。申込みの札を作り直すと、前のメールのリンクが使えなくなり、送れなかったとき（`off`）に本人が申込みを開けなくなる。返事の札は申込みの札と同じ力（その申込みを見る・取り消す・返事をする）だけを持つ。
- LINE の人の返事のリンクは自分の申込み（`WEB_URL/my-bookings`）。申込みページでも打診中と期限を出し、自分の申込みへの入口を出す。

## R9 期限切れを取りこぼさない（定期・書く・読む）【仮決め】

- **Decision**：
  1. **定期の窓口** `POST /api/v1/booking/jobs/tick`：threads-002 と同じ形（`DomainRouteDeps.isJobRequest` で `Authorization: Bearer <JOB_TRIGGER_SECRET>` を時間の差が出ない比べ方で確かめ、合わなければ 404〈窓口があることを知らせない〉。組み立ての機械の道〈`/api/v1/<領域>/jobs/…`〉として、アプリが切のときだけ止まる）。対象は、使い方が自前で中止していない交流会のうち、待っている打診かキャンセル待ちがあるもの、または最後に知らせた日時が今の1日前より後のもの。交流会ごとに1つのトランザクションで片付け（期限切れ → 打診 → 当日の空き）と変更の知らせ（R10）を行う。答えは数だけ（交流会・期限切れ・打診・当日の空き・変更）。Cloud Scheduler は10分おき・日本時間 9時〜23時台（DB が動いている時間。AD-10・AD-24）。
  2. **書く窓口**：申込み・返事・取り消し・主催者の操作（状態・手で打診・定員・中止・手で足す・取り込み）は、どれも同じ片付けの関数を先に（か後に）通す。期限を過ぎた返事は、片付けたあとに 410。
  3. **読む窓口**（申込みページ・自分の申込み・札のページ・名簿・設定）は書かない（GET は何も書かない。booking-003 S5）。期限を過ぎた打診は「期限切れ」として見せ（返事のボタンを出さない・席を押さえない）、自前の残りがあってもキャンセル待ちがいれば新しい人はキャンセル待ち（申し込むと書く窓口が片付けてから決める）。
- **Rationale**：AD-24（定時の処理は Cloud Scheduler からジョブの合言葉つきの窓口）。定期の仕事が止まっても（夜・失敗）、書く窓口と読む窓口で期限が守られる。
- **Alternatives**：読むときに書く（GET で片付ける）→ メールの下見の仕組み・クローラーが開いても状態が変わる。booking-003 の決まり（GET は書かない）を守る。

## R10 日時や場所の変更（event を直さない形）【仮決め】

- **Decision**：
  - booking が `booking_setting.notified_starts_at`・`notified_venue`（最後に知らせた、または使い始めた日時と場所）を持つ。使い方を自前にしたときと、空のまま見つけたとき（定期の仕事）に、今の要約で埋める（知らせない）。
  - event の要約（`getEventSummary`）の `startsAt`・`venue` が、持っているものと違えば「変更あり」。設定の答え（`change`）に前と今を出す（主催者の帯）。
  - `POST /api/v1/booking/events/{eventId}/change-notice`（主催者だけ・`{ notify: boolean }`）：`notify: true` なら確定・打診中・キャンセル待ちの申込みに `changed`（前の日時か場所。変わったものだけ）を送る。どちらでも、持っているものを今に合わせる。変更がなければ 409 `BOOKING_NO_CHANGE`。
  - 定期の仕事：変更を初めて見たら `change_detected_at` を入れ、それから30分たっても主催者が選んでいなければ、`notify: true` と同じに送る。変更が戻ったら（前と同じ）`change_detected_at` を消す。
- **event を直さない理由**：AD-23（event は booking を知らない）。event の更新のあとに呼ぶ差し込み口を event に置くと、event の `index.ts`・道を直す共通の変更になり、ほかの領域のセッションとぶつかる。比べる形なら、booking の中だけで済み、ほかの入口（今後の event の画面・MCP など）からの変更も拾える。
- 30分待つ理由：打ちまちがいを直す時間と、主催者が「知らせずに済ませる」を選ぶ時間。交流会を直したあとの画面は一覧へ戻る（event の画面）ので、主催者が帯を見ない日もある（UJ-6「日時を変えると、全員に届く」）。
- **Alternatives**：event の更新の窓口に差し込み口を置く（共通の変更）。画面（event の直す画面）のあとに booking の窓口を呼ぶ（event の画面を直す）。

## R11 中止【仮決め】

- **Decision**：event には中止の状態がない（AD-7：交流会を消す機能もない）。booking の「予約を中止する」：`POST /api/v1/booking/events/{eventId}/cancel-booking`（主催者だけ・使い方が自前）。`booking_setting.cancelled_at` を入れ、確定・打診中・キャンセル待ちの申込みを取り消しにし（打診は `withdrawn`）、それらに `cancelled_event` を送る。申込みページの受付の状態は `cancelled`（「この会は中止になりました」）で、申し込めない（409 `BOOKING_EVENT_CANCELLED`）・受付を開けない（同じ 409）。戻せない（間違えたら、主催者が名簿で行を戻す。知らせは送らない）。もう中止なら同じ答え。
- 受付（チェックイン）は変えない（受付は予約を知らない。AD-23）。

## R12 知らせの中身とリンク【仮決め】

| 種類 | いつ | リンク（LINE の人） | リンク（メールの人） |
|---|---|---|---|
| `confirmed` | 自前で確定・打診に参加・主催者がキャンセル待ちと打診中を確定・当日の空きで確定 | 申込みページ・カレンダー | 札のページ（手にある札）・カレンダー |
| `waitlisted` | 自前の申込みがキャンセル待ちに入った（何番目か）・主催者が手でキャンセル待ちに入れた | 申込みページ | 札のページ（確定のときの札） |
| `offered` | 打診（期限） | 自分の申込み（返事） | 返事の札のページ |
| `offer_expired` | 期限切れ | なし | なし |
| `changed` | 日時や場所の変更（前の日時か場所） | 申込みページ | なし（申込みのときのメールのリンクから見られる。札を作り直さない。R8） |
| `cancelled_event` | 中止 | なし | なし |
| `same_day` | 当日の空き（1回） | 自分の申込み | 申込みページ（ページは公開。メールの人は申込みのときのリンクから「参加する」） |

- 文面は `notice-templates.ts` に足す（`same_day`）。`entryStatus` の言葉に「キャンセル待ち」「打診中」を足す。
- 知らせの例外はログに出して、処理の答えは成功のまま（booking-003 R12）。
- 手で足した人・取り込みの人（アカウントもメールもない）は「送り先がない」。

## R13 送った知らせの一覧【仮決め】

`GET /api/v1/booking/events/{eventId}/entries/{entryId}/notices`（主催者だけ。受付係は 403）：`{ notices: [{ kind, method, result, createdAt }] }`（新しい順・200件まで）。`booking_notice` の列を選んで読む（本文・宛先はもともと持たない）。名簿の行の「送った知らせ」で開く。

## R14 主催者の手の操作【仮決め】

- **Decision**：
  - 「打診する」：`POST …/entries/{entryId}/offer`（主催者だけ・自前で定員がある・行がキャンセル待ち）。席がなくても打診中にする（主催者が決めたので。埋まった席が定員を超えたら超えた人数を出す）。期限は R6、1時間取れなければ 409 `BOOKING_OFFER_WINDOW_SHORT`（「確定にしてください」）。キャンセル待ちでなければ 409 `BOOKING_ENTRY_NOT_WAITLISTED`。打診の知らせを送る。
  - 「確定にする」：今の `PUT …/entries/{entryId}/status`（`confirmed`）。キャンセル待ち・打診中からなら打診を取り下げ、確定の知らせを送る。取り消しから戻すときは知らせない（booking-001・003 のまま）。
  - 「取り消す」：今の `PUT …/status`（`cancelled`）。打診中なら取り下げ、片付けで次の人に打診する。知らせは送らない（booking-003 R14）。
  - 状態の入力（`RosterStatusInput`）は `confirmed`・`cancelled` だけ（キャンセル待ち・打診中は窓口が決める）。
- 名簿の絞り込みに「キャンセル待ち」（キャンセル待ちと打診中を並びの順に）を足す。行に何番目か・打診の期限（期限切れなら「期限切れ（次の回で回します）」）。

## R15 定員を変えたとき

- 定員を増やす・枠を減らす・定員を空にする：保存のあとに片付け（空いた席の分だけ打診。定員なしなら全員）。
- 定員を減らす：取り消さない（超えた人数を出す。FR-B63）。新しい打診はしない。

## R16 画面【仮決め】

- 準備の画面の「申込みページ」の節の下に「定員とキャンセル待ち」の節（`CapacitySection`）：定員の欄（空＝定員なし）・媒体の枠（媒体・席の数・管理ページの URL を最大3行。足す・外す）・「定員を保存する」（主のボタン）・席の内訳（埋まった席・自前の残り・キャンセル待ち・満員・止める媒体・超えた人数）・変更の帯（「変更を知らせる」「知らせずに済ませる」）・「予約を中止する」（危ない操作。確かめの枠）。名簿を使う交流会では、定員と枠と内訳だけ。
- 名簿の画面：上に席の内訳と変更の帯（同じ部品）、絞り込みに「キャンセル待ち」、行に何番目か・期限・「打診する」「確定にする」・「送った知らせ」（開くと一覧）。満員のとき「1人足す」の欄に「定員を超えて足す」「キャンセル待ちに入れる」。
- 申込みページ：席の欄（「残り n 席」・「満員です（キャンセル待ち n 人）。申し込むとキャンセル待ちに入ります」・「当日の空き：残り n 席（先着）」）。ボタンの文は満員なら「キャンセル待ちに申し込む」。完了の画面に状態と何番目か。打診中なら期限と「自分の申込みで答える」。中止なら「この会は中止になりました」。
- 自分の申込み：状態の札（確定・キャンセル待ち〈n番目〉・打診中〈期限〉・取り消し）、打診中なら「参加する」（主のボタン）・「辞退する」、当日の空きなら「参加する」。
- 札のページ：同じ（返事のボタン）。
- 1画面に主のボタンは1つ（打診中のカードは「参加する」を主、ほかは二次）。押せる所は 44px 以上（`min-h-xl`）。

## R18 設定で止めるか【仮決め】

`DOMAIN_FEATURES` の印は足さない（booking-001〜003 と同じ）。定員は交流会ごとに主催者が入れたときだけ動く（入れなければ booking-003 と同じ）。知らせは `NOTIFY_MODE`（本番の既定は `off`）。定期の仕事は Cloud Scheduler の仕事を作るまで動かない（作っても、書く窓口と読む窓口で期限は守られる）。

## R19 退会

新しい表の外部キー：`booking_quota.event_id`・`booking_offer.event_id`・`booking_offer.entry_id` は CASCADE（交流会・申込みと一緒に消える）、`booking_offer.offered_by` は SET NULL（誰がしたか。AD-7）。退会の確かめの中身は変えない（打診は申込みの一部）。

## R20 作りながら決めたこと

- **準備の画面の「定員とキャンセル待ち」の節は開いたときに読む**：節（`CapacitySection`）は約束の zod の形（`CapacityInput`）で入力を確かめる。「使い方」の節（`ModeSection`）は event の差しこみの場所から準備の画面と一緒に最初に読まれるので、そのまま読むと画面の zod の設定（jitless）より先に形が作られ、CSP の eval の違反になった（E2E が見つけた。booking-003 R23 と同じ）。`React.lazy` で別の束にした。
- **枠の媒体の言葉は booking の約束に持つ**：`QUOTA_SOURCE_LABELS` を受付の約束から読まずに書き、`options.test.ts` が受付の言葉と同じかを見張る（同じ理由）。
- **取り消しの押さえる順**：参加者の取り消しは、行を押さえる前に設定の行を押さえる（申込みと同じ順。違う順で押さえると、同じ人の申込みと取り消しが同時に来たときにデッドロックになりうる）。
- **主催者の手の打診は受付を閉じていてもできる**。キャンセル待ちの繰り上げ（自動）も、受付を閉じたあとも続ける（spec の Edge Cases）。中止のあとはどちらもしない。
- **まとめるときの状態**：確定を優先し、なければ残す行の状態（残す行が取り消しなら消す行の状態）。消す行の打診は行と一緒に消えるので、残す行が打診中でないのに打診中にはしない（キャンセル待ちにする）。残す行の打診中を確定にしたら打診を取り下げる。
- **主催者が手でキャンセル待ちに入れた人にも `waitlisted` の知らせを積む**（アカウントもメールもないので「送り先がない」と記録される。記録で主催者が分かる）。
- **キャンセル待ちの人の「辞退する」は取り消しと同じ**（当日の空きの画面では「参加する」だけを出す）。
- **メールの人への変更の知らせにはリンクを入れない**（申込みの札の平文は手にない。申込みのときのメールのリンクで見られる）。前の日時・場所は変わったものだけを入れる。
- **定期の仕事は、知らせた日時と場所が空の自前の交流会を見つけたら、今の要約で埋める**（booking-003 で自前にした交流会。知らせない）。
- **名簿の画面も設定（`…/setting`）を読む**（席の内訳と変更の帯・満員のときの手で足す選び）。受付係にも内訳は見えるが、変更の帯のボタンは主催者だけ。

## 計画のときのセキュリティの確かめ（[開発の流れの決まり](../../../docs/rules/development-flow.md) 2）

定期の窓口・返事の札・競り合い（二重の打診・定員超え）・外へ送る知らせを持つので、`security-audit` スキルの観点（認証と認可・札・競り合い・回数の制限と送りつけ・情報の漏れ・ログ・列挙）で確かめた。

| # | 見つけたこと（起こりうること） | 対策 | 確かめ |
|---|---|---|---|
| S1 | 定期の窓口を外から呼ばれる（打診を早める・知らせを送らせる） | `isJobRequest`（`Authorization: Bearer <JOB_TRIGGER_SECRET>` を SHA-256 にそろえて時間の差が出ない比べ方）。合わなければ 404（窓口があることを知らせない）・ログに「合言葉の合わない要求」だけ。合言葉の設定がなければいつも 404。仕事は冪等（何度呼んでも、期限の来た打診と変更だけを片付ける） | 結合（合言葉なし・違う → 404・何も変わらない。合う → 片付く） |
| S2 | 定期の仕事と申込み・返事が同時に走り、二重に打診する・定員を超えて打診する | 片付けは設定の行を `FOR UPDATE` で押さえ、押さえたあとに読み直した行から決める。待っている打診は申込みごとに1つ（部分の一意）。知らせは確定したトランザクションが変えた行の分だけ | 結合（片付けを同時に2回 → 打診は1つ・知らせは1回。最後の1席に2人 → 1人が確定・1人がキャンセル待ち） |
| S3 | 期限を過ぎた打診に返事して確定する | 返事は押さえたトランザクションの中で、片付け（期限切れ）のあとに打診中かを決める。期限の後は 410。読む窓口も期限切れとして見せる | 結合（期限の1ミリ秒あと → 410） |
| S4 | 返事の札の推測・総当たり | 32バイトの乱数（base64url）。DB は SHA-256 だけ（一意の索引）。窓口は `/api/v1` の IP ごとの回数の制限 | 結合（DB に平文がない） |
| S5 | 返事の札が漏れて、ほかの人が参加・辞退する | 札の力は1つの申込みを見る・取り消す・返事するだけ（申込みの札と同じ）。外へのリンクは `rel="noreferrer"`・`Referrer-Policy`（booking-003 S3）。札のページの答えは `Cache-Control: no-store` | 読み合わせ |
| S6 | メールの下見の仕組みが返事のリンクを開いて、勝手に参加・辞退する | GET は読むだけ。参加・辞退は画面のボタンの POST だけ | 結合（GET で状態が変わらない） |
| S7 | ほかの人の申込みに返事する（IDOR） | LINE の人の返事は本人の行だけ（違えば 404）。札は SHA-256 で1つの行だけ | 結合 |
| S8 | CSRF（ほかのサイトから参加・辞退・中止させる） | 組み立ての `csrf` と Origin の確かめ（`/api/v1` の状態を変える道）。JSON だけを受ける。クッキーは `SameSite=Lax`。定期の窓口はクッキーを使わず合言葉だけ | 組み立ての既存のテスト |
| S9 | 受付係・部員が定員・手で打診・中止・送った知らせを使う | 主催者だけ（event の `requireEventRole(["organizer"])`。要求のたびに引く） | 結合（受付係・部員 → 403） |
| S10 | 送った知らせの一覧・名簿から、参加者のメールアドレス・本文・札が漏れる | 知らせの記録は種類・手段・結果・時刻だけ（本文・宛先を持たない）。答えは列を選んで作る | 結合（答えにアドレスがない） |
| S11 | 知らせの送りつけ（キャンセル待ちに何度も打診・当日の空きを何度も送る） | 打診は待っている打診が申込みごとに1つ。当日の空きは交流会ごとに1回。変更の知らせは「知らせた日時と場所」を合わせるので同じ変更に1回。守り（`NOTIFY_MODE`・許可リスト）を通す | 結合（同じ変更・当日の空きは1回） |
| S12 | 定員の入力で大きな数・負の数・形の違う URL（`javascript:`） | zod（定員 1〜1000・枠 1〜1000・3つまで・URL は `http(s)://` で500文字まで）と DB の CHECK。画面のリンクは `rel="noopener noreferrer"`・`target="_blank"` | 単体・結合（400） |
| S13 | 参加者の画面にほかの人の名前が出る（キャンセル待ちの並び） | 参加者には自分の何番目かと人数だけを返す。名前を返すのは主催者・受付係の名簿だけ | 結合（ページの答えに名前がない） |
| S14 | ログに名前・アドレス・札が出る | 領域のログは交流会と申込みの ID・種類・結果・数だけ | 結合（ログを調べる） |
| S15 | 定期の仕事の重さで DB が止まる・時間切れ | 対象は自前で、待っている打診かキャンセル待ちか近い変更がある交流会だけ。交流会ごとに短いトランザクション | 読み合わせ |
