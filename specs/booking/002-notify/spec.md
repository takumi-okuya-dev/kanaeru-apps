答える人がいないため、PRD と構成の決めごとから AI が決めた（【仮決め】。理由は [research.md](./research.md)）。

- Q: Webhook の道 → A: `POST /api/v1/booking/webhooks/line/{channelId}`。AD-24 の `line-webhook/{channelRowId}` から、今の組み立てが「外のサービスの Webhook」として扱う形（`/api/v1/<領域>/webhooks/…`：CSRF の確かめの外・アプリが切のときだけ 404）にそろえた。組み立て（共通）を直さないため。AD-24 を直す【仮決め R1】
- Q: 紐づけのリンクの道と形 → A: 参加者が外から開く道に `/line-link/{linkToken}` を足す（AD-14 の一覧と `packages/contracts/src/core` の `participantPaths`）。`-` を含むのでアプリの key（英小文字と数字だけ）とぶつからず、予約語は足さない。あいさつに入れる URL は、API が LIFF ID を知らないので、画面の源（`WEB_URL`）＋道にする（LINE のトークのリンクは LINE の中のブラウザで開き、画面が LINE ログインを求める）【仮決め R2】
- Q: 紐づけの札の期限と使い方 → A: 7日・1回だけ。SHA-256 だけを持つ。同じ人が友だち追加をし直すと、前の札は消す。使った札は「使った」として残し、同じ人が開き直したら「もう紐づいています」を出す【仮決め R3】
- Q: あいさつ（友だち追加への返事）を守り（`NOTIFY_MODE`）でどう扱うか → A: `off` なら送らない（札も作らない）。`allowlist`・`on` なら、許可リストに関係なく返事（reply。友だち追加した本人への返事で、無料・リンクだけ）を送る。許可リストの人を足すには、その人の公式アカウントから見える ID が要り、紐づけて「確かめのメッセージ」を送ると画面に出るため【仮決め R4】
- Q: 知らせの送り先の決め方 → A: (1) 申込みのアカウントが、その交流会に当てはまる公式アカウント（組織に入れた交流会は組織の設定、ほかは持ち主の個人の設定）と紐づいていれば LINE (2) ほかで、本人が入れたメールアドレス（`booking_contact`）があればメール (3) どちらもなければ「送り先がない」と記録する。LINE で送れなかったときは、メールに切り替えない（二重に届かないように）【仮決め R5・R6】
- Q: メールの送り主と返信先をどこに持つか → A: 送り主の名前は「<組織の名前>（kanaeru）」（個人の持ち主なら表示名）で、画面では変えられない。返信先のアドレス（任意）は公式アカウントの設定と同じ行（`booking_line_channel.reply_to_email`）に持つ。LINE の値がなくても返信先だけを入れられるよう、LINE の値の列はそろって空か、そろって入っているかにする（CHECK）【仮決め R8】
- Q: 画面に出す鍵の末尾 → A: シークレットとアクセストークンのそれぞれの末尾4文字を、入れたときに平文で持つ（画面に出すたびに開けない）。値そのものは画面に戻さない【仮決め R9】
- Q: 入れた値の確かめ → A: 保存するときに LINE のボット情報（`GET /v2/bot/info`）を読み、アクセストークンが使えるかを確かめ、ベーシック ID（友だち追加のリンクのため）を持つ。メッセージを送らない読み取りなので、`NOTIFY_MODE` に関係なく本番では読む。手元とテストは偽の答え【仮決め R10】
- Q: だれが設定を変えられるか → A: 組織の設定は、その組織の管理者だけ（編集者・メンバー・組織の外の人は 403）。個人の設定は本人だけ（窓口が今の利用者のものしか扱わない）【仮決め R11】
- Q: 知らせの記録（`booking_notice`）に何を持つか → A: 申込み（確かめのメッセージは空）・種類・手段（LINE・メール・なし）・結果（送った・止めている・許可リストにない・送り先がない・送れなかった・メールの準備がない）・使った公式アカウントの設定・時刻。本文・宛先・トークンは持たない。今月の数は、その設定で LINE で送った数（確かめのメッセージも数える。日本時間の月）【仮決め R12】
- Q: 参加者のメールアドレスの入れ方 → A: 表（`booking_contact`。アカウントごとに1つ）と、本人が読む・入れる・消す窓口だけを作る。入れる画面は、申込み完了の画面を作る自前の申込みページの仕様で足す（FR-B84）【仮決め R14】
- Q: 手元で紐づけを試す方法 → A: 偽の送り手は、送ったものを数十件だけ覚える。試験用のログインが使える環境（手元とテスト）で偽の送り手のときだけ、覚えたものを読む窓口（`GET /api/v1/booking/dev/notify-outbox`）を出す。ログには本文・宛先・札を出さない【仮決め R18】
- Q: 大きな機能を止める設定 → A: `DOMAIN_FEATURES` の印は足さない。`NOTIFY_MODE`（本番の既定は `off`）が送ることの止め口で、設定の画面と紐づけは送らないので止めない【仮決め R19】

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 組織の管理者が LINE 公式アカウントを設定し、自分で確かめる (Priority: P1)

組織の管理者は、設定の「予約の知らせ」から組織の画面を開き、LINE 公式アカウントの Messaging API のチャネル ID・チャネルシークレット・チャネルアクセストークンを入れる。保存すると値は末尾だけになり、Webhook の URL（コピーのボタン）・紐づいた人数・今月送った数・あいさつの文の見本が出る。Webhook の URL を LINE の画面に貼り、自分で友だち追加してリンクから紐づけ、「自分に確かめのメッセージを送る」で届くかを確かめる（FR-B82・UJ のモックアップ A4）。

**Why this priority**: 公式アカウントの設定がないと、LINE の知らせも紐づけも始まらない。

**Independent Test**: 組織の管理者として値を入れると、答えに値が含まれず末尾4文字だけが返り、編集者・メンバー・ほかの人は 403 になることを確かめる。

**Acceptance Scenarios**:

1. **Given** 公式アカウントの設定のない組織, **When** 管理者がチャネル ID・シークレット・アクセストークンを入れて保存する, **Then** 画面にはシークレットとアクセストークンの末尾4文字・Webhook の URL・紐づいた人数 0・今月送った数 0・あいさつの見本が出る。値そのものは答えにもログにも出ない
2. **Given** 設定のある組織, **When** 管理者が「入れ直す」でアクセストークンだけを入れ直す, **Then** シークレットは前のまま、アクセストークンの末尾が変わる
3. **Given** 設定のある組織, **When** チャネル ID を別のものに変える, **Then** 前の公式アカウントの紐づけはすべて消える（公式アカウントが違えば LINE のユーザー ID も違うため）
4. **Given** 使えないアクセストークン, **When** 保存する, **Then** 「アクセストークンが合いません」が欄のそばに出て、保存されない
5. **Given** 組織の編集者・メンバー・組織の外の人, **When** 組織の設定を読む・変える, **Then** 403。画面は「組織の管理者だけが変えられます」
6. **Given** 鍵の束（`TOKEN_ENCRYPTION_KEYS`）の設定がない環境, **When** 保存する, **Then** 503 で「準備ができていません」
7. **Given** 自分が紐づいている, **When** 「自分に確かめのメッセージを送る」, **Then** 守り（`NOTIFY_MODE`）を通して自分にだけ送り、結果（送った・止めている・許可リストにない〈自分の ID を出す〉・送れなかった）がボタンのそばに出る。今月送った数が増える
8. **Given** 自分が紐づいていない, **When** 「自分に確かめのメッセージを送る」, **Then** 送らずに「まだ紐づいていません。公式アカウントを友だち追加し、届いたリンクを開いてください」を出す
9. **Given** 個人の持ち主, **When** 設定の「予約の知らせ」で自分の公式アカウントを入れる, **Then** 組織と同じに使える（本人だけ）

### User Story 2 - 参加者が公式アカウントを友だち追加し、リンクから紐づける (Priority: P1)

参加者が組織の公式アカウントを友だち追加すると、公式アカウントから「予約の知らせを LINE で受け取るには、リンクを開いてください」というあいさつが届く。リンクを開いて LINE でログインし、「紐づける」を押すと、その人の kanaeru のアカウントとその公式アカウントの友だちが結びつく。ブロックすると紐づけは消える（FR-B83）。

**Why this priority**: LINE で知らせを受け取る唯一の入口（LINE のユーザー ID はプロバイダーごとに違うため）。

**Independent Test**: 署名を付けた友だち追加の Webhook を送ると、偽の送り手に札つきのリンクを含むあいさつが残り、そのリンクの札でログインした人が紐づけると紐づいた人数が1になり、ブロックの Webhook で0に戻ることを確かめる。

**Acceptance Scenarios**:

1. **Given** 設定のある公式アカウント・`NOTIFY_MODE` が `allowlist` か `on`, **When** LINE から署名の合う友だち追加（`follow`）が届く, **Then** 200 をすぐ返し、その人に札つきのリンクのあいさつを返事で送る（札は SHA-256 だけを持つ）
2. **Given** 署名が合わない・ない, **When** Webhook が届く, **Then** 本文のない 400 で、何もしない
3. **Given** 知らない設定の ID, **When** Webhook が届く, **Then** 404
4. **Given** あいさつのリンク, **When** 参加者が開いてログインし「紐づける」を押す, **Then** 紐づけができ、「紐づけました。<名前>の予約の知らせが LINE に届きます」が出る
5. **Given** 期限（7日）の切れた札・使った札・知らない札, **When** 開く, **Then** 理由と「公式アカウントをいったんブロックしてから友だち追加し直すと、新しいリンクが届きます」を出す。使った札を本人が開き直したら「もう紐づいています」
6. **Given** 紐づいた人, **When** LINE からブロック（`unfollow`）が届く, **Then** 紐づけと、その人の使っていない札を消す
7. **Given** `NOTIFY_MODE` が `off`, **When** 友だち追加が届く, **Then** あいさつを送らず、札も作らない（ブロックは今までどおり紐づけを消す）
8. **Given** ほかの種類の知らせ（メッセージなど）, **When** 届く, **Then** 何もせず 200
9. **Given** 同じ公式アカウントで、別の LINE の友だちとしてすでに紐づいている人, **When** 新しいリンクで紐づける, **Then** 前の紐づけを置きかえる（1つの公式アカウントに1人1つ）

### User Story 3 - 知らせを送る業務の関数と守り (Priority: P1)

次の仕様（自前の申込み・キャンセル待ち）が、申込みの確定などのときに `sendNotice` を呼ぶ。booking は、交流会に当てはまる公式アカウントと紐づいていれば LINE、なければメール、どちらもなければ送らずに記録する。どの手段も守り（`NOTIFY_MODE`・`NOTIFY_ALLOWLIST`）を通し、手元とテストでは本物に送らない（FR-B80・FR-B81・FR-B86〜FR-B88）。

**Why this priority**: ステージングがないまま本番に出すための守りの中心。ここが崩れると外の人に誤って送る。

**Independent Test**: 単体と結合のテストで、送り先の選び方（LINE・メール・なし）と守り（`off`・`allowlist`・`on`・手元とテストは偽）を組み合わせて確かめ、記録に本文と宛先がないことを確かめる。

**Acceptance Scenarios**:

1. **Given** 組織に入れた交流会の申込み・そのアカウントが組織の公式アカウントと紐づいている, **When** `sendNotice`（確定）, **Then** LINE で送り、記録は手段 LINE・結果「送った」
2. **Given** 個人の交流会, **When** `sendNotice`, **Then** 持ち主の個人の公式アカウントを使う（組織の設定は使わない）
3. **Given** 紐づいていない・メールアドレスがある, **When** `sendNotice`, **Then** メールで送る（送り主の名前は「<組織の名前>（kanaeru）」・返信先は設定のアドレス）。メールの送信のサービスが決まるまで、本番では「メールの準備がない」と記録する
4. **Given** どちらもない（名簿に手で足した人など）, **When** `sendNotice`, **Then** 送らずに「送り先がない」と記録する
5. **Given** `NOTIFY_MODE` が `off`, **When** `sendNotice`, **Then** 送らずに「止めている」と記録する
6. **Given** `allowlist`・宛先が許可リストにない, **When** `sendNotice`, **Then** 送らずに「許可リストにない」と記録する。宛先が許可リストにあれば送る
7. **Given** `APP_ENV` が `local`・`test`, **When** どの設定でも, **Then** 本物の LINE・メールの API を呼ばず、偽の送り手に残す
8. **Given** どの知らせ, **When** 記録・ログを見る, **Then** 本文・宛先（LINE のユーザー ID・メールアドレス）・トークン・札は出ない
9. **Given** 6つの種類（確定・キャンセル待ち・打診〈期限つき〉・打診の期限切れ・日時や場所の変更・中止）, **When** 文面を作る, **Then** 交流会の名前・日時・場所・自分の状態と、渡されたリンク（取り消し・返事・カレンダー）が入る

### User Story 4 - 返信先のメールアドレスを入れる・参加者が自分のメールアドレスを持つ (Priority: P3)

管理者は、設定の画面のメールの節で、送り主の名前（変えられない）を確かめ、返信先のアドレス（任意）を入れる。参加者は、自分のメールアドレス（任意）を入れ・消せる（入れる画面は次の仕様。この版は窓口だけ）（FR-B84・FR-B85）。

**Independent Test**: 返信先を入れて読み直すと出ること、参加者のメールアドレスは本人の窓口だけが読み、名簿や設定の答えに出ないことを確かめる。

**Acceptance Scenarios**:

1. **Given** 設定の画面, **When** 開く, **Then** メールの節に「送り主：<組織の名前>（kanaeru）」と返信先の欄が出る
2. **Given** 返信先の欄, **When** メールアドレスの形でない値を入れる, **Then** 欄のそばに誤りが出る
3. **Given** 参加者, **When** 自分のメールアドレスを入れる・消す, **Then** 本人の窓口が答える。名簿・設定・ほかの人の答えには出ない

### Edge Cases

- Webhook の本文が大きすぎる（64KB を超える）：署名を確かめる前に本文のない 400
- Webhook が同じ友だち追加を2回送る（再送）：札を作り直し、前の札は消す（あいさつは2回届くことがある）
- 紐づけようとした札の公式アカウントの設定が、そのあと消えた・チャネル ID が変わった：札は消えているので「使えません」
- 設定のない組織の交流会：LINE は使わずメールか「送り先がない」
- 組織が消えた・個人の持ち主が退会した：その持ち主の設定・紐づけ・札は一緒に消える（知らせの記録は残り、設定への参照が空になる）
- LINE の API が 429・5xx・時間切れ：「送れなかった」と記録する（この版では送り直さない）
- 夜間（0時〜8時）は DB が止まる：Webhook は 503 になり、LINE が送り直す（LINE の再送の設定は組織が入れる。quickstart に書く）
- 同じ人が2つの組織の公式アカウントと紐づく：公式アカウントごとに別の紐づけ（組織どうしで混ざらない）

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 送る道具（LINE の Messaging API の push と reply・ボット情報の読み取り・Webhook の署名の確かめ・メールを送る形・本物に送らない偽の送り手・守りの判定）は、業務を知らない技術の道具として `platform/notify` に置く。業務（何をいつ誰に送るか・文面）は booking が持つ（AD-18・AD-24）。
- **FR-002**: 守りの設定 `NOTIFY_MODE`（`off`・`allowlist`・`on`。既定は `off`）と `NOTIFY_ALLOWLIST`（LINE のユーザー ID とメールアドレスの並び）を設定で読む。`APP_ENV` が `local`・`test` なら、いつも偽の送り手を使う（FR-B88）。
- **FR-003**: メールは送る形（送り主の名前・返信先・宛先・題・本文）だけを決め、この版は偽の送り手だけを持つ。送信のサービスは、booking を直さずにあとから足せる（Open Questions 8）。
- **FR-004**: 公式アカウントの設定（`booking_line_channel`）は、組織か個人のどちらか1つを持ち主にし、チャネル ID・シークレットとアクセストークンの暗号文（秘密の箱）・末尾・ベーシック ID・返信先のアドレスを持つ（FR-B82）。
- **FR-005**: 組織の管理者は組織の設定を、本人は個人の設定を、読む・入れる・入れ直す・LINE の値を消すことができる。ほかは 403（FR-B82）。
- **FR-006**: 設定の画面は、末尾だけ・Webhook の URL とコピー・紐づいた人数・今月 LINE で送った数・あいさつの見本・確かめのメッセージ・メールの送り主の名前（変えられない）と返信先・今の送り方（止めている・許可リストだけ・送る）を出す。
- **FR-007**: Webhook は、その設定のシークレットで `x-line-signature` を時間の差が出ない比べ方で確かめ、合わなければ何もしない。友だち追加ではリンクのあいさつを返事で送り、ブロックでは紐づけを消す。ほかの知らせは無視し、すぐ 200 を返す（FR-B83）。
- **FR-008**: 紐づけの札は使い切りで、SHA-256 だけを持ち、7日で切れる。参加者がリンクを開いて LINE でログインし確かめると、紐づけ（設定・公式アカウントから見えるユーザー ID・アカウント）を作る。LINE ログインの `sub` を送り先に使わない（AD-24）。
- **FR-009**: `sendNotice(db, deps, { entryId, kind, … })` は、送り先を LINE → メール → なしの順に決め、守りを通して送り、`booking_notice` に記録する（FR-B81・FR-B87）。
- **FR-010**: 知らせの種類は、確定・キャンセル待ち・打診（期限つき）・打診の期限切れ・日時や場所の変更・中止の6つと、設定の画面の確かめのメッセージ。文面には交流会の名前・日時・場所・自分の状態・渡されたリンクを入れる（FR-B80・FR-B86）。
- **FR-011**: 知らせの記録は、相手の申込み・種類・手段・結果・時刻だけを持つ。本文・メールアドレス・LINE のユーザー ID・トークン・札はログにも記録にも出さない（FR-B87・Constitution II）。
- **FR-012**: 参加者は、自分のメールアドレス（任意。予約の知らせのためだけ）を入れ・読み・消せる。主催者には見せない（FR-B84・Constitution II）。
- **FR-013**: 公式アカウントの設定・紐づけ・札は持ち主（組織・個人）の中に閉じ、ほかの組織の設定・紐づけに届かない。
- **FR-014**: 紐づけの画面は参加者が外から開く道（AD-14）に置き、外枠のナビを出さない。

### Key Entities

- **公式アカウントの設定（booking_line_channel）**：組織か個人に0か1行。LINE の値（暗号文と末尾）と返信先。
- **紐づけ（booking_line_link）**：設定・公式アカウントから見える LINE のユーザー ID・アカウント。
- **紐づけの札（booking_line_link_token）**：設定・LINE のユーザー ID・札の SHA-256・期限・使った時刻。
- **連絡のメールアドレス（booking_contact）**：アカウントごとに0か1行。
- **知らせの記録（booking_notice）**：申込み・種類・手段・結果・設定・時刻。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 組織の管理者が、設定の画面だけで公式アカウントの設定から自分への確かめのメッセージまでを10分以内に終えられる（quickstart の手順）。
- **SC-002**: `NOTIFY_MODE` が `off` の環境で、どの知らせも LINE とメールの API を1回も呼ばない（結合のテストで外への出口が呼ばれないことを確かめる）。
- **SC-003**: 手元とテストで、どの設定でも本物の API を呼ばない（単体のテスト）。
- **SC-004**: 知らせの記録・ログ・設定の答えに、本文・宛先・トークン・札が1つも出ない（結合のテストでログと答えを調べる）。
- **SC-005**: ほかの組織・ほかの人の設定の窓口は、すべて 403（結合のテスト）。

## Assumptions

- 交流会の持ち主・組織・役目の判定は event-002、組織の役割は suite の `findMembership` をそのまま使う。
- 申込みのアカウントは、自前の申込みページの仕様から入る（この版の名簿の行のアカウントは空なので、`sendNotice` は「送り先がない」になる）。
- メールで申し込む人（アカウントのない人）のメールアドレスは、メールで申し込む仕様で申込みの側に持つ。`sendNotice` の送り先の決め方は、そのときに足す。
- LINE の Webhook の再送（Webhook redelivery）は、組織が LINE の画面で入れる（夜間に DB が止まっているあいだの知らせを取りこぼさないため）。
- インフラ（Secret Manager・Cloud Run の環境の変数）の変更は、この仕様では行わず、[quickstart.md](./quickstart.md) に必要なものを書く。
