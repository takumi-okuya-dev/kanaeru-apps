# Research: 予約の知らせの仕組み（booking-002）

2026-11-20 作成。答える人がいないため、PRD 受付アプリの予約と構成の決めごと（AD-24 ほか）から決めた。【仮決め】は主催者の確かめを待つ。番号は spec.md の Clarifications と同じ。

## R1 Webhook の道【仮決め】

- **Decision**：`POST /api/v1/booking/webhooks/line/{channelId}`（`channelId` は `booking_line_channel.id`）。
- **Rationale**：組み立て（`app.ts`）は、`/api/v1/<領域>/webhooks/…` を「外のサービスの Webhook」として、フォームの形の CSRF の確かめを通さず（`WEBHOOK_PATH`）、アプリが切のときだけ 404 にする（`MACHINE_PATH` の `requireAppNotOff`）。AD-24 の `line-webhook/{channelRowId}` のままだと、組み立て（共通）を直す共通の PR が要る。道の形だけを今の決まりにそろえ、組み立ては直さない。回数の制限は、Meta の Webhook と同じく `/api/v1` の書く道の IP ごとの制限がそのまま効く。
- **Alternatives**：`/api/v1/booking/line-webhook/{id}` と組み立ての正規表現を足す（共通の PR が要る・決まりが2つになる）。
- AD-24 の道を直す（2026-11-20 の注を付ける）。

## R2 紐づけのリンクの道と URL【仮決め】

- **Decision**：参加者が外から開く道に `/line-link/$linkToken` を足す（`PARTICIPANT_ROUTE_PATTERNS.lineLink`・`participantPaths.lineLink`）。あいさつに入れる URL は `WEB_URL` ＋ この道。
- **Rationale**：AD-14 は外から開く道を `packages/contracts/src/core` の1か所に持つ。`-` を含む頭はアプリの key（英小文字と数字だけ）とぶつからないので、予約語（`RESERVED_APP_KEYS`）は足さない。ミニアプリの URL（パーマリンク）は LIFF ID が要るが、LIFF ID は画面の組み立てに埋める値（`VITE_LIFF_ID`）で API は知らない。API に LIFF ID の設定を足すとインフラの変更が要る。LINE のトークで開いた URL は LINE の中のブラウザで開き、画面は LIFF の外なので `liff.login()` で LINE ログインに移り、同じ道に戻る（Open Questions 3・7 で確かめる）。札は7日で切れるので、置き場所の URL が変わっても困らない。
- **Alternatives**：ミニアプリの URL（API に LIFF ID の設定を足す）。`/e/…` の下（交流会に属さないので合わない）。

## R3 紐づけの札【仮決め】

- **Decision**：32バイトの乱数を base64url にした札。DB には SHA-256（16進）だけ。期限は7日。1回だけ使え、使ったら `used_at` と使った人を残す。同じ設定・同じ LINE の友だちの使っていない札は、新しい札を作るときとブロックのときに消す。
- **Rationale**：AD-24（使い切り・SHA-256 だけ）。友だち追加してすぐ開くとは限らないので、24時間より長くする。使った札を残すのは、本人が開き直したときに「もう紐づいています」と出すため。
- **Alternatives**：24時間（開くのが遅い人が困る）。使ったら消す（開き直した人に「使えません」と出て迷う）。

## R4 あいさつと守り【仮決め】

- **Decision**：友だち追加では、`NOTIFY_MODE` が `off` なら何もしない（札も作らない）。`allowlist`・`on` なら、許可リストに関係なく、LINE の返事（reply。replyToken を使う）であいさつを送る。予約の知らせ（push）と確かめのメッセージは、許可リストの判定を通す。
- **Rationale**：許可リストには公式アカウントから見える ID を入れる。その ID は紐づけたあとの「確かめのメッセージ」で本人の画面に出すので、あいさつまで許可リストで止めると、確かめる人を許可リストに足せない（鶏と卵）。あいさつは、本人が友だち追加した操作への返事で、リンクだけを入れ、交流会のことを書かない。reply は LINE のメッセージの数に数えない。`off` では返事も送らない（本番の既定で、外の人に何も送らない）。
- **Alternatives**：あいさつも許可リストで止める（確かめる人の ID が分からない）。許可リストを account の ID にする（AD-24 と違う・運営者が account の ID を引く手間）。

## R5 当てはまる公式アカウント【仮決め】

- **Decision**：交流会を組織に入れていれば、その組織の設定。入れていなければ、交流会の持ち主の個人の設定。どちらもなければ LINE を使わない。
- **Rationale**：AD-24（組織の公式アカウントから送る）と、個人の持ち主の交流会（PRD 3章の「組織（個人の持ち主なら、その人）」）。交流会の組織は event の `findEventOrganizationId`、持ち主は `findEventOwnerAccountId`（どちらも event の `index.ts`。AD-3）。

## R6 送り先の順と、送れなかったとき【仮決め】

- **Decision**：LINE（紐づけがある）→ メール（`booking_contact`）→ なし。LINE が送れなかった（ブロック・429・5xx・時間切れ）ときは、メールに切り替えず「送れなかった」と記録する。この版では送り直さない。
- **Rationale**：PRD FR-B81 の順。切り替えると、LINE が実は届いていたとき（時間切れ）に二重に届く。送り直しは、打診の定時の処理を作る仕様で決める（打診は期限があるので、送り直しが要るかもしれない）。
- 守りの判定は手段ごとの宛先で行う（LINE は公式アカウントから見える ID、メールはアドレス）。止めたときは「止めている」「許可リストにない」と記録し、次の手段は試さない（守りで止めた知らせを、別の手段で抜けないため）。

## R7 送る道具の形（`platform/notify`）

- **Decision**：`platform/notify` に、守りの判定（`decideDelivery`）・LINE の HTTP の呼び方（push・reply・ボット情報。`deps.fetch` を使い、5秒で切る。push には `X-Line-Retry-Key`）・Webhook の署名の確かめ（HMAC-SHA256 の base64 を `timingSafeEqual` で比べる）・メールの送る形と送り手の差しこみ口（`EmailSender`）・偽の送り手（送ったものを50件まで覚える）・それらを束ねた `createNotifier` を置く。道具の型（`Notifier`）は土台（`kernel/notifier.ts`）に置き、組み立てが設定から作って `DomainRouteDeps.notifier` で領域に渡す。
- **Rationale**：AD-18・AD-24（送る道具は技術の道具で、業務を知らない）。土台は共通（platform）を読めない（境界の決まり）ので、領域に渡す型は土台に置く（`SecretBox` の型を土台の `DomainRouteDeps` が持つのと同じ）。許可リストは Secret Manager の値なので、`DomainConfig` に入れず、道具の中に閉じる（`metaApp`・`isJobRequest` と同じ考え方）。メールの送信のサービスは、`EmailSender` を1つ足し、組み立てで渡せばよい（booking は直さない）。
- `APP_ENV` が `local`・`test` のときは、設定の確かめ（`kernel/config.ts`）が `notify.fakeOnly = true` にし、`createNotifier` は本物の HTTP を作らない（AD-24 が環境の名前で決めると決めている）。
- **Alternatives**：booking の中に送る道具を書く（AD-18 に反する・ほかのアプリで作り直しになる）。`@line/bot-sdk` を入れる（依存が増える。使うのは3つの窓口だけ）。

## R8 メールの送り主と返信先【仮決め】

- **Decision**：送り主の名前は「<組織の名前>（kanaeru）」（個人の持ち主は「<表示名>（kanaeru）」）。返信先は `booking_line_channel.reply_to_email`（任意）。LINE の値の列は、そろって空か、そろって入っているか（CHECK）にして、返信先だけの行を許す。送り主のアドレスは、送信のサービスとドメインが決まったら設定に足す（Open Questions 8）。本番でメールの送り手がないときは「メールの準備がない」と記録する。
- **Rationale**：PRD FR-B85。表を分けると、持ち主（組織か個人）の決まりと CHECK を2つ持つことになる。
- **Alternatives**：`booking_mail_setting` を別に作る。

## R9 鍵の末尾【仮決め】

- **Decision**：シークレットとアクセストークンの末尾4文字を、入れたときに平文で持つ（`channel_secret_tail`・`access_token_tail`）。
- **Rationale**：画面を開くたびに秘密の箱で開けない（開けた値がメモリに残る時間を短くする）。4文字なら、残りの長さ（シークレット32文字・トークン100文字以上）から見て、推測の手がかりにならない。

## R10 入れた値の確かめ【仮決め】

- **Decision**：保存するとき、ボット情報（`GET https://api.line.me/v2/bot/info`）を読む。401 なら「アクセストークンが合いません」で保存しない。届かなければ「LINE に確かめられませんでした」（502）で保存しない。答えのベーシック ID（`@xxxx`）を持つ（自前の申込みページの「公式 LINE を友だち追加」のリンクに使う。PRD FR-B43）。メッセージを送らない読み取りなので、本番では `NOTIFY_MODE` に関係なく読む。手元とテストは偽の答え（ベーシック ID `@fake`。アクセストークンが `invalid` で始まると 401 として扱う）。
- **Rationale**：入れ間違いを、知らせが届かないと分かる前に見つける。
- チャネル ID とシークレットの組み合わせは、LINE に問い合わせて確かめる窓口がない（Webhook の署名で分かる）。画面に「LINE の画面で Webhook の『検証』を押して、成功になるかを確かめてください」と書く。

## R11 権限【仮決め】

- **Decision**：組織の設定は、要求のたびに suite の `findMembership` で役割を引き、管理者だけ。ほか（編集者・メンバー・組織の外）は 403 `BOOKING_NOTIFY_FORBIDDEN`。個人の設定の窓口は、今の利用者の設定しか扱わない（道に人の ID を持たない）。
- **Rationale**：AD-24「組織のものを変えられるのは組織の管理者だけ、個人のものは本人だけ」。組織の外の人も 403 にする（組織の ID は推測できない uuid）。

## R12 知らせの記録【仮決め】

- **Decision**：`booking_notice`（申込み〈確かめのメッセージは空〉・設定〈消えたら空〉・種類・手段・結果・時刻）。結果は `sent`（送った）・`off`（止めている）・`not_allowed`（許可リストにない）・`no_destination`（送り先がない）・`failed`（送れなかった）・`unavailable`（メールの準備がない）。今月の数は、その設定で手段 LINE・結果「送った」の数（日本時間の月の初めから）。
- **Rationale**：AD-24・PRD FR-B87。確かめのメッセージも LINE の数に数えられるので数える。主催者が申込みごとに「何を送ったか」を見る画面は、知らせを送る仕様で足す（この版は記録だけ）。

## R13 Webhook の受け方

- 本文の上限は 64KB（署名を確かめる前に読む量を縛る。組み立ての 100KB の上限より小さく）。本文はそのままの文字で読み、署名を確かめてから JSON にする。署名が合わない・本文が読めないときは本文のない 400（Meta の Webhook と同じ）。
- 知らない設定・LINE の値がない設定・秘密の箱がない環境は 404。
- 友だち追加（`follow`）：`source.type` が `user` で `userId` があるときだけ。札を作り、あいさつを reply で送る（アクセストークンを開ける）。ブロック（`unfollow`）：紐づけと使っていない札を消す。ほかの種類は無視する。
- 返事を送るまで待ってから 200 を返す（LINE の HTTP は5秒で切る）。Cloud Run は答えを返したあとの処理を止めることがあるため、答えの前に済ませる。
- ログには、設定の ID・知らせの数と種類・結果だけを出す。本文・署名・ユーザー ID・札は出さない。
- 夜間（DB が止まる0時〜8時）の Webhook は 503 になる。LINE の Webhook の再送を入れておけば、LINE が送り直す（quickstart）。

## R14 参加者のメールアドレス【仮決め】

- **Decision**：`booking_contact`（`account_id` が主キー・`email`）。窓口は本人の読む・入れる・消す（`/api/v1/booking/me/contact`）。主催者の窓口と名簿には出さない。入れる画面は、申込み完了の画面（自前の申込みページの仕様。PRD FR-B43・FR-B84）で足す。退会すると消える（CASCADE）。
- **Rationale**：Constitution II（任意・本人が消せる・主催者に見せない）。組織ごとに分けると、同じ人が組織ごとに入れ直すことになる。

## R15 ブロックと友だち追加のし直し

- ブロック（`unfollow`）で紐づけを消す（PRD FR-B83「ブロックされたら紐づけを止める」）。友だち追加し直すと、新しいあいさつと札が届き、もう一度紐づける。

## R16 紐づけのぶつかり

- 1つの設定の中で、LINE の友だち1人に1つ、アカウント1つに1つ（どちらも一意）。紐づけるときは、同じ設定の「同じ LINE の友だち」か「同じアカウント」の前の紐づけを消してから作る（同じトランザクション）。札は `FOR UPDATE` で押さえ、2回押しても1つだけ使う。

## R17 設定の読み方（`kernel/config.ts`）

- `NOTIFY_MODE`：`off`・`allowlist`・`on`（既定 `off`）。
- `NOTIFY_ALLOWLIST`：カンマで並べた LINE のユーザー ID（`U` と16進の32文字）かメールアドレス。メールアドレスは小文字にそろえて比べる。秘密の値と同じく Secret Manager から渡す（AD-24）。
- `Config.notify = { mode, allowlist, fakeOnly }`。`fakeOnly` は `APP_ENV` が `local`・`test` のとき true。
- 領域には値を渡さず、組み立てが `createNotifier` で道具にして渡す（`DomainRouteDeps.notifier`。手で組み立てるテストは書かなくてよく、なければ booking は「止めている」の偽の道具を使う）。

## R18 手元で紐づけを試す

- 偽の送り手は、送ったもの（手段・宛先・本文）を50件まで覚える（ログには手段と文字数だけ）。`GET /api/v1/booking/dev/notify-outbox` は、試験用のログインが使える（`TEST_LOGIN_ENABLED`。staging・production では起動のときに止まる）かつ偽の送り手のときだけ、ログインした人に覚えたものを返す。ほかは 404。E2E と手元の quickstart は、ここからあいさつのリンクを読む。

## R19 大きな機能を止める設定

- `DOMAIN_FEATURES` の印は足さない。送ることは `NOTIFY_MODE`（本番の既定 `off`）で止める。設定の画面・Webhook・紐づけは外の人に送らない（`off` ではあいさつも送らない）ので止めない。設定の画面には今の送り方（止めている・許可リストだけ・送る）を出す。

## R20 設定の画面の置き場所

- 設定の画面の項目（`feature.settings`）に「予約の知らせ」（アプリの設定のまとまり。道 `/settings/reception/notify`）を足す。開くと、個人の設定と、自分が管理者の組織の一覧（組織の設定への入口）が出る。組織の画面（suite の設定 › 組織）には、`feature.organization.links` で「予約の知らせの設定」（`/settings/reception/notify/organizations/$organizationId`）を出す。管理者でない人が開くと「組織の管理者だけが変えられます」を出す。

## R21 入力の形

- チャネル ID：数字だけ（1〜20文字）。シークレット：16進の32文字。アクセストークン：空白のない20〜1000文字（LINE の長期のトークンは170文字ほど）。入れ直しは、どれか1つ以上（初めはチャネル ID・シークレット・アクセストークンの3つが要る）。チャネル ID が変わったら、シークレットとアクセストークンも入れ直す（前の公式アカウントの値を使わない）。
- 返信先：メールアドレスの形（254文字まで）か空。

## R22 退会

- 個人の設定・紐づけ・札・連絡のメールアドレスは、アカウントを指す外部キーの CASCADE で消える。退会の確かめの中身に「LINE 公式アカウントの設定（個人）」を足す（設定があるときだけ）。組織の設定は組織が消えると消える。

## 計画のときのセキュリティの確かめ（[開発の流れの決まり](../../../docs/rules/development-flow.md) 2）

外からの知らせ（Webhook）と外のサービスの秘密の値（LINE のチャネルシークレット・アクセストークン）を持つので、`security-audit` スキルの観点（入力の境界・認証と認可・秘密の扱い・ログ・SSRF・再送と順番・DoS）で確かめた。

| # | 見つけたこと（起こりうること） | 対策 | 確かめ |
|---|---|---|---|
| S1 | 偽の Webhook で、だれかの紐づけを消す・札を作らせる | その設定のシークレットで `x-line-signature` を確かめる（HMAC-SHA256・`timingSafeEqual`・長さが違えば先に落とす）。合わなければ何もせず本文のない 400 | 結合のテスト（署名なし・違う・別の設定のシークレット） |
| S2 | 署名の比べ方の時間の差で、署名を推し量る | `timingSafeEqual`（長さをそろえた比べ） | 単体のテスト |
| S3 | 大きな本文・たくさんの要求で止める（DoS） | 本文 64KB の上限を署名の前に。`/api/v1` の書く道の IP ごとの回数の制限（Meta の Webhook と同じ） | 結合のテスト（大きな本文は 400） |
| S4 | シークレット・トークンが DB・答え・ログから漏れる | 秘密の箱（AES-256-GCM・ひもづけは設定の ID と種類）。答えは末尾4文字だけ。ログに本文・署名・トークン・札・宛先を出さない（ログの組み立ても本文を出さない） | 結合のテスト（答えとログの中に値がない） |
| S5 | 包んだ値を別の行に写して、別の組織のトークンで送らせる | 秘密の箱のひもづけ（`<設定の ID>:secret`・`<設定の ID>:token`）。写しても開けない | 結合のテスト |
| S6 | ほかの組織の設定を読む・書く（IDOR） | 組織の設定は要求のたびに管理者かを引く。個人の設定は今の利用者のものだけ。Webhook は道の設定の ID でだけ探す | 結合のテスト（編集者・メンバー・外の人は 403） |
| S7 | 札の推測・使い回し・盗み見 | 32バイトの乱数・SHA-256 だけを持つ・7日・1回だけ（`FOR UPDATE`）・ログに出さない・URL は利用者の LINE のトークにだけ届く | 結合のテスト（期限切れ・使った・知らない） |
| S8 | LINE ログインの `sub` を送り先に使い、別人に届く | 送り先は Webhook の公式アカウントから見える ID だけ（紐づけの表）。`sub` は使わない | コードの読み合わせ・結合のテスト |
| S9 | 本番で誤って外の人に送る（ステージングがない） | `NOTIFY_MODE` の既定 `off`・`allowlist`・手元とテストは偽の送り手だけ（設定で決める）・あいさつも `off` では送らない | 単体のテスト（守りの組み合わせ）・結合のテスト（外への出口が呼ばれない） |
| S10 | SSRF（入れた値で、内側の宛先に要求させる） | LINE の宛先は決まった `https://api.line.me` だけ。利用者の入れた値は URL に入れない（ヘッダーのトークンだけ） | コードの読み合わせ |
